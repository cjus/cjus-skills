# PR review: Add a guide profile to createbook and makebook

Reviewed 2026-09-20 against `PLAN.md` and `pr-summary-2026-09-20.md`. The branch has no
commits; the diff reviewed is `git diff` over ten tracked files plus the three untracked
fixture folders.

### Scope of this review

Read by line: `check-book.sh`, `check-provenance.sh`, `build-book.py` (the whole diff),
`createbook/SKILL.md`, `makebook/SKILL.md`, `updatebook/SKILL.md`, `README.md`,
`plugin.json`, and the `guide`, `guide-under-narration` and `jq-unrunnable` fixtures.
Findings were checked by execution, not by eye: the six fixtures were run through
`check-book.sh`, the old and new builders were loaded side by side and their chapter HTML,
figure records, `plain` text and glossary output compared on `fence`, `overview`,
`overview-nothing-carried` and `provenance`, and the slide and appendix paths were exercised
with a modified copy of the `guide` fixture.

**Not read by line:** `reference/chapter-prose.md` and `NOTES.md` (prose specs, reviewed for
presence and citation targets only), and the `## Deviations` reasoning in `PLAN.md` was taken
at face value where it describes work already re-verified above.

## Summary

Adds a second rule set (`guide`) to `createbook`, selected by `"profile"` in `book.json`; a
`reading` edition to `makebook` that strips paragraph tags and moves the header's `Draws on`
and `Fills in` rows to chapter endnotes; boxed callouts; an appendix file kind; a
lesson-script slide row that stays off the Figures page; a glossary sort and render fix in
both builders; reader-facing source display names; and a fixture pinning the jq guard.

## What is working well

- **Backward compatibility is real, not asserted.** I loaded `HEAD`'s builder and the
  branch's builder in the same process and compared output on four narration fixtures:
  chapter HTML, figure records, harvested `plain` text and glossary HTML are all identical.
  A book with no `profile`, no `edition` and no `slide_figures` binds byte for byte as before.
- **The `set -u` trap on the no-jq path was caught before it shipped.** Initialising
  `declared_profile` and `source_keys` beside the other declarations, rather than inside the
  jq block, is exactly right, and the new no-jq note that names which rule set actually ran
  is the difference between a screen of failures and a screen of failures you can act on.
- **The `check-provenance.sh` fix is the good kind of scope creep.** `[val] if
  isinstance(val, str) else val` iterating a dict over its keys is a genuinely nasty bug —
  two fabricated failures per source and the real file never opened — and the replacement
  validates the list form too instead of just tolerating the object form. The `path`-missing
  guard reports rather than crashes.
- **`inline_code_html` escapes first and then re-introduces `<code>`.** That ordering is what
  makes it safe, and the docstring says so. Lifting `gloss_sort_key` so the sort and the
  letter heading come from one definition is the right shape for a bug that had to be fixed
  twice.
- **The `jq-unrunnable` fixture has two halves.** Most regression fixtures for a guard only
  assert the guard fires; asserting that the same book passes in the strongest mode with a
  working jq is what stops a checker that rejects everything from reading as a pass.
- **The `PARA_TAG_RE` anchoring rationale** ("a bracketed pair of numbers mid-sentence is
  prose the book wrote and stripping it would silently edit the text") is the kind of comment
  that stops the next person loosening the regex.

## Issues found

### Critical

🔴 **SVG lesson-script slides are never measured against the legibility floor**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:1535-1560` (`emit_slide`),
called from `:1665`

**What I see:**

```python
def emit_slide(inner, caption, is_svg, aspect=None, source=None, raster=None):
    ...
    if is_svg:
        inner = scope_svg_css(inner, sid)
        inner = re.sub(r"<svg\b", f'<svg id="{sid}"', inner, count=1)
        if source is not None:
            legible = svg_legibility(source, False)
            if legible:
                rec["min_pt"] = legible[0] * SLIDE_WIDTH_SHARE
                rec["vb_width"] = legible[1]
    elif raster is not None:
        ...
```

and the only call site:

```python
if slide_dir and ref and html_mod.unescape(ref.group(1)).lstrip("./").startswith(slide_dir):
    return emit_slide(tag, caption, False, aspect, text or None, blob)
```

`is_svg` is hard-coded `False` there, correctly — the inner HTML is an `<img>` tag, not an
inlined `<svg>`. But the legibility measurement is gated on `is_svg` rather than on
`source`, so for an `.svg` slide the first branch never runs; and `blob` is only assigned in
the raster branch of `from_img`, so it is still `None` for an `.svg` and the `elif` does not
run either. **Neither branch executes.** No `min_pt`, no `vb_width`, no
`unchecked_text`.

Compare the sibling `emit`, which gets this right by keying on the value rather than the
flag:

```python
if source is not None:
    legible = svg_legibility(source, is_wide)
```

**Verified by execution.** Running `figurize` over `fixtures/guide`:

```
FIGURES [{'id': 1, 'number': '1.1', ..., 'min_pt': 11.63, 'vb_width': 520.0}]
SLIDES  [{'chapter': 1, 'caption': 'Week one, opening slide', 'number': '1.s1'}]
```

`svg_legibility` on that same slide returns `(17.28, 400.0)`, so the number exists and is
simply never recorded. The `--report` block at `:3379-3400` then filters
`[f for f in slides if f.get("min_pt") ...]`, which for SVG slides can never be non-empty.

**The risk:** this is the failure mode this codebase names as the worst one it has, in its
own words at `check-book.sh:54-60`: *"A checker that can report OK without having run is
worse than no checker."* The report prints `slides: N lesson-script slide(s), set at 62%
measure` and then silently omits the one measurement that justified shrinking the art. A
slide whose labels print at 4pt passes with no line of output. `makebook/SKILL.md` §
Lesson-script slides states the opposite in bold — *"is still **measured against the
legibility floor**, at the narrower width it actually prints at"* — and `PLAN.md` Phase 2
carries "The legibility floor still applies to the art" as a delivered checkbox. It is not
delivered for the SVG case, which is the documented and recommended authoring form.

It is also a regression in the narrow sense: before this branch a slide under
`diagrams/slides` was an ordinary figure and `emit` measured it. Declaring `slide_figures`
now buys the compact row at the cost of the check.

The fixture would not have caught it either way: that slide computes to
`17.28 × 0.62 = 10.7pt` against a `MIN_LEGIBLE_PT` of `8.0`, so it clears the floor and the
`tight` list would have been empty even with the bug fixed.

**Suggested fix:** key the branch on the value, exactly as `emit` does, and let the raster
branch stay an `elif`:

```python
        if source is not None:
            # Measured against the narrow slide column rather than the text
            # measure, because that is the width it prints at.
            legible = svg_legibility(source, False)
            if legible:
                rec["min_pt"] = legible[0] * SLIDE_WIDTH_SHARE
                rec["vb_width"] = legible[1]
        elif raster is not None:
            ...
```

The `scope_svg_css` / `id` injection genuinely does belong under `is_svg` — keep it there,
guarded separately — since the referenced form is never inlined.

Then give the fixture teeth. A second slide SVG with, say, `font-size="9"` in a 400-wide
viewBox lands at `9 × 0.62 ≈ 5.6pt` and makes the `tight` branch fire; asserting that line
appears is what stops this reverting. The existing slide should stay, so the fixture also
proves a legible slide is *not* reported.

**Learning note:** when you fork a function, the thing most likely to rot is a parameter
whose meaning changed between the two copies. Here `is_svg` means "the inner HTML is an
inlined SVG" in both, but only `emit` noticed that it is not the same question as "do we
have SVG source to measure". Deriving the branch from the data you are about to use — the
truth — rather than from a flag that travels beside it is what keeps a fork from drifting.

### Important

🟡 **An appendix's carried-in terms are graded against a chapter number they do not have**

📍 Location: `plugins/bookcraft/skills/createbook/scripts/check-book.sh:811` and `:1082-1099`

**What I see:**

```sh
[ -n "$cterm" ] && carried_records+=("$((10#$num))|$base|$cterm")
```

For an appendix, `num` was reassigned to `app_num` at `:319`, so appendix 1 records `1`. The
cross-check at `:1097` then reads that as chapter 1:

```sh
elif [ "$hit_ch" -ge "$rec_ch" ]; then
  problem "$rec_base: the carried-in line names \"$rec_term\", taught in chapter $hit_ch, ..."
```

**Verified by execution.** Adding an `## In short` with `Carried in: **profile**` to the
guide fixture's appendix (the glossary teaches `profile` in chapter 1) produces:

```
FAIL  guide-fixture-appendix-1-the-labels.md: the carried-in line names "profile",
      taught in chapter 1, which is not earlier than chapter 1
```

That book is correct. An appendix binds after every chapter, so every glossary chapter number
is earlier than it by construction and this comparison can only ever produce a false failure.

**The risk:** a false FAIL is more expensive than a missed one here, because the operator's
only remedies are to delete a correct carried-in line or to stop using `## In short` in
appendices — both of which quietly remove the orientation the guide profile exists to
provide. The comment at `:820-824` says appendices are exempt from *requiring* these sections
but "Where one IS present it is still checked", so this path is deliberate rather than
accidental; it just checks the wrong thing.

**Suggested fix:** record appendices at a rank above every chapter, so the ordering rule
still runs and can only fail for a genuinely forward reference:

```sh
# An appendix binds after every chapter, so every glossary chapter number is
# earlier than it. Ranking it above the chapters keeps the ordering check live
# without making "taught in chapter 1" read as a failure for appendix 1.
if [ "$is_appendix" -eq 1 ]; then
  rec_rank=$((10000 + 10#$num))
else
  rec_rank=$((10#$num))
fi
[ -n "$cterm" ] && carried_records+=("$rec_rank|$base|$cterm")
```

and reword the message so it does not print `chapter 10001`: carry the kind in the record, or
report the file's own label. The message at `:1098` names both numbers, so both halves need
the fix, not just the comparison.

**Learning note:** the moment you reuse a variable (`num`) for two different kinds of
identity, every downstream consumer inherits an assumption nobody restated. The tag check at
`:586-614` was updated for this and the carried-in record was not, which is the usual shape:
the consumers you can see from the edit get fixed, the one three hundred lines away does not.
Grepping for every read of a variable whose meaning you widened is cheaper than finding this
from a bug report.

🟡 **The step-4 `book.json` template hands every new book `"edition": "reading"` and `"slide_figures"` with no prose explaining either**

📍 Location: `plugins/bookcraft/skills/createbook/SKILL.md:283-284`

**What I see:** the fenced `book.json` block that step 4 tells the skill to write now carries

```json
  "edition": "reading",
  "slide_figures": "diagrams/slides",
```

and `grep -n 'edition\|slide_figures' createbook/SKILL.md` returns those two lines and
nothing else. Every other key in that block — `profile`, `sources`, `provenance`,
`suggested_reading`, `tags`, `glossary`, `exclude`, `unsourced` — has a bolded paragraph
directly beneath it saying what it does and what absent means. These two have none.

**The risk:** step 4 is an instruction to an agent, and the fenced block is the template it
copies. `PLAN.md` Phase 2 says "Keep the existing edition as the default so nothing rebinds
differently until asked" — but a book written from this template declares the reading edition
without anyone asking, which inverts that guarantee at the only place it is actually
operationalised. `slide_figures` is worse in one respect: it names a folder that may not
exist, and if it does, it silently takes every figure under it off the Figures page. Neither
key has a paragraph the agent can read to decide it should not be there, and `profile`, the
one key in the block that *is* explained, is set to `"guide"` — so the block does not read as
"all keys, choose among them" either.

**Suggested fix:** either drop both keys from the template and point at `makebook/SKILL.md §
The reading edition` and `§ Lesson-script slides` from a single sentence, or add the two
missing paragraphs on the pattern of the others. The shortest version of the second:

> **`edition` picks which edition `/makebook` binds by default.** Absent means the default
> edition, which is what every book bound before the option existed gets. Set `"reading"`
> only where the operator asked for it; `--reading-edition` binds it for one run without
> committing the folder to it.
>
> **`slide_figures` names a folder of lesson-script slides.** Images under it render as a
> compact row, take no figure number and stay off the Figures page. Omit it unless the book
> actually has such a folder, since declaring it changes how every image beneath it binds.

**Learning note:** in a skill file the example *is* the API. A key that appears in a template
with no accompanying rule will be copied, because the reader has nothing else to go on — the
absence of prose reads as "this is standard", not as "this is optional".

🟢 **`ok` in the callout awk is incremented and never read**

📍 Location: `plugins/bookcraft/skills/createbook/scripts/check-book.sh:906`

```awk
if ($0 ~ /^[[:space:]]*> \*\*(Decide|Warning|In the room|Grade this)\.\*\* [^[:space:]]/) {

`ok` is never printed and never tested; the `COUNT` line carries `n`, which is what the

guide about a repo that shows `cat CLAUDE.md` in a fence, with `CLAUDE.md § ...` as a source

## Questions

1. **Was the slide legibility path exercised at all during validation?** `PLAN.md`'s evidence
   table records six binds with `epubcheck` clean, which the slide bug would not disturb —
   the art still renders, it is only the measurement that goes missing. If the `slides:`
   report line was read during those binds, it would have shown a count with no measurement
   beneath it. Worth knowing whether the line was read, because it changes what the fixture
   should assert.
2. **Is `"edition": "reading"` in the step-4 template deliberate?** If the intent is that
   guide-profile books default to the reading edition, that is a defensible position but a
   different one from Phase 2's "existing edition stays the default", and it should be stated
   rather than implied by a template line.
3. **Are appendices meant to carry `## In short` at all?** The exemption at `:825` makes it
   optional and the cross-check at `:1097` then mis-grades it. If the answer is "no, an
   appendix never carries one", the cheaper fix is to skip the carried-in record for
   appendices entirely rather than to rank them.

## Verdict

The branch delivers its objective and the backward-compatibility guarantee holds under
execution, which is the part I most expected to find cracks in. The blocker is narrow and
mechanical: one branch in `emit_slide` keyed on the wrong variable, which turns a documented
check into a silent no-op for the authoring form the skill recommends. That is a correctness
defect this PR introduced, in a codebase whose own comments name "a checker that reports OK
without having run" as its worst failure mode, and it is roughly a four-line fix plus a
fixture slide.

VERDICT: REQUEST_CHANGES

Fix `emit_slide`'s legibility branch and give the slide fixture a slide that fails the floor;
fix the appendix carried-in rank; decide what the step-4 template should say about `edition`
and `slide_figures`.
