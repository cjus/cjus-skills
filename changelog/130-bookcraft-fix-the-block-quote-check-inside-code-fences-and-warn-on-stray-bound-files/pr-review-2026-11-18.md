# PR review: bookcraft: fix the block-quote check inside code fences and warn on stray bound files

Issue: https://github.com/cjus/cjus-skills/issues/130
Reviewed: uncommitted working tree against `main`, plus the plan folder. First review on this branch; no prior `pr-review-*.md` exists.

### Summary

The PR fixes two defects found while building a trial book. Under the narration profile, `check-book.sh` no longer reads a `> ` line inside a fenced block as a block quote. `/makebook` now warns when it binds an unnumbered markdown file in a folder whose other chapters are numbered. The new `book_model.strays` holds that rule, and the fixtures and both SKILL.md files cover it. Both objectives in `PLAN.md` are delivered and nothing regresses.

### Verification performed

- `plugins/bookcraft/scripts/test-fixtures.sh`: 21 passed, 0 failed.
- `main`'s `check-book.sh` run against the branch's `fixtures/fence` fails with `fence-fixture-02-...: body carries a block quote`. The branch's `check-book.sh` passes the same folder. So the fixture is a real regression guard and not just decoration.
- `guide-under-narration` still fails both chapters with "body carries a block quote". Real block quotes outside fences are still caught.
- A real bind of a copy of `fixtures/fence` with a `BRIEF.md` added printed `warning: BRIEF.md: carries no chapter number while the other chapters do, so it was bound as Chapter 1; add it to book.json "exclude" if it is not a chapter`.
- I probed `strays` directly with uppercase names, single-digit names, folders holding appendices and unnumbered-only folders. It never reports an appendix, it returns nothing for a plain notes folder, and it returns nothing when `labels` is declared.
- I swept the diff and the plan folder for em dashes, attribution trailers, the banned cross-project terms and `org/repo#N`-shaped backlinks. None found.

### What is working well

- **The fence fix follows the house pattern exactly.** The new awk uses `/^[[:space:]]*```/ { infence = !infence; next }`, the same toggle used at about a dozen other sites in `check-book.sh`, including the guide branch directly above it. A reader who knows one fence-aware sweep can read this one too, and a later change to fence detection will find every site with one grep.
- **The outside-a-fence behavior is unchanged.** The new check still requires `> ` with a space, like the old `grep -E '^\s*> '`, and it trades GNU-only `\s` for the portable `[[:space:]]`. Nothing that failed before passes now unless it sits inside a fence.
- **The comment explains the consequence, not just the mechanics.** It records that the false positive pushed a chapter agent to make the chapter worse in order to pass. That is exactly the "why" the next maintainer needs before they tighten this back up.
- **`strays` sits in the shared model, not inside the binder.** Every checker reads `book_model`, so `check-book.sh` or `/revisebook` can reuse the rule later and the definition stays in one place. Its docstring names the two exemptions (plain notes folder, `labels`) and gives the reason for each.
- **The exemptions are well chosen.** With no numbered file there is no convention to break. An unnumbered introduction is the documented use of `labels`. Both prevent the flood of warnings that the comment above `claimed` already warns about.
- **The fixture cases are the right four.** A stray, an excluded file, `labels` and a plain folder each map to a branch in `strays`. The stray case also puts an appendix alongside to show appendices are never counted.
- The version bump (1.17.0 to 1.17.1) and the SKILL.md wording fit a patch-level fix.

#### Suggestions

🟢 **The stray message says "carries no chapter number" for names that do carry one**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:4117-4122`, `plugins/bookcraft/scripts/book_model.py:348-351`

**What I see:**
`strays` keys on `name_number is None`, and `CHAPTER_OPENING` needs a lowercase slug and two or more digits. So `bk-1-one.md` and `Bk-03-Intro.md` both count as strays. For them the warning reads `bk-1-one.md: carries no chapter number while the other chapters do`.

**The risk:**
Low. Warning on these files is an improvement: before this PR their malformed name was suppressed, because they are not in `claimed`. But the text is wrong for them, and an author looking at `bk-1-one.md` may decide the warning is a binder bug and ignore it.

**Suggested fix:**
Word it in terms of the pattern rather than the presence of a digit, for example:

```python
f'{f["name"]}: does not follow the numbered chapter pattern the other '
f'chapters follow, so it was bound as {f["label"]}; add it to '
f'book.json "exclude" if it is not a chapter'
```

This also matches the ticket's own phrasing ("does not follow the chapter filename pattern its neighbours follow").

**Learning note:**
A message should describe the rule the code actually tests. When the predicate is "the regex did not match", saying "has no number" is a paraphrase that holds for the common case and misleads in the edge cases.

🟢 **The stray warning prints after the position warnings it causes**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:4113-4122`

**What I see:**
In the real bind, `BRIEF.md` sorts before the lowercase chapter names. Its position shifts every numbered chapter's position, so two "is chapter N but sits at position N+1" warnings print first and the stray warning, which is the root cause, prints last.

**The risk:**
The author reads the symptoms before the cause. Nothing is wrong, but it is noise in front of the one line that tells them what to do.

**Suggested fix:**
Build the stray list first and prepend it (`name_warnings = stray_warnings + name_warnings`). Optionally, when any stray is present, drop the position warnings for files that would sit correctly if the strays were removed. The prepend alone is enough.

**Learning note:**
When one warning can explain several others, put it first. Readers act on the first actionable line.

---

🟢 **The binder's warning line has no fixture assertion**

📍 Location: `plugins/bookcraft/skills/makebook/fixtures/bind/run.sh`

**What I see:**
`fixtures/book-model` covers `strays` itself. The binder's use of it (the list comprehension and its `f["label"]` lookup) was verified only by the manual bind recorded in `CHANGELOG.md`.

**The risk:**
Small. The integration is five lines over a key that `classify` always sets. A later refactor of `name_warnings` could still drop it silently.

**Suggested fix:**
In the bind fixture, add an unnumbered `BRIEF.md` to a copied folder and grep the binder's stdout for `warning: BRIEF.md: ` plus `"exclude"`.

**Learning note:**
Unit-test the rule and integration-test that someone calls it. These are two different failure modes.
