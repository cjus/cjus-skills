## PR review: [#135] bookcraft: fix the makebook/bind fixture failing intermittently on macOS CI

PR #136, branch `feature/135-bookcraft-fix-the-makebook-bind-fixture-failing-intermittently-on-macos-ci`, one commit (27d10f7) ahead of `main`. Reviewed: the committed diff plus the working-tree `PLAN.md` change and the untracked `pr-summary-2026-11-19.md`. First review of this branch; there is no earlier `pr-review-*.md` in the plan folder.

### Summary

The macOS `makebook/bind` flake was not pagination drift. Chromium 159 writes "fi" into the PDF text layer as two letters on one render and as U+FB01 on the next. That made the binder's clean-render check in `build-book.py` see a changed page, so it fell back to the probed PDF, whose page 2 opens on the `ZQTOCSTARTQZ` probe, and both fixture failure forms follow from that. The fix is a single line: `flat()` now NFKC-normalizes each page before it strips whitespace and probes. That matches what `bare()` already does for index terms.

### What is working well

- **The diagnosis is excellent.** The author compared 18 job logs on runner image, Playwright/Chromium and poppler versions and found the one variable that tracks pass/fail. They then reproduced the failure locally by matching the CI Chromium, and confirmed all six failing binds differed *only* by `fi` against U+FB01. That is root cause, not symptom-chasing.
- **The fix is in the right layer.** Making the fixture more tolerant would have left the false fallback shipping `ZQ...QZ` markers in real users' books, where a screen reader reads them aloud. Pinning Chromium would have hidden the fragility. Fixing the comparison removes it. The PLAN allowed either route, and the reasoning for this one is written down.
- **The change is minimal and consistent with the file.** `unicodedata` is already imported (`build-book.py:56`), and the same normalization is already used in `bare()` (`build-book.py:2999-3000`). The order is correct: normalize, then collapse whitespace, then strip probes. NFKC leaves the ASCII `ZQ([A-Z0-9]+)QZ` probes untouched, and I checked that `flat("proﬁles ZQCH01QZ") == flat("profiles")` holds.
- **The comment explains why.** It records the measurement (6 in 40, 2026-11-19, the guide fixture) and why NFKC cannot mask a real reflow: a reflow moves words between pages, while a ligature only respells one. The next reader will not "simplify" it away.
- **The evidence is real.** Locally: 6/40 failures went to 0/40, and 15/15 fixture runs passed. In CI, five consecutive attempts of `fixtures (macos-latest)` passed on Chromium 159 (run 44557860724). The summary is also honest that five clean runs alone is only about a 1-in-4 chance event at the old rate, and that the 40-bind local result is the stronger evidence.

#### Important

🟡 **No bookcraft version bump, so the user-facing half of the fix will not reach installs**

📍 Location: `plugins/bookcraft/.claude-plugin/plugin.json:5` (still `1.20.0`)

**What I see:**
The PR changes runtime behavior in `plugins/bookcraft/skills/makebook/scripts/build-book.py` but leaves the plugin at `1.20.0`. Every recent bookcraft PR that touched plugin code also moved the version: #131 (a fix, `1.17.1`), #132, #133, #134 (`1.20.0`) and #103. Those squash messages record it ("the plugin moves to 1.17.1", "the plugin version, 1.20.0").

**The risk:**
The CI half of the objective does not depend on this, which is why it does not block. But the PR's own case for fixing the binder instead of the fixture is that "the same false fallback ships markers in users' books too". Plugins install to a version-scoped path (README "Releasing" and line 46), so a release tag needs a raised `version` before installs pick anything up. Without the bump, the fix reaches CI but never the users it was justified by. It also breaks a pattern the repo has kept on every comparable change.

**Suggested fix:**
Raise `plugins/bookcraft/.claude-plugin/plugin.json` to `1.20.1` in this PR, and mention it in the CHANGELOG entry and the COMMITMSG the close will write ("the plugin moves to 1.20.1"). If makebook's `SKILL.md` or a NOTES file carries a version log, add a one-line entry there in the same style as #131.

**Learning note:**
A behavior fix is only as good as its delivery path. In a repo where releases are keyed to a manifest version, "merged" and "shipped" are different states. The patch bump is what turns the first into the second.

#### Suggestions

🟢 **The regression guard for `flat()` is probabilistic and tied to one Chromium version**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:4309-4311`

**What I see:**
The only test that would catch a revert is the existing `makebook/bind` fixture. It fails about one run in four, and only on a Chromium that emits the ligature nondeterministically. The summary says so plainly ("No fixture was added").

**The risk:**
When Playwright moves past 159, the fixture may stop exercising this path entirely, and a future edit to `flat()` (say, someone reordering normalization after `PROBE_RE.sub`) could regress unnoticed.

**Suggested fix:**
Optional, and only if cheap: lift `flat` to module level (it closes over nothing but `PROBE_RE`) and add a two-line assertion to an existing makebook fixture's `run.sh`, along the lines of `python3 -c 'from build_book_helpers import flat; assert flat("proﬁles ZQCH01QZ") == flat("profiles")'`. Use whatever import route the fixtures already use. If that extraction feels like more surface than this PR wants, leaving it is reasonable. It is coverage for logic this PR added, so it is in scope, but not required.

**Learning note:**
A test that only fails when an outside dependency misbehaves at random is a smoke alarm with a flaky battery. A deterministic input that pins the exact case you fixed survives the dependency moving on.
