# PR review: Fix cleanup's close-check pathspec overmatching ticket numbers

Reviewed 2026-09-23 against `main` (b27bc4b, one commit ahead). Draft PR #26, ticket
[#25 — Fix cleanup's close-check pathspec overmatching ticket numbers](https://github.com/cjus/cjus-skills/issues/25).
This is the first review of this branch. No earlier `pr-review-*.md` exists in this folder, so
nothing here re-raises a settled finding. The two items in `PLAN.md § Deferred` about
`abort`/`sync` and `gh pr view --repo` are treated as settled and not raised again.

## Summary

`/pr:cleanup` step 1 now reads the one plan folder the resolved branch names,
`<changelogRoot>/<slug>/`, instead of globbing on the ticket number. Step 0 now resolves the
workspace from the branch name, using `git for-each-ref … | grep -iE` with a segment-start
anchor, instead of from a substring of the worktree path. It also excludes the main checkout and
sets `WORKTREE_PATH`, `BRANCH` and `SLUG`. `Bash(grep:*)` is added to allowed-tools and `pr` goes
from 0.2.3 to 0.2.4.

The objective is delivered: another ticket's artifacts can no longer satisfy the close check.
One PR-introduced regression needs a decision before merge. Step 0's pattern no longer finds any
workspace in a repo whose `branchPrefix` does not end in `/`.

## What is working well

- **The fix removes the bug class instead of patching one instance of it.** An exact-slug read
  leaves no glob near the ticket number. It also makes step 1 agree with how `/pr:start` names
  the folder (`start/SKILL.md:24`) and how the state script finds it
  (`pr-lifecycle-state.mjs:159-161, 206`). Three components now share one rule instead of
  keeping a parallel approximation of it.
- **The issue's suggested fix was rejected on evidence, not taste.** Case H shows that the
  anchored forms never reach `changelog/abc-6-…/`. That is exactly the check a suggested fix
  should get before anyone adopts it.
- **Step 0 was caught as the same bug.** Without that, the step 1 fix would have verified the
  wrong workspace's record correctly. Case K is a good find as well: a worktree root whose own
  name carries digits matched every workspace under it.
- **`[^/[:space:]]` is a careful detail.** It stops the segment group from crossing the tab into
  the worktree-path field, so a path can never satisfy the pattern that is meant for the branch
  name.
- **The main-checkout exclusion is the right addition.** Once matching moved to branch names,
  a branch checked out in the main checkout became matchable. Without the exclusion, step 5
  would have been handed the main working tree.
- **I verified the repro instead of trusting it.** The pattern in `repro.sh` is byte-identical
  to `SKILL.md:40`, and all 16 assertions pass. I also ran step 0 against this repo: ticket 25
  resolves this worktree only, and 2, 5, 6 and 1 return nothing. The step 1 pathspec for
  `6-fixture-health-for-createbook-s-checker` returns only that folder's three files, where the
  old glob also returned the `16-…` and `26-…` `COMMITMSG.md`. That is the reported bug,
  reproduced on real data.
- **The shell grep and BSD grep behave the same.** In this environment's zsh, `grep` is a shell
  function that runs **ugrep** with `-G`, so the skill runs under ugrep and not the BSD grep that
  `repro.sh` used under bash. The later `-E` overrides `-G`, and both tools gave identical rows
  for every case I tried. I did not run GNU grep, but the pattern uses only POSIX ERE (a bracket
  expression with a class, grouping, `*`, `?`).
- **The incident wording is honest.** The counterfactuals are hedged ("Had ticket 6's folder
  lacked…", "it would resolve…"). The one unhedged claim, that `/pr:cleanup 6` matched 16 and 26,
  is what issue #25 reports as observed, and it still reproduces in this repo today.

## Issues found

### Critical

None.

### Important

🟡 **Step 0 no longer finds any workspace when `branchPrefix` does not end in `/`**

📍 Location: `plugins/pr/skills/cleanup/SKILL.md:39-45`

**What I see:**

```bash
git for-each-ref --format='%(refname:short)%09%(worktreepath)' refs/heads \
  | grep -iE '^([^/[:space:]]+/)*(<ticketPrefix>-)?<ticket>-'
```

The pattern only lets the ticket start a `/`-delimited segment. `branchPrefix` is a free string:
the schema (`pr-config.schema.json:20-24`) sets no constraint, and `config.md:62` says it is
"Prepended to every branch name". `ticket/SKILL.md:67` builds the branch as
`<branchPrefix><ticketPrefix-><number>-<slug>` by plain concatenation. So with
`branchPrefix: "feature-"` the branch is `feature-6-fix-x`, which has no segment that starts with
`6-`.

**The risk:**

I checked this in a scratch repo. With `feature-6-dash` and `feature-16-dash` worktrees:

- On main, step 0 found `…/feature-6-dash`, along with the 16 decoy, which is the original bug.
- On this branch, the pattern returns nothing for it, so `/pr:cleanup 6` reports "no workspace
  found for ticket 6" and stops.

Cleanup stops working in every repo configured that way. The failure is safe: nothing gets
deleted. But it is a regression against something this PR was meant to preserve. `PLAN.md`
rejected the issue's anchored forms because they "miss every folder in a repo that sets
`ticketPrefix`". That same standard applies to a repo that sets a dash-terminated
`branchPrefix`. The rest of the plugin handles such a repo: the state script slices the prefix,
`config.md:131` includes `(?:<branchPrefix>)?`, and abort's `branch --list "<prefix><ticket>-*"`
matches it.

**Suggested fix:** add the optional prefix group that `config.md:131` already uses. Take the
opportunity to switch to `lstrip=2` as well (see the first suggestion below):

```bash
git for-each-ref --format='%(refname:lstrip=2)%09%(worktreepath)' refs/heads \
  | grep -iE '^(<branchPrefix>)?([^/[:space:]]+/)*(<ticketPrefix>-)?<ticket>-'
```

> Drop each optional group whose config value is empty, and escape any regex metacharacter in
> `branchPrefix`.

With the default `feature/`, the new group adds nothing, because `([^/]+/)*` already consumes
`feature/`. I re-ran all 16 of `repro.sh`'s assertions with this pattern and `lstrip=2`, and all
passed. With `(feature-)?`, BSD grep and ugrep both find `feature-6-a`, `feature-abc-6-e` and
`feature-owner/6-f`, and both reject `feature-16-b`, `feature-66-c`, `feature-6x-d` and
`feature-14-phases-6-9`. Add `feature-6-…` to the list in the prose at `:45`.

If you would rather declare that `branchPrefix` must end in `/`, that is also a valid outcome.
In that case, say so in `config.md:62` and the schema description, so the constraint is written
down somewhere other than a regex in one skill.

**Learning note:** an anchor built from what the default config produces fixes the default
config. When a pattern stands in for a configurable value, test it against each shape the
config allows, not only the one in the examples. The plan applied this test to `ticketPrefix`.
It did not apply it to `branchPrefix`.

### Suggestions

🟢 **Use `%(refname:lstrip=2)` instead of `%(refname:short)`**

📍 `SKILL.md:39`

`:short` produces the shortest *unambiguous* name. I checked this: when a tag
`feature/6x-thing` exists, it prints `heads/feature/6x-thing`. That row still matches, but
"branch minus `branchPrefix`" then leaves `heads/feature/…` as `SLUG`. Step 1 would report "never
ran" on a correctly closed ticket. That is the safe direction, but it is exactly the "cried wolf"
false positive the incident reference warns about. `lstrip=2` always strips exactly
`refs/heads/`. The change costs one token and is included in the fix above.

🟢 **"Multiple rows" does not say which rows can be chosen**

📍 `SKILL.md:49-50`

The first bullet separates rows checked out in a worktree of their own from rows that are not.
The second bullet asks about every row. Consider a worktrees-on repo with a live
`feature/6-a` worktree and a stale `feature/owner/6-b` that is checked out nowhere. Both rows
are listed. If the operator picks the stale one, `WORKTREE_PATH` is empty in a mode where step 0
would otherwise have stopped. The main branch never offered that choice, because its multiple
matches were always worktree paths. Suggested wording:

> **Multiple rows** → list them and ask, then apply the bullet above to the row chosen.

Separately, the parenthetical at `:47` ("when worktrees are off and the branch is checked out
there") also applies when worktrees are on and someone checked the branch out in the main
checkout. The "Neither is a workspace" rule already covers that case, so it only needs "or".

🟢 **Step 3 still re-assigns `BRANCH` after step 0 now sets it**

📍 `SKILL.md:52` and `SKILL.md:96`

Step 1 now keys on step 0's `SLUG`, while steps 4 and 6 key on step 3's
`BRANCH=$(git -C "$WORKTREE_PATH" rev-parse --abbrev-ref HEAD)`. For a linked worktree the two
are identical by construction, since `%(worktreepath)` is where that ref is HEAD. So the step 0
change does not break step 3 in any path this PR is responsible for. The two can only diverge
when `WORKTREE_PATH` is empty, which is the Deferred item below. Making step 3 a check instead of
an assignment would make the invariant explicit and would close the worst half of that item for
free:

```bash
[ "$(git -C "$WORKTREE_PATH" rev-parse --abbrev-ref HEAD)" = "$BRANCH" ] \
  || { echo "workspace HEAD is not $BRANCH; stopping"; exit 1; }
```

This is optional here.

🟢 **Two small wording overreaches** (these answer the incident-wording question)

- `SKILL.md:263`: "The loose glob that fixed it caused the next incident". The next entry
  records an overmatch whose verdict happened to be correct, not a failure that fired. "led to
  the overmatch below" says exactly what happened. The new entry at `:265` is itself accurately
  hedged and needs no change.
- `CHANGELOG.md:61-62`: "so they check the skill's text rather than a copy of it". The script
  holds a verbatim *copy* of the pattern template, and the pathspecs are hand-substituted
  (`changelog/$2/…`). "copied verbatim from the edited `SKILL.md`" is accurate. The claim that
  matters, that the tested text equals the shipped text, holds: I diffed the two.

### ⏭️ Deferred to follow-up

These do not affect the verdict.

- **Cleanup's worktrees-off path acts on the session's checkout, not the resolved branch.** This
  applies to `cleanup/SKILL.md:96` and steps 6 and 8, and it widens `PLAN.md § Deferred` item 3,
  which names only step 1. When the branch is checked out nowhere, step 3 re-derives `BRANCH`
  from `git -C ""`, so steps 4 and 6 check and offer to delete whatever branch the session is on.
  When the branch is checked out in the main checkout, step 6's `git branch -D` refuses a
  checked-out branch and step 8 pulls into the feature branch. This predates the PR and is not
  worsened by it. theme: cleanup worktrees-off path. Clears the TICKET bar:
  - *Symptom:* in a worktrees-off repo, `/pr:cleanup N` run from a checkout on another branch
    prints that branch as the target and gates its deletion on that branch's PR.
  - *Occasion:* the fix for Deferred item 3. It is the same code and the same fix.

Considered and dropped, so no entry is needed:

- A worktree with a detached HEAD no longer appears in the rows, so it gets "no workspace
  found". That fails safe, and step 6 needs a branch anyway.
- The grep exits 1 on no rows. The prose already covers "no rows".
- An owner segment shaped like `6-team/` would match ticket 6. This is contrived.

## Questions

1. **Was the incident repo's owner segment in the branch name, or only in the folder?** Step 1
   is now correct if the branch was `feature/<owner>/6-…`. If the folder was
   `changelog/<owner>/6-…` under a flat `feature/6-…` branch, step 1 now asks on every close
   there, whereas the old glob found it. That layout is not one `/pr:start` produces, and the
   state script would miss those plans too, so I am not raising it as a finding. But the
   rationale for the segment-start anchor rests on that incident, so it is worth confirming.
2. **Is a `branchPrefix` without a trailing `/` meant to be supported?** The answer decides the
   Important item: either add the prefix group, or document the constraint.

## Verdict

VERDICT: NEEDS_DISCUSSION

In a repo whose `branchPrefix` does not end in `/` (the schema allows it, and
`ticket/SKILL.md:67` builds branches that way), `/pr:cleanup N` resolved the workspace on main and
now reports "no workspace found" and stops. Either add `(<branchPrefix>)?` to the step 0 pattern,
which is a one-group change that I verified keeps every existing case passing, or document that
`branchPrefix` must end in `/`. After that, this is an APPROVE.
