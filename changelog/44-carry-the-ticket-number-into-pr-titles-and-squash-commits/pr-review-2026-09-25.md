## PR review: [#44] Carry the ticket number into PR titles and squash commits

Ticket: `44-carry-the-ticket-number-into-pr-titles-and-squash-commits` · PR #45 (draft) · base `main` · 1 commit (`5ac3774`)

### Summary

The pr plugin now prefixes PR titles with the ticket ID (`[#32] <title>`, or `[ABC-32] <title>` with `ticketPrefix` set), so a squash merge lands with both numbers in its subject. `/pr:pre-test` prefixes on create. `/pr:close` gains step 4b, which corrects an existing title and folds a title assertion into the step-4 verification query that 8b re-runs. `/pr:init` gains a squash-title check that asks before PATCHing the setting. The lifecycle `pr` line now names both numbers. `ticketing.md` and `config.md` document the rules, and acceptance phase 8 covers the new `pr` line with a stub `gh`.

First review of this branch. No earlier `pr-review-*.md` exists in the plan folder.

### What is working well

- **The rule lives in one place.** The title shape sits beside the slug rule in `config.md`, and `pre-test`, `close` and `init` all point at it instead of restating it. That placement is what stops two skills drifting to two formats.
- **The title check reuses the existing verification query.** Step 4b adds a third element to the query that already asks GitHub what it resolved, so the title is checked against what will merge, not against the string just written. 8b re-runs it after step 7. This is the same "ask the system, not the text" discipline the closing-reference check already follows.
- **The title read has the same fail-closed guard as the body read.** `TITLE=$(…) && [ -n "$TITLE" ]` stops on a failed read, so a network error cannot become a title of `[#44] ` followed by nothing.
- **The operator's wording is kept.** Prepend rather than replace, and `[WIP]` is named explicitly as operator-owned. A model would otherwise very plausibly "normalize" such a title to the issue title.
- **Init step 6 is careful with a repo-wide setting.** It asks first, says plainly that the change is to GitHub rather than a file, reports the read-back value rather than the value sent, and treats a non-admin token as a reportable outcome rather than a failed run. I ran the read against `cjus/cjus-skills`, and it returns `true\tPR_TITLE\tCOMMIT_MESSAGES` as expected.
- **`prLink` takes "closes" only from `closingIssuesReferences`**, never from a string match on the body, which matches how `hasCloses` already works.
- **Acceptance phase 8 is hermetic.** It uses a stub `gh` first on `PATH`. The quoted heredoc means `FAKE_CLOSES` is read when the stub runs, not when it is written, and `GIT_SSH_COMMAND=false` makes the fetch fail fast. The temp directory is removed afterwards.
- **The "PR #41, never bare #41" rule is applied to this PR's own report rows.** Rows 6b and 8b now say `issue #<n>`.

🟡 **1. "Ticket ID" means two different things, and the rule in `config.md` contradicts its own example**

📍 Location: `plugins/pr/reference/config.md:L116`, `L130`, `L132`; `plugins/pr/skills/close/SKILL.md:L48`; `plugins/pr/skills/pre-test/SKILL.md:L48`

**What I see:**
`config.md` defines the unprefixed ticket ID as `123` (L116). Its new rule then reads:

```
- **A title counts as prefixed only when it starts with exactly `[<ticket ID>] `.**
```

Taken literally, that is `[123] `. Four lines earlier, though, the example title is `[#123] Fix the blank render`. `close/SKILL.md:L48` resolves the tension by redefining the term locally: `$ID` is "the ticket ID as the PR title writes it … `#32` with no prefix". `pre-test/SKILL.md:L48` writes `--title "[<ticket ID>] …"` and relies on the prose on L52 to say `[#32]`.

**The risk:**
A model that follows the cross-reference into `config.md` and applies the rule as written can produce `[123] Fix the blank render`. That title then compounds with 🟡 2: step 4b does not treat `[123]` as ticket-shaped, so it falls through to "Anything else" and prepends, giving `[#123] [123] Fix the blank render`. That title passes verification and lands on `main`. The examples make this unlikely, but this PR's stated aim is "so every skill derives it one way", and the one canonical sentence gives the wrong answer for the default configuration.

**Suggested fix:**
Name the bracketed token once, in `config.md`, and use that name everywhere:

```markdown
- Ticket ID `123`
- Title tag `#123`            <!-- new line -->
…
- Ticket ID `ABC-123`
- Title tag `ABC-123`         <!-- new line -->

**The PR title is the title tag in square brackets, one space, then the title.** The title tag is the
ticket ID, with `#` in front when it is a bare number …

- **A title counts as prefixed only when it starts with exactly `[<title tag>] `** — `[#123] ` or `[ABC-123] `.
```

Then change `close/SKILL.md:L48` to "Derive the title tag … Step 4 and step 4b use it as `$ID`", and the `pre-test` snippet to `[<title tag>]`.

**Learning note:**
When a reference exists so that "every skill derives it one way", its defining sentence has to be literally correct, because a model will apply it literally. If a term needs a local redefinition in a caller, the reference is missing a term.

🟡 **2. Step 4b's rules leave a gap that produces a doubled prefix, and the verification accepts it**

📍 Location: `plugins/pr/skills/close/SKILL.md:L264-L273`

**What I see:**
The table has three rows: exact `[$ID] ` (leave it), "a **different** ID of the same shape" (replace), and "Anything else" (prepend). Two cases fall through to the prepend row:

- **The same ID, malformed.** `[#44]Carry` or `[#44]: Carry` is not an exact match, and it is not a *different* ID. The result is `[#44] [#44]Carry`.
- **`[#N]` in a prefixed repo.** The row reads "`[#<digits>] `, or `[<PREFIX>-<digits>] ` with a prefix configured". That parses two ways: either `[#N]` is always ticket-shaped, or it is only the shape when no prefix is set. The second reading turns `[#12] Carry` into `[ABC-32] [#12] Carry`. A repo that adds `ticketPrefix` after using the plugin would hit this on every open PR.

The verification is `startswith("[$ID] ")`, which is **true** for `[#44] [#44]Carry`. I confirmed this with jq. So the doubled prefix is reported green and lands in the squash subject.

**The risk:**
The squash subject on `main` reads `[#44] [#44]Carry the ticket… (#45)`. The ticket is still carried, so this is not a regression against the objective. But it is a new-logic edge case that the verification cannot catch, and the edit placeholder `<title without any old prefix>` (L270) leaves the model to improvise the parse.

**Suggested fix:**
Replace the three prose rows with one rule: strip a leading ticket-shaped token, whether same ID or different, with any trailing spaces or colon, then prepend `[$ID] `. Making the rule deterministic removes the interpretation entirely. I tested this form with jq 1.8. It is idempotent, and it leaves `[WIP]` and foreign tags such as `[XYZ-9]` in place:

```bash
# $PREFIX is ticketPrefix uppercased, or empty
NEW_TITLE=$(jq -rn --arg t "$TITLE" --arg id "$ID" --arg p "$PREFIX" '
  ("^\\[(#[0-9]+" + (if $p == "" then "" else "|" + $p + "-[0-9]+" end) + ")\\][ :]*") as $re
  | "[\($id)] " + ($t | sub($re; ""; "i"))')
[ "$NEW_TITLE" = "$TITLE" ] || gh pr edit "$BRANCH" --repo "$REPO" --title "$NEW_TITLE"
```

| In | Out (`ID=#44`) |
|---|---|
| `[#44] Carry` | unchanged |
| `[#44]Carry` / `[#44]: Carry` | `[#44] Carry` |
| `[#4] Carry` | `[#44] Carry` (report the old token) |
| `[WIP] Carry` | `[#44] [WIP] Carry` |
| `[#12] Carry`, prefix `ABC`, `ID=ABC-32` | `[ABC-32] Carry` |

If you prefer to keep the prose table, at least make the replace row read "a leading `[#<digits>]`, or `[<PREFIX>-<digits>]` when a prefix is configured, **whether or not it matches `$ID`**, followed by any spaces or a colon", and make the verification reject a second leading tag: `(.title | startswith("[$ID] ") and (ltrimstr("[$ID] ") | startswith("[$ID]") | not))`.

**Learning note:**
A prose decision table with an "anything else" fallthrough is only as good as its row boundaries. Where the rule is really a string transform, give the model the transform. And check that the assertion distinguishes the good result from the plausible bad one, which here it does not.

🟡 **3. The `pr` line drops its missing-ticket warning when the PR closes some other issue**

📍 Location: `plugins/pr/scripts/pr-lifecycle-state.mjs:L632-L637`; `plugins/pr/scripts/test-acceptance.sh:L204-L226`

**What I see:**

```js
const prLink = (p) =>
  p.closesIssues?.length > 0
    ? ` → closes ${p.closesIssues.map((n) => `#${n}`).join(", ")}`
    : ticketNumber
      ? ` → no closing ref to #${ticketNumber}`
      : "";
```

"No closing ref" is keyed on the list being **empty**, not on `hasCloses`. I reproduced both states with the stub `gh` on branch `feature/42-add-a-widget`:

```
closes=[{"number":99}]  draft  →  pr       PR #57 → closes #99, OPEN (draft), …
closes=[]               draft  →  pr       PR #57 → no closing ref to #42, OPEN (draft), …
```

**Answer to the brief's question:** the line does not *mislabel* the PR, because `closes #99` is exactly what GitHub resolved. But in the case where a reader most needs the relationship spelled out, it stays silent that ticket #42 is not closed. For a **draft**, nothing else says so either: the `pr-missing-closes` gap only fires for ready PRs, and the close step's `closing ref to #42 absent` evidence only appears once `COMMITMSG.md` exists. This is not a regression, since `main` printed no closing information at all. It is an unhandled case in logic this PR added, and phase 8 does not cover it or the no-ticket branch.

**Suggested fix:**
Key the warning on `hasCloses` so both facts can appear together:

```js
const prLink = (p) => {
  const closes = p.closesIssues?.length > 0
    ? ` → closes ${p.closesIssues.map((n) => `#${n}`).join(", ")}`
    : "";
  const missing = p.hasCloses === false
    ? `${closes ? "," : " →"} no closing ref to #${ticketNumber}`
    : "";
  return closes + missing;
};
```

That yields `PR #57 → closes #99, no closing ref to #42`. The two existing phase-8 strings are unchanged. Add a third stub case:

```bash
OUT=$(FAKE_CLOSES='[{"number":99}]' PATH="$FAKE:$PATH" GIT_SSH_COMMAND=false node "$S" --text)
chk "a PR closing another issue still names the missing ref" "closes #99, no closing ref to #42" "$OUT"
```

**Learning note:**
When the code already computes a precise boolean (`hasCloses`), derive the display from that boolean rather than from a coarser proxy (`length > 0`). The proxy and the fact agree on the tested cases and disagree on the one that matters.

🟢 **4. `$CURRENT_MESSAGE` is never assigned, and the stated reason for sending it is backwards**

📍 Location: `plugins/pr/skills/init/SKILL.md:L128`, `L140-L146`

The read prints a TSV line but assigns nothing, so the PATCH's `$CURRENT_MESSAGE` has no source in the snippet. Shell state also does not persist between tool calls. If it is empty, GitHub rejects the value with a 422, so the failure is loud but not covered by the 403/404 guidance. Read the message on its own, with the same guard pattern as the title and body reads:

```bash
CURRENT_MESSAGE=$(gh api "repos/$REPO" --jq .squash_merge_commit_message) && [ -n "$CURRENT_MESSAGE" ] \
  && gh api -X PATCH "repos/$REPO" -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message="$CURRENT_MESSAGE"
```

Avoid `read -r A B C <<< "$(… @tsv)"`: tab is IFS whitespace, so an empty middle field shifts the rest left.

The docs require the **title** when the **message** is sent, not the reverse, so "GitHub requires the title whenever the message is sent" does not explain why the message is sent. The approach itself is sound, and the operator's live PATCH confirmed it. Suggested wording: "Send the current message back with it, unchanged, so the call pins the pair and changes only the title."
