### Important

#### 🟡 1. "Three of the four" is still the wrong count, and "only the two file paths survived intact" is also false

📍 Location: `changelog/…/pr-summary-2026-09-20.md:64`, `changelog/…/CHANGELOG.md:13,19`,
and the commit message body of `8749cbc`

**What I see** (summary, `:64`; the CHANGELOG and commit message say the same thing):

> The ticket's own line-number citations had drifted — three of the four. The catalog was
> at `README.md:87` not `:88`, the `code-reviewer` line at `:137` not `:149`, and the
> `/pr:init` sentence at `:69` not `:71`, where line 71 is inside a code fence. **Only the
> two file paths survived intact.**

**The risk:**

I read issue #27's body directly (`gh issue view 27`) rather than `PLAN.md`'s reproduction
of it. It carries exactly **five** anchors:

| Anchor | Kind | State |
|---|---|---|
| `README.md:88` | line | drifted (87) |
| `README.md:149` | line | drifted (137) |
| `README.md:71` | line | drifted (69) |
| `plugins/pr/hooks/README.md` | path | **intact** |
| `plugins/bookcraft/plugin.json` | path | **does not exist** |

Two separate errors follow.

**First, the denominator.** There are three line-number citations, not four, and *all
three* drifted. "Three of the four" asserts a fourth line number that stayed correct, and
there is no fourth. Under the only other available reading — four *items*, one anchor each
— the count is two, since items 1 and 3 cite no line at all. No reading makes "three of the
four" true, and pairing it with "the two file paths" implies a five-anchor set being
described as four in the same sentence.

**Second, the survivors.** `plugins/bookcraft/plugin.json` does not exist and never did on
this branch's history: `ls` fails, and `git show main:plugins/bookcraft/plugin.json` returns
`fatal: path … does not exist in 'main'`. The real manifest is
`plugins/bookcraft/.claude-plugin/plugin.json`, which is the path the branch's own
`## Releasing` rewrite correctly uses. So **one** anchor survived intact, not two.

This is the third consecutive draft of this one paragraph to miscount, and it now sits in
the PR body, where the reader most likely to check it is the reader who opens issue #27 in
the next tab. The paragraph's own thesis — that a documentation ticket whose citations rot
is the argument for anchoring on text — is undercut by the sentence that carries it, which
is exactly the objection review 1 raised about the previous draft.

**Suggested fix:**

> The ticket's own anchors had rotted: of its five, one survived. All three line numbers
> had moved — the catalog to `README.md:87` from `:88`, the `code-reviewer` line to `:137`
> from `:149`, and the `/pr:init` sentence to `:69` from `:71`, where line 71 is now the
> opening of a code fence. Of the two file paths, `plugins/pr/hooks/README.md` was right
> and `plugins/bookcraft/plugin.json` was already wrong: the manifest lives at
> `plugins/bookcraft/.claude-plugin/plugin.json`, which is the path this branch's
> `## Releasing` rewrite uses. Edits were anchored on text rather than offsets.

Apply it in all three places. The commit message needs an amend and a force-push, which
this branch has already done once, so the cost is known.

**Learning note:**

The first draft got a fact wrong; this draft gets the *arithmetic over the facts* wrong,
which is the failure mode that survives fact-checking. Every individual anchor in the
sentence is now correct — it is the summary statistic over them that is not, and summary
statistics are the part reviewers skim because the details underneath them check out. When
a sentence contains both a count and a list, derive the count *from* the list as the last
step, and make the list exhaustive first: here, enumerating all five anchors before
counting would have made both errors impossible.

#### 🟡 2. The summary contradicts itself on how many defects the review gate caught, and drops one of them from the record

📍 Location: `changelog/…/pr-summary-2026-09-20.md:9` vs `:66-69`

**What I see:**

`:9` — "The review gate then re-derived all of it independently and caught **two** defects
this branch had introduced in its own prose, both fixed here."

`:66` — "**Two defects** were introduced by this branch and caught before merge, **one in
self-review and one at the review gate**", followed by a two-item list: the "in all three
commands" wording (Phase 6) and the changelog anchor count (review gate).

**The risk:**

These cannot both be right. `:9` credits the review gate with two; `:66` credits it with
one. The enumerated list at `:67-69` then omits the `/pr:continuity-prune` confirmation
clause entirely, even though it is one of the two things review 1 raised and one of the two
fixes in this commit — the commit message records it correctly at its final paragraph, so
the PR body is the only artifact that loses it.

The reconciliation is simple: three items were raised against this branch's own prose. Self-
review caught one, the review gate caught two, one of which it filed as a 🟢 suggestion
rather than a defect. Whichever framing you prefer, the two sentences need to agree, and
the list needs to hold everything it claims to count.

**Suggested fix:**

At `:66`, restore the third item and align the attribution:

> **Three items were raised against this branch's own prose and all three are fixed here**,
> one in self-review and two at the review gate:
>
> 1. The first draft of the generalized `## Releasing` said to substitute the plugin name
>    "in all three commands" when only two of the three contain `<plugin>`. Caught in Phase 6.
> 2. The changelog's account of which ticket anchors had drifted was wrong. Caught at the
>    review gate.
> 3. The `/pr:continuity-prune` catalog line omitted that it lists the candidates and waits
>    for confirmation before deleting. Caught at the review gate.

Then make `:9` agree — "caught two further defects" reads correctly once the list is three.

**Learning note:**

A count stated in an overview and a list given later are the same claim written twice, and
they drift apart whenever one is edited alone. The overview is written first and revised
last, which is why it is usually the one left stale. If a number appears in a summary, make
the enumeration the source of truth and reread the summary line whenever the list changes.

📍 Location: `changelog/…/pr-summary-2026-09-20.md:26-33` and `:48-52`

**What I see:** the first block shows the removed line as

```diff
-`plugins/bookcraft/.claude-plugin/plugin.json` carries the version, and it is the source of truth.
```

but the actual line on `main` continues "… To cut a release, raise `version` there, commit,
then:". The two `+` lines are one line in the file, so the change reads as a 1→2 line
expansion when it is 1→1. The third block's `-` line is likewise a mid-sentence fragment of
`README.md:69`.

**The risk:** nothing substantive — the semantics are faithful and the excerpts are clearly
illustrative. But a ```` ```diff ```` fence reads as a literal hunk, and on a branch whose
product is citation fidelity it is the one place a skeptical reader will diff against the
real thing. The middle block (`agents/code-reviewer.md`) *is* byte-exact, which makes the
other two look accidental rather than deliberate.

**Suggested fix:** add `…` to the truncated lines, or a half-sentence before the first
block: "abridged to the clauses that changed". Either removes the ambiguity.

**Learning note:** formatting carries a claim of its own. A diff fence promises literal
text, a blockquote promises a quotation, a table promises exhaustiveness. Where the content
is an excerpt, mark it, or use a form that does not promise more than you are delivering.
