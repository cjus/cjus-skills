## What is working well

- **Phase 1 went beyond reproducing the bug.** It checked whether `gh pr edit --repo` failed
  the same way, and found that it does not. The argument-less form falls back to the checkout,
  so the old `:212` pipeline turned a failed read into a silent body replacement that the
  `:239` length check could not catch. That finding explains why the outer `gh pr edit` also
  gets `"$BRANCH"`, even though it was not strictly failing.
- **The fix copies an existing pattern.** `gh pr view "$BRANCH" --repo "$REPO"` is already the
  form used at `abort/SKILL.md:109` and `cleanup/SKILL.md:114`. It uses the same `$BRANCH` as
  close step 4's own `gh pr list --head` and `gh pr create --head`. Nothing new to learn and
  nothing to drift.
- **Resume step 1 now names its inputs** ("Take the branch, repo and default branch from
  that."), in the same form as close's Context section. Before this, step 6 used `$REPO` and
  step 5 used `$DEFAULT_BRANCH` without saying where either came from. The lifecycle `--text`
  output provides all three: a `branch` line, a `repo` line, and the default branch in the
  `commits` line (`git.defaultBranch` in `--json`).
- **The no-PR case is handled in both skills.** Once the argument is present, gh's failure
  changes from a usage error to "no pull requests found for branch". Each note says what that
  means for its step: report it in resume, fall back to the local check in close 1b. A model
  running the skill will not mistake the expected pre-PR state for a fault.
- **Both notes say *why*, not only *what*.** They quote the exact gh error, so a later editor
  who removes the argument will recognize the failure they cause.

### Suggestions

🟢 **The close note says "every" call passes the branch, but one mention in the skill does not**

📍 Location: `plugins/pr/skills/close/SKILL.md:72`, contradicted at `:393`

**What I see:**

```
**Every `gh pr view` and `gh pr edit` in this skill passes the branch.**
```

while `:393` still reads "Do not surface cleanup until `gh pr view --json state` actually
reports `MERGED`."

**The risk:** Low. `:393` is reference prose, has no `--repo`, and would work from the
worktree. But this PR adds an absolute claim that the same file then breaks. A later editor
grepping to check the rule finds an exception and has to work out whether it is intentional.
Rules that are almost true stop being trusted.

**Suggested fix:** either narrow the claim so it is true:

```
**Every `gh pr view` and `gh pr edit` command in this skill passes the branch.**
```

or align `:393` with it by writing `` `gh pr view "$BRANCH" --json state` ``. That also matches
the `gh pr view <branch> --json state` wording at `cleanup/SKILL.md:20`.

**Learning note:** A universal rule written in documentation acts as a test: readers check the
file against it. Scope it to what you actually changed, or make the file obey it everywhere.

🟢 **The step 1b note combines a skill-wide rule with a step-local outcome**

📍 Location: `plugins/pr/skills/close/SKILL.md:72-75`

**What I see:** the note sits between the `:69` command and the bullets that interpret its
output. Its first three sentences state a rule for the whole skill. Its last two ("'No pull
requests found for branch' here means no PR exists yet. Use the local check.") are really a
third outcome of `:69`, next to `CONFLICTING` and `UNKNOWN`. The wording is **consistent** with
the rest of the step: "Prefer GitHub's own verdict where a PR exists" plus the "Local fallback"
section already imply that no PR means the local check. But "Use the local check" comes one
sentence after "falls back to the checkout", and those read alike on a skim.

**The risk:** Readability only. A model reading step 4 in isolation will not see a rule that
lives inside step 1b. A reader of step 1b gets the outcome cases split across a paragraph and a
list.

**Suggested fix:** move the rule to the Context section, next to where `$BRANCH` is
established, and make the no-PR case a bullet:

```markdown
## Context
...
Take the branch, slug, repo, default branch, ticket number and plan folder from that. ...

**Every `gh pr view` and `gh pr edit` command in this skill passes the branch.** With `--repo`,
`gh pr view` refuses to infer the PR ("argument required when using the --repo flag"), while
`gh pr edit` silently falls back to the checkout.
```

```markdown
- `mergeable: "CONFLICTING"`, or `mergeStateStatus: "DIRTY"` → **stop.** ...
- `mergeable: "UNKNOWN"` → GitHub is still computing. Fall back to the local check.
- "no pull requests found for branch" → no PR exists yet. Fall back to the local check.
```

**Learning note:** Put a rule where its scope begins. A skill-wide rule belongs with the
skill's context. A result of one command belongs with that command's other results.
