## PR review: [#104] add a generic remote-build plugin

### Summary

Reviewed implementation checkpoint `2e82a97` against `main` for the objective in
`104-add-a-generic-remote-build-plugin/PLAN.md`, corresponding to
https://github.com/cjus/cjus-skills/issues/104 and PR https://github.com/cjus/cjus-skills/pull/105.
The shared CLI, thin skills, bounded offline tests and explicit infrastructure responsibilities
follow the repository conventions. Two newly introduced behaviors need repair before the
safe-snapshot and initial Rust workflow goals are met.

### What is working well

- Launch intent is saved before mutation, and ambiguous outcomes reconcile without creating a
  second instance. Teardown checks the account, token, tags and recorded instance identity.
- Uploads use saved source fingerprints; jobs and outputs remain associated with that source.
- SSH host verification remains strict. Cloud janitor declarations are clearly distinguished
  from actual independent cleanup, and no live-cloud testing is claimed.
- The 20 existing offline tests pass, including the fake AWS/SSH CLI round trip. Review added
  two independent local probes described below; neither contacted cloud services.
- Repository configuration disables continuity and assertions, and no local AGENTS.md or
  CLAUDE.md was present in this checkout. Manifest/catalog changes match the existing format.

### Issues found

#### Critical

**Prevent symlink replacement between source validation and reading.**

Location: `plugins/remote-build/scripts/remote_build.py`, `snapshot`, the `is_symlink`/`stat`
checks followed by `p.read_bytes()`.

What I see: path validation and file opening are separate operations. `read_bytes()` follows
symlinks even though the earlier check rejects them.

The risk: a concurrent source writer can replace an eligible file or an ancestor directory
with a symlink after validation. The archive then contains data outside the selected project,
violating the explicit safe-source boundary. This is introduced by this PR, not a preexisting
issue. The manifest's original path and later content hash do not prove that the bytes came
from the intended directory.

Evidence: an offline fixture created an ordinary source file and a same-length outside-project
file with synthetic innocuous content. Replacing the source file with a symlink immediately
before `Path.read_bytes` caused `snapshot` to succeed with the outside file's SHA-256. The
existing symlink test only covers a link already present before validation.

Suggested fix: open the root directory once and traverse components relative to directory
file descriptors with no-follow semantics; open the final file without following links,
validate its file descriptor using `fstat`, and read that descriptor. Refuse a raced or changed
entry rather than retrying it through an unrestricted path. Add regression cases for both a
final-component replacement and a parent-directory replacement.

Learning note: a safety check on a pathname must apply to the same filesystem object that
is subsequently read. Checking first and reopening later leaves that identity unbound.

#### Important

**Preserve a preinstalled rustup toolchain while isolating each job's writable home.**

Location: `plugins/remote-build/scripts/worker.py`, `execute`, construction of `env`.

What I see: the worker replaces HOME and CARGO_HOME and discards RUSTUP_HOME. Cargo/rustc
shim paths inherited through PATH therefore resolve toolchains against the empty job home.

The risk: ordinary preprovisioned Rust images using rustup fail before the requested build,
even when the toolchain is already installed. README currently documents a special direct-
executable image restriction, but the parent has confirmed standard rustup-image support as
part of the authorized initial Rust workflow fix. This is new behavior in this plugin.

Evidence: a synthetic installed rustup directory, an explicit RUSTUP_HOME, and a local command
that resolves rustup's directory were passed to `execute`. The same command returned exit 7
under the worker because the provisioned context was discarded. No actual rustup installation
or dependency download was performed.

Suggested fix: preserve only the trusted worker's preprovisioned toolchain location or resolve
actual toolchain executables before applying the isolated job environment. Do not broadly
inherit credentials or copy the caller's Cargo configuration. Test the default rustup location
and an explicit RUSTUP_HOME offline. Document which directory is immutable/toolchain-only and
which directories are job-writable.

Learning note: toolchain discovery and writable build caches are separate concerns; isolating
one should not accidentally discard the other.

#### Suggestions

Per-job Cargo directories prevent concurrent writes but currently provide no warm cache reuse
between iterations. The README describes fresh per-job directories, so this is not concealed;
keep retention versus reuse explicit if session-cache support changes. Do not share a mutable
target directory across concurrent jobs merely to improve cache hits.

#### Deferred to follow-up

None. Retained EBS caches, other providers, MCP and binary download remain the documented v1
scope decisions; this review does not expand them into new tickets.

### Questions

None requiring user input. Both findings have local, offline-testable fixes within the
existing plugin objective.

### Verdict

VERDICT: REQUEST_CHANGES

The introduced check-then-open race can include outside-project data in an approved source
snapshot. Repair it and the confirmed Rust-image compatibility issue, then review the delta.
