## PR review: makebook: give the PDF a navigable outline, so a Kindle Scribe shows an expandable table of contents

Second close review, 2026-10-03, against `main`. This is a delta review. The first review,

Its Important finding and its "no automated failure-path test" suggestion were resolved in

### Summary

`17283a1` does two things. First, `build_outline` now receives the settled page map, and a
top-level entry counts only if its `/Dest` opens the page the binder found that page or
chapter on. A body `h1` that shares the next chapter's title is therefore filed as a section,
not taken as the chapter. Second, the index's page numbers become links after rendering.
`link_pages` reads `pdftotext -raw -bbox` from the index onward, matches words in order
against the index's page references, and lays a `/Link` with an explicit `/XYZ` destination
over each one. The index HTML stays identical to `main`, so its layout can't move.

The operator's amended objective is delivered, including item 7 (the index links), and
nothing regresses `main`.

### What is working well

- **The first review's fix is the right one, built the right way.** The page comes from
  `state`, the settled map that the final render was verified to match page for page. Any
  render that doesn't match is replaced by the probed render, which is what `state`
  describes. So the expectation and the PDF being checked can't drift apart. Chapter `num`s
  are unique across chapters and appendices (`"num": len(chapters) + 1`), so
  `settled["pages"].get(ch["num"])` can't confuse Appendix 1 with Chapter 1.
- **The fixture reproduces the exact misfile from the first review**: chapter 1 ends with
  chapter 2's title as an `h1`, and `outline_is` asserts it lands under chapter 1. That
  also guards the permissive `page is None` fallback. If Chromium ever switched to named
  destinations, `opens()` would return `None`, the check would quietly fall back to text,
  and this fixture would fail. So the fallback can't regress without anyone noticing.
- **The error message is now actionable**: "the first missing is 'Two' opening page 4",
  plus each top-level entry paired with the page it opens. Someone debugging a failed bind
  sees both pieces of evidence at once.
- **The refusal test calls the binder's own `render()` and `build_outline`**, without
  mocking either. The two exit paths a real book can't reach, no outline at all and a
  chapter short, are now asserted against their messages. That closes the first review's
  gap cheaply.
- **Laying links onto the finished PDF, rather than into the HTML, is a disciplined call.**
  Plan Phase 17 records that the inline-anchor version measured 0.14px wider per
  seven-number entry and wrapped a number in a full-length book. Dropping a version that
  worked because it broke the "nothing moves" promise is the right instinct. Reading
  `-raw` order, because `-layout` reading order interleaves the two columns, is also
  correct and is explained where it matters.
- **The index check is strong on the main path.** `page-links.py` crops `pdftotext` to
  each link's rectangle and requires the number printed under it to equal the page it
  opens. `links_open` then holds the link count to the bind's own count of page references.
  Together they catch both mutants the plan lists: no links, and links a page early.
- **`attach_scripts` is safe alongside the new links by construction.** An index link
  carries a `/Dest` and no `/A`, so `uri` is `""` and the loop skips it (around
  `build-book.py:2963`).
- **`--no-index` and an empty index are handled.** `entries` defaults to `[]`, and
  `link_pages` returns before running `pdftotext` at all.

#### Important

🟡 **A bare number in an index term that equals the entry's first page takes that page's link**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py`, the word loop in
`link_pages` (`for x0, y0, x1, y1, word in BBOX_WORD_RE.findall(words)`), and the matching
claim in `SKILL.md`, The linked contents ("A number inside a term is passed over").

**What I see:**

```python
for x0, y0, x1, y1, word in BBOX_WORD_RE.findall(words):
    if made == len(wanted):
        break
    if float(y0) > h - FOOTER_BAND_PT or word.rstrip(",") != str(wanted[made]):
        continue
    ...
    made += 1
```

A word is linked as soon as it equals the next page reference. The term's own words come
first in the stream and go through the same test. So a term word is skipped only when its
number differs from the page the entry prints first.

**The risk:** I reproduced this with the binder's `render()` and `link_pages`. The index
was the entry `Top 2 lists  2, 3` followed by `Zeta  3`. `pdftotext -raw -bbox` gives the
words `Top`, `2`, `lists`, `2,`, `3`. The link meant for page 2 went onto the term's `2`
(x0 77.7), and the printed `2,` (x0 109.1) got no link. Nothing caught it:

- `link_pages` found all 3 of 3, so its "not found" check passed.
- `page-links.py` reported `ok … Index: 3 links, 0 opening a page other than the one
  printed under them`, because the digit under the stray link really is 2.
- The count in `links_open` matched.

The matcher then falls back into step, so this never fails a bind. The cost is one dead
page number per affected entry, plus a tap target inside the term, which still opens the
right page. It is rare: the term must contain a bare number, as in "Python 3" or "Top 10",
equal to its own first page. But `SKILL.md` and the docstring both claim the opposite, and
the bind prints "each a link". This is new code, so it is in scope. It doesn't regress
`main`, which had no index links, so it doesn't block.

**Suggested fix:** consume each entry's term before matching its numbers. `link_pages`
already has the terms, because `entries` is `(display, pages)`. Walk the entries in order,
and for each one skip words until the term has been read, comparing as `build_outline`'s
`key()` does (whitespace removed). Only then match its `len(pages)` numbers:

```python
for display, pgs in entries:
    term = re.sub(r"\s+", "", display)
    seen = ""
    while seen != term:          # read the term's words, which are never links
        seen += next_word().text  # next_word() walks pages and skips the footer band
    for p in pgs:
        w = next_word()
        if w.text.rstrip(",") != str(p):
            raise RuntimeError(...)  # strict: the next word must be this number
        add_link(w, p)
```

Unescape `&amp;` and the other entities before comparing. Before relying on the
whitespace-removed comparison, check whether index terms can hyphenate at a column wrap.
This also makes the matcher strict rather than greedy, so a misplaced link fails the bind
instead of drifting back into step. A case in `fixtures/bind/run.sh` would pin it down: an
index term with a bare number equal to its first page. If harvesting makes that awkward to
arrange in the guide fixture, a probe in the style of the refusal test, calling
`link_pages` directly, would do. If you'd rather not change the matcher now, the minimum is
to correct the `SKILL.md` sentence and the docstring so they don't promise what the code
doesn't do.

**Learning note:** a greedy in-order matcher that "re-syncs" is self-healing, and that is
exactly why its mistakes are invisible. If the input has structure (term, then numbers),
parse the structure, and make every deviation an error. Then the count check means
something.

#### Suggestions

🟢 **`FOOTER_BAND_PT` restates `render()`'s bottom margin as a second literal**

📍 Location: `build-book.py`, `FOOTER_BAND_PT = 0.95 * 72`, and `margin={"bottom": "0.95in"}`
in `render()`.

The comment ties them together, but the code doesn't. Change the margin and the two drift
apart. A smaller margin fails the bind loudly ("not found"), but a larger one lets the
footer's title words, which can contain numbers, into the matcher. A single `PAGE_MARGIN_IN`
constant, or `BOTTOM_MARGIN_IN`, used by both would remove the coupling.

before, and passed. Raises RuntimeError when an expected entry is missing: a short". It's
