## PR review: makebook: give the PDF a navigable outline, so a Kindle Scribe shows an expandable table of contents

Fourth close review, 2026-10-03, against `main`. This is a delta review of `eeb7026`
(`git diff f7ba3da..eeb7026`). The first three reviews (`pr-review-2026-10-03.md`, `-2.md`
and `-3.md`) are settled, and this review doesn't raise their findings again. That
includes everything parked under `PLAN.md`'s `## Deferred` and the third review's DROP note
on the unbounded scan.

### Summary

`eeb7026` applies the third review's fix as proposed. `link_pages` no longer anchors an
index entry's numbers on its term's last whitespace token. It now finds the exact printed
run (`2,` `3`) first. Then it rebuilds the stripped text of the words before the run, back
to the cursor `at`, until that text is at least as long as the stripped term, and requires
it to end with the whole term. `bare()` gains an NFKC step. The "not found" message no
longer doubles its commas. A new `fixtures/bind/run.sh` check renders "large language model
pre-training" at 17pt through the real `build_css()` and `build_index()`. It asserts that
the term wraps at its hyphen, that the entry gets 4 links, and that `link_pages` refuses an
entry whose numbers never printed.

**The binder change is correct, and I found no way for it to fail or mis-anchor where the
last-word anchor didn't.** The issue is in the new fixture. Its wrap precondition depends on
font metrics, and on the Linux CI runner the term doesn't wrap. So the advisory Linux
fixtures leg goes from green (on `main` and at `f7ba3da`) to red, and it would stay red on
every run after merge.

### What is working well

- **The fix is a faithful, minimal application of the proposal.** The diff in
  `build-book.py` matches the third review's snippet line for line. The docstring and the
  `SKILL.md` sentence were updated to say "whole term" and to explain why: a line can break
  after a hyphen. Nothing else in the binder moved.
- **The whole-term anchor is strictly safer than the last-word one.** I worked through the
  cases where it could accept a run the old one rejected. The tail is bounded below by `at`,
  so it only ever holds the current entry's own words, plus a letter heading (or the lead
  paragraph for the first entry). A candidate run inside the term is preceded by a proper
  prefix of the term. That prefix can't end with the whole term, and a letter heading
  prepended to it can't make it do so either, because a heading letter is only alphabetic
  when the term starts with a letter. The bound also closes the third review's "4 by 4"
  DROP. With the cursor right after a "Week 4" entry, the term's leading `4` sits at `at`,
  the tail loop never runs, and `"".endswith("4by4")` is false.
- **Its tolerance sits in the right place.** Stripping to letters and digits absorbs every
  way line breaking can disagree with the source: removed spaces, a split after a hyphen,
  a slash or a dash, and any `hyphens: auto` hyphen. It doesn't absorb any change to the
  letters themselves. I rendered eight entries at 11.8pt and 17pt through the real
  stylesheet: "4 by 4" `[4]`, "C++ & Q", an NFD-decomposed "café crème", "ﬁle ﬁnder" written
  with ligature code points, a 50-character multi-hyphen term, "Week 4", the fixture's
  hyphenated term, and "Python 3" `[3, 5]`. All 14 links were made, each over a printed page
  number, at both sizes.
- **The regression test has teeth.** I ran the committed probe's input against
  `f7ba3da`'s binder. It raises exactly the error the third review reported, so the new
  check does fail the last-word matcher, as the commit claims.
- **Asserting the wrap before the links is the right instinct.** Without it, a probe that
  stopped wrapping would pass without testing anything. That is why the Linux failure below
  is loud instead of silent. The problem is only how the precondition is produced.

#### Important

🟡 **The new hyphen-wrap check fails on Linux fonts, turning the advisory Linux fixtures leg red**

📍 Location: `plugins/bookcraft/skills/makebook/fixtures/bind/run.sh:307-345` (the `hyphen=`
probe and its `report`).

**What I see:**

The probe renders one entry, `("large language model pre-training", [2, 3, 4, 5])`, and
needs `pre-` and `training` to print as separate words:

```python
print("wraps" if "pre-" in text and "training" in text else f"does not wrap: {text[-8:]}")
```

Whether that one string wraps at its hyphen depends on the exact advance widths of the
index font. In PR #63's CI run for `eeb7026` (run 37146907650), the `fixtures
(ubuntu-latest)` job fails with:

```
FAIL  link_pages should link a term that wraps at its hyphen, and refuse numbers that never printed
      | does not wrap: ['model', 'pre-training', '2,', '3,', '4,', '5', 'T', '1']
      | links=4
      | unprinted: the page numbers of 'Never printed' (2, 3) were not found after its term
passed 17   failed 1   skipped 0
```

The binder behaves correctly on Linux: 4 links, and the refusal raises. Only the
precondition fails.

**The risk:**

The Linux leg passed on `main` (run 36764042344) and at `f7ba3da` (run 37144751427). This
commit is what turns it red. `fixtures.yml` explains what that means: the leg is advisory,
so the workflow run still concludes `success`, but "the job and its check run both report
`failure` ... Anything reading check runs, including the pr plugin's close gate, will see
it and should." After merge, every push to `main` and every later PR would carry a red
Linux check. That red would come from a font difference the workflow already calls the
likelier cause, not from a binder regression. That is the noise the advisory leg's comment
warns about, and it teaches readers to ignore the leg.

The suite's local result of 18/0/0 is the macOS result. On Linux it's 17/1/0.

**Suggested fix:** make the wrap independent of the font. Slide the hyphen across the line
end, so that for any reasonable metrics at least one entry breaks there, and assert at
least one wrap plus every link. I tested this on macOS at 11.8pt, 14pt and 17pt, and it
made 16 of 16 links each time, with 1, 1 and 2 hyphen wraps. Each step is one word "model"
(about 3em at the index's size), which is narrower than the window in which the hyphen is
the last break that fits (about the width of "training"). So a sweep of 8 steps can't jump
over the window on any font with ordinary proportions.

```python
entries = [(" ".join(["model"] * n) + " pre-training", [2, 3]) for n in range(1, 9)]
filler = "".join(f"<section style='break-before: page'><p>Page {n}.</p></section>"
                 for n in (2, 3))
# ... build_css(binder.MAX_BODY_PT), build_index(entries), render() as now ...
words = subprocess.run([...pdftotext -raw page 1...]).stdout.split()
wraps = sum(1 for a, b in zip(words, words[1:]) if a == "pre-" and b == "training")
print("wraps" if wraps else f"does not wrap: {words[-12:]}")
print(f"links={binder.link_pages(pdf, entries, 1)}")   # expect 16
# refusal as now, appended to `entries`
```

Then assert `links=16` in place of `links=4`. Keep the "wraps" line first, so a sweep that
somehow stops wrapping still fails instead of passing vacuously. If you'd rather keep the
single realistic term, the alternative is to make that check's precondition report `skip`
on Linux. But `--strict` fails a skip, so the sweep is the simpler fix.

**Learning note:** a regression test that depends on line breaking has two jobs. It has to
produce the layout it needs, and it has to prove it did. This probe does the second job well
and the first by luck of one font's metrics. A sweep that slides the break point across the
line produces the layout with any metrics, which is the property a cross-platform fixture
needs.

📍 Location: `fixtures/bind/run.sh:330-334`

The committed refusal case, `("Never printed", [2, 3])`, raises because the run `2,` `3`

This is cheap and optional.
