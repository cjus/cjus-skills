## PR review: makebook: give the PDF a navigable outline, so a Kindle Scribe shows an expandable table of contents

Reviewed 2026-10-03 against `main`, commits `9fb320f` and `d485edf`, plus the uncommitted
status refresh to `PLAN.md`. This is the first review on the branch. No earlier
`pr-review-*.md` exists, so there are no settled findings to honor.

### Summary

The branch turns on Chromium's outline (`outline=True, tagged=True`). It promotes every page
title and chapter title from `h2` to `h1` so the outline nests by chapter. Then
`build_outline()` relinks Chromium's own outline entries in place with pypdf. That step
limits the depth to sections, labels chapters `Chapter N:` and `Appendix N:`, nests them
under parts, retitles entries that lost a space at a wrap, and fails the bind when an
expected entry is missing. A second commit adds prefixed ids to every page and figure and
lays an empty anchor over each contents and list-of-figures row, so every row links to its
page without moving anything.

The objective in `PLAN.md`, including the operator's 2026-10-03 amendment, is delivered.
Nothing regresses `main`.

### What is working well

- **Relinking rather than rebuilding the outline** is the right call, and the comments say
  why. Each entry keeps Chromium's explicit `/Dest`, which I confirmed is a page reference
  plus `/XYZ`, and its `/SE` back into the structure tree. The `/Count` arithmetic is
  correct: the root counts the top-level entries plus the children of open parts, an open
  part counts its chapters, a collapsed chapter carries the negative of its section count,
  and a leaf carries no `/Count`.
- **Matching with whitespace removed and casefolded, then retitling from the page's HTML**
  fixes the joined-words bug at its source. I bound a book whose titles hold `&`, `<…>`,
  curly quotes and an em dash, and every entry came through correctly escaped and matched.
- **The empty-anchor overlay** is a careful answer to a layout trap that is easy to miss.
  The `.toc-group:first-of-type` analysis in PLAN Phase 11 is exactly the kind of reasoning
  that keeps a "nothing moves" promise honest. An absolutely positioned child of a flex
  container takes no part in flex layout, and `position: relative` with no offsets moves
  nothing.
- **The ids are prefixed** (`mb-ch-N`, `mb-fig-NNN`), so raw HTML in a chapter cannot hijack
  a link.
- **The tests check real behavior.** `outline_is` compares the whole tree, including the
  collapsed and expanded markers. `contents-links.py` compares the printed numbers with the
  pages the links open. It runs again after `attach_scripts`, the other step that rewrites
  annotations. The plan records the mutation runs (no retitle, no pruning, no `tagged`, no
  links, links one chapter off), which is how you find out whether a test can fail at all.
  I re-ran `fixtures/bind/run.sh` (16/16 ok) and `fixtures/save-scripts/run.sh` (10/10 ok).
- **The measurement is honest.** The +50% file size and +1 to 2 s per bind are measured,
  recorded and documented rather than glossed over.
- **The outline matches the rest of the book.** `build_outline` groups chapters with
  `group_for` and the same `grp != current` rule as `build_toc`, so parts that aren't
  contiguous repeat in the outline exactly as they do on the contents page. I checked this.
- **The repo audit is clean.** No banned cross-project terms, and no cross-repo links, in any
  file the branch touches, the uncommitted changelog artifacts included.

#### Important

🟡 **A body H1 that shares the next entry's title takes that entry's place, and the bind passes**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:3071-3086` (the
`for ref in tops` match loop in `build_outline`)

**What I see:**

```python
for ref in tops:
    if (len(found) < len(expected)
            and key(title_of(ref)) == key(expected[len(found)][0])):
        found.append((expected[len(found)][1], ref, children(ref)))
    elif found:
        found[-1][2].append(ref)
```

Entries are matched on text and order alone.

**The risk:** I reproduced this. In a copy of the guide fixture, I ended chapter 1 with
`# What the Checker Reads`, which is chapter 2's title. The bind exited 0 with no warning,
and the outline came out like this:

```
- Chapter 2: What the Checker Reads  [p8]     <- page 8 is inside chapter 1
      What the Checker Reads  [p9]            <- the real chapter 2 title, now a "section"
```

Chapter 2's real sections were also dropped, because they became grandchildren. The
contents page correctly says 9. The same thing happens when a body H1 reads `Glossary` or
`Index` next to that back matter. It is rare, since chapters are written in `##` sections.
But this is the one failure the new check exists to stop: the docstring says "a short outline
sends the reader to the wrong chapter", and this one sends the reader there silently. It
does not regress `main`, which had no outline at all, so it doesn't block.

**Suggested fix:** the binder already knows where every page landed, so check the
destination as well as the text. Pass the settled page map into `build_outline` and require
a matched chapter entry's `/Dest` to open that chapter's page:

```python
page_of = {p.indirect_reference.idnum: i + 1 for i, p in enumerate(writer.pages)}

def opens(ref) -> int | None:
    dest = ref.get_object().get("/Dest")
    return page_of.get(dest[0].idnum) if isinstance(dest, list) else None

# in the match condition, for a chapter:
want = expected[len(found)]
ok = key(title_of(ref)) == key(want[0]) and (
    want[1] is None or opens(ref) == pages[want[1]["num"]])
```

Front and back matter can be checked the same way against `lof_page`, `gloss_page` and
`index_page`. One extra condition turns a silent misfile into either a correct match (the
real heading comes next and matches) or a loud failure. A fixture line covers it: append the
next chapter's title as an H1 to chapter 1 in the second bind, which already appends a stray
H1 to chapter 2.

**Learning note:** when you validate output against an expectation, use the strongest
identity you have. The text is a proxy, and the page is the fact the binder has already
verified. Matching on a proxy will sooner or later match the wrong thing.

#### Suggestions

🟢 **Tagging leaves `attach_scripts`' replaced links dangling in the structure tree**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:2912`
(`annots[j] = writer._add_object(...)`)

**What I see:** with `tagged=True`, Chromium gives every link annotation a `/StructParent`
and an `/OBJR` in the structure tree. `attach_scripts` swaps each marker link for a new
`/FileAttachment` object. In the save-scripts book, 7 of the 10 `/OBJR`s now point at an
annotation that no page carries, and none of the 7 attachments carries a `/StructParent`.

**The risk:** low. No viewer was seen to care, and the PDFKit and pdfdetach checks pass. But
the PR presents the structure tree as a screen-reader benefit, and these seven are
inconsistent in it. On `main` there was no tree, so the inconsistency is new, even though
the code that causes it is not.

**Suggested fix:** keep the link's object number. Rewrite the existing annotation dictionary
in place: set `/Subtype /FileAttachment`, drop `/A`, add `/FS`, `/AP`, `/Name` and
`/Contents`. That keeps its `/StructParent` and every `/OBJR` valid.

**Learning note:** once a PDF is tagged, an object's number is part of its identity.
Replacing an object breaks references you can't see.

🟢 **The reading edition adds a "Notes" section under every chapter**

📍 Location: `build-book.py:1022` (`<h2 class="endnotes-title">`) and `SKILL.md`, The outline

I bound the guide fixture as the reading edition. Each chapter's outline ends with `Notes`,
because the endnotes heading is an `h2`. That is arguably right, since it is a real place in
the chapter. But SKILL.md says a chapter expands to "its `##` headings", and the endnotes
heading isn't one. Either say so in SKILL.md, or leave the heading out of the outline if
that wasn't the intent. Whichever you choose, the reading-edition outline is untested.

🟢 **`contents-links.py` checks only the first page of a listing**

📍 Location: `plugins/bookcraft/skills/makebook/fixtures/bind/contents-links.py:45-46`

A page counts only if its first line is the listing's title, so the second page of a long
contents page or list of figures is skipped. That is fine for the fixtures, which fit on one
page, but anyone who reuses the script on a full-length book will get a pass that covered
less than it seems. One sentence in the docstring would do. Tracking "inside listing X until
the next page whose first line is a known title" would be a fuller fix.

🟢 **The failure path has no automated test**

The rule that a short outline fails the bind was mutation-tested by hand, with no `tagged`.
No fixture asserts the exit 1 or its message. The misfile fixture suggested above would add
one cheaply if the fix makes it fail. Otherwise, call `build_outline` on a PDF rendered
without `tagged`.

### Questions

1. **Was the "Notes" section in the reading edition intended?** See the suggestion above.
2. **Should the ticket's GitHub body be scrubbed?** It isn't part of this diff. Issue #62's
   body on GitHub names another repository and branch, a course code, and a file path in
   that repository. `PLAN.md` restates it generically, as the repo's rules require, but the
   issue itself is public, and closing it from this PR will link to it. Consider editing the
   issue body to the plan's generic wording before `/pr:close`.
3. **Should a label inside a title be detected more widely?** The rule matches
   `Chapter 3`/`Appendix 1` at the start of a title. A title like "Appendix A: …" for
   Appendix 1 becomes "Appendix 1: Appendix A: …". That seems acceptable, but say so if
   letter-labeled appendices are expected.
