## PR review: keep copied underscores inline and attach saved scripts to the bound pdf

Branch `feature/52-makebook-code-copied-out-of-the-bound-pdf-will-not-run`, one commit (`f76045f`) against `main`. Ticket: `52-makebook-code-copied-out-of-the-bound-pdf-will-not-run`. No PR is open yet, so CI has not run. This is the first review of the branch.

### Summary

The branch fixes the binder's half of the "copied code will not run" problem. Every code font size is rounded to a quarter pixel, so Chromium writes each code line as one text run and PDFKit keeps `_` inline. The half that cannot be fixed on the page, lost indentation, is routed around: every block the book asks the reader to save is embedded in the PDF as a file, both as a FileAttachment annotation over a printed note and in the document's EmbeddedFiles list. A save instruction the binder cannot tie to a block and a filename is reported as a warning. All three "Done when" items in `PLAN.md` are implemented.

### What is working well

- **The root cause was found rather than guessed.** The plan expected a style rule; bisection showed the trigger is any font size off a quarter pixel. The CSS comment records what was measured and on which engine, and `code_pt()` mirrors the rounding so the fenced-line width warning measures the size that actually prints. I recomputed the thresholds: 79, 67 and 54 at 8.8125, 10.3125 and 12.75pt, unchanged as claimed.
- **Placing the attachment needs no page measurement.** The note's filename links to a reserved `.invalid` URI, Chromium draws the link annotation exactly over it, and `attach_scripts` swaps it for the attachment. The invariant is enforced, not assumed: a missing or leftover marker fails the bind.
- **Detection reads tokens, not text.** A list item's sentence pairs with its own fence, and the `asked` set stops a sentence with no block from taking its neighbour's. `SAVE_OTHER_RE` keeps "save the output as" from attaching the command beside it.
- **Careful PDF handling.** The rewrite goes to a temp file and replaces the original atomically. The name tree is keyed by book order, so two chapters can save the same filename. I bound the fixture book with `main`'s binder and with this branch's and compared them: `/Title`, `/Creator` and `/Producer` survive the pypdf rewrite unchanged.
- **The EPUB is untouched.** It has its own stylesheet, so the `round()` rules never reach an e-reader. `data-script` is stripped, the note is PDF-only, and the fixture asserts both.
- **The fixture tests what the reader sees**, not just the internals: attachments byte for byte, `ast.parse` on every extracted script, PDFKit's own copy on macOS, and a run count that makes the same failure visible on Linux. The summary also records that reverting the rounding makes it fail, which is the check that matters.
- **Honest about what is unverified.** Viewer support is stated as unmeasured in SKILL.md, the summary and the plan, and the author is told to check their readers' viewer.

**Verified locally:** `plugins/bookcraft/scripts/test-fixtures.sh --strict` passes 18 of 18 on macOS.

### Issues found

#### Critical

🔴 **An indented code block beside a save sentence now fails the whole bind**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:1098` (`find_scripts` accepts `code_block`), `:2155-2174` (`SCRIPT_PRE_RE`, `script_notes`), `:2843` (the raise)

**What I see:**
`find_scripts` treats both `fence` and `code_block` tokens as scripts and calls `attrSet("data-script", ...)` on them. But markdown-it renders the two differently. A fence's attributes go on `<code>`, while an indented block's go on `<pre>`:

```html
<pre><code data-script="0" class="language-python">...   <!-- fence -->
<pre data-script="0"><code>...                           <!-- code_block -->
```

`SCRIPT_PRE_RE` only matches the first shape (`<pre><code data-script="(\d+)"...`). So an indented block gets no note and no marker link, `attach_scripts` finds the script unplaced and raises, and `main` returns 1 before `build_epub` runs.

Reproduced with this chapter:

```markdown
# Indented Code

Save the script below as `indented.py`.

    for _ in range(3):
        print("x")
```

- `main`'s binder: exit 0, writes the PDF and the EPUB.
- This branch: exit 1, no EPUB, and
  `error: could not attach the book's scripts to .../cb.pdf: attachment links missing for ['indented.py'], unrecognised for none`

**The risk:**
Indented code blocks are valid CommonMark, and nothing in `/createbook`'s checkers refuses them. A book that bound yesterday now does not bind at all. The error message describes the binder's internals rather than anything the author can change, so the author has no route out except guessing that they should convert the block to a fence. This regresses the default branch, and it sits on the exact path objective item 2 adds.

**Suggested fix:**
Look for the marker on either tag. I applied this to a scratch copy of the binder: the chapter above binds, `pdfdetach` extracts `indented.py` intact with its indent, and `save-scripts/run.sh` still passes 9 of 9.

```python
# markdown-it puts a fence's attributes on <code> and an indented block's on
# <pre>, so the marker is looked for on either tag.
SCRIPT_PRE_RE = re.compile(
    r'<pre(?P<pre>[^>]*)><code(?P<code>[^>]*)>(?P<body>.*?)</code></pre>', re.S)
SCRIPT_NUM_RE = re.compile(r' data-script="(\d+)"')


def script_notes(body_html: str, ch: dict) -> str:
    def one(m: re.Match) -> str:
        k = SCRIPT_NUM_RE.search(m.group("pre") + m.group("code"))
        if not k:
            return m.group(0)
        n = int(k.group(1))
        name = html_mod.escape(ch["scripts"][n]["name"])
        pre = SCRIPT_NUM_RE.sub("", m.group("pre"))
        code = SCRIPT_NUM_RE.sub("", m.group("code"))
        return (f"<pre{pre}><code{code}>{m.group('body')}</code></pre>"
                f'<p class="script-note">...')  # unchanged from here
    return SCRIPT_PRE_RE.sub(one, body_html)
```

An acceptable alternative is to accept only `fence` in `find_scripts` and report a save beside an indented block as a gap ("put it in a fence with `file=NAME`"). Either way, add an indented block to `fixtures/save-scripts/book/` (and to `want` in `run.sh`) so this shape is covered from now on.

**Learning note:**
When one stage talks to another through a serialised form (token attributes, then HTML, then a regex), the contract is the renderer's output for **every** token type the first stage accepts. `find_scripts` explicitly accepts two types but the fixture exercises one. Test each accepted type end to end, or narrow what the first stage accepts.

#### Important

🟡 **An explicit "above" is overridden by "next" or "following" anywhere in the paragraph, so the wrong block is attached silently**

📍 Location: `plugins/bookcraft/skills/makebook/scripts/build-book.py:1142-1147`

**What I see:**

```python
if SAVE_BACK_RE.search(text) and not SAVE_AHEAD_RE.search(text):
    order = [prev]
elif SAVE_AHEAD_RE.search(text) and not SAVE_BACK_RE.search(text):
    order = [nxt]
else:
    order = [nxt, prev]
```

`text` is the whole paragraph. Any "next", "following" or "previous" elsewhere in it cancels the direction the save clause itself states, and the next block wins. Reproduced with ordinary guide phrasing:

```markdown
```python
def f():
    return 1
```

Save the code above as `f.py`. Next, run it:

```bash
python f.py
```
```

This attaches `python f.py` as `f.py`. The Python block gets nothing, and the bind warns about nothing. "Save the code above as `f.py`; the following section explains it." does the same.

**The risk:**
The note under the bash block tells the reader to trust the attachment rather than the page, and the attachment is the wrong file. That is worse than no attachment, because the author gets no warning and the reader is actively pointed at broken content. "Next," as a sentence opener after a save step is common in exactly the guide books this targets.

**Suggested fix:**
Take the direction from the matched save clause first, and fall back to the paragraph only when the clause names none. I checked this on a scratch copy: both examples attach the Python block, and `find_scripts` returns the same scripts and gaps for both fixture chapters as before.

```python
clause = m.group(0)
scope = clause if (SAVE_BACK_RE.search(clause)
                   or SAVE_AHEAD_RE.search(clause)) else text
back, ahead = SAVE_BACK_RE.search(scope), SAVE_AHEAD_RE.search(scope)
if back and not ahead:
    order = [prev]
elif ahead and not back:
    order = [nxt]
else:
    order = [nxt, prev]
```

Add the "Next, run it:" shape to the fixture book.

**Learning note:**
Heuristics over prose should weight evidence by proximity. The word closest to the verb is what the writer meant, and a direction word two sentences away is usually about something else.

🟡 **`requirements.txt` still allows a Playwright whose Chromium cannot parse the new CSS**

📍 Location: `plugins/bookcraft/skills/makebook/requirements.txt:1` (`playwright>=1.40`); `build-book.py:206, 344, 349, 365`

**What I see:**
CSS `round()` first shipped in Chromium 125, and Playwright 1.44 is the first release to bundle Chromium 125. The floor is still 1.40 (Chromium 120). `install.sh` runs `pip install -r` without `--upgrade`, and pip leaves an installed package alone if it already satisfies the specifier. So a venv built at 1.40 to 1.43 keeps its old Chromium even after the `install.sh` rerun that SKILL.md now asks for.

**The risk:**
In that engine every `round()` declaration is invalid at parse time and is dropped. `.chapter pre` then has no `font-size` at all and inherits the body size: 14pt instead of 10.4pt at the default. Fenced lines longer than about 49 characters are cut off, while the width warning still measures against 67. The result is a silent layout regression for that population. I could not bind on an old Chromium to observe it; the outcome follows from how CSS discards unknown functions. The affected population may well be empty today, but the fix is one line, and this release already requires an install rerun.

**Suggested fix:**

```
playwright>=1.44
```

With this floor, pip upgrades an older Playwright on the rerun, and `playwright install chromium` then fetches the matching browser. A fallback declaration before each rounded one would keep old engines at the old sizes, if you want to guard beyond the floor as well: `font-size: ${pre}pt; font-size: round(nearest, ${pre}pt, 0.25px);`

**Learning note:**
Adopting a newer platform feature is a dependency change even when no import changes. Raise the declared floor in the same commit that starts relying on it.

#### Suggestions

🟢 **SKILL.md understates when a sentence reaches back.** `SKILL.md:412` says a sentence after the block counts only "when it says 'above'". The code also reaches back when the sentence names no direction (`order = [nxt, prev]`), which is how the fixture's `later.py` sentence is handled. Tighten either the text or the code so they agree.

🟢 **Use the public `root_object`.** `build-book.py:2857` reads `writer._root_object`, but pypdf 6 exposes `writer.root_object`. That leaves `_add_object`, which has no public equivalent, as the only private API in use, as the summary already notes.

🟢 **Prose-named data files attach code.** "Save the data as `data.csv`" beside a Python block attaches the Python source as `data.csv`. Adding `data` to `SAVE_OTHER_RE`, or comparing the extension with the fence's language, would catch the common cases. This is arguable, because SKILL.md says the detector can be wrong and `file=` is the override.

🟢 **Make the attach error read as a binder fault.** Once the Critical is fixed, `attach_scripts`' `RuntimeError` guards an internal invariant. Phrasing it as one, naming the chapter and asking for a bug report, would stop an author from trying to fix their book.

Dropped as arguable, no action: the same `file=` name used twice in one chapter attaches twice with no warning; a prose-named path such as `src/app.py` is attached as `app.py` while the note prints the full path; the note's text sits in the text layer, so a term like "attachment" could pick up an index reference to a note page.
