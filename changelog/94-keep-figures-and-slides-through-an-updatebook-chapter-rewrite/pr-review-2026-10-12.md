### Summary

An `/updatebook` chapter rewrite now lists the figures and slides the old chapter places before
drafting (rewrite step 3). It hands that list to the chapter agent as a new item 15 in
`/createbook`'s step 5 prompt, which only a rewrite fills (step 4). It then reads the agent's
findings file for drops (step 5), re-checks each kept figure against its new paragraph (step 6),
and diffs what the chapter places at `HEAD` against the new file (step 9). Step 6's report names
each one kept, corrected or dropped. #87's slide exemption is retired, and § Adding prose and
the levels table now say a rewrite keeps the chapter's figures and slides. bookcraft goes from
1.13.0 to 1.14.0.

### Issues found

#### Critical

**1. Step 9 cannot see an inline SVG drawn to the house style, and tells the session that
silence means every figure was kept.**

Location: `plugins/bookcraft/skills/updatebook/SKILL.md:248` and `:252`.

**What I see:**

```bash
placed() { grep -oE '^!\[[^]]*\]\([^)]+\)|<title>[^<]*</title>' | sed -E 's/^!\[[^]]*\]//'; }
```

The `<title>` alternative matches only a bare `<title>`. `makebook/references/diagram-style.md:127`
gives every figure `<title id="xx-t">` as required scaffolding, for `aria-labelledby`. The binder
reads titles with `<title[^>]*>` (`build-book.py:1716`). Tested: a rewrite dropping one
bare-title SVG and one `id`-title SVG printed only the bare one, and with only the `id` one
dropped it prints nothing.

**The risk:**
Step 3 names "each inline SVG, fenced or raw" as a figure the rewrite answers to, and step 9 is
the check the plan names for making a loss visible. When a rewrite drops a house-style inline
figure, step 9 prints nothing. Line 252 then says "**No output means every one was kept.**"
That is a false all-clear on the objective's own clause, and it primes the § 6 report to mark
the figure kept. The PR introduced this. It is not a regression against `main`, which had no
check, but it means the PR does not deliver "a loss without a decision has to be visible before
the run reports" for one of the two figure kinds it names.

**Suggested fix:**
Accept any `<title>` and normalise it, so a changed `id` alone is not a difference:

```bash
placed() { grep -oE '^!\[[^]]*\]\([^)]+\)|<title[^>]*>[^<]*</title>' | sed -E 's/^!\[[^]]*\]//; s/^<title[^>]*>/<title>/'; }
```

Tested together with Important 2's fix. It reports both drops, with a relative or an absolute
path, and prints nothing when the chapter keeps everything. Also update the comment on `:247`
if you want it to say "each inline SVG's title".

**Learning note:**
A check that asserts "no output means safe" has to match the producer's format, not the
simplest example of it. Here the producer's format is written down (`diagram-style.md`), and so
is a parser that already handles it (`build-book.py:1716`). Copying the binder's pattern is the
cheapest way to stay in step with it.

#### Important

**2. Step 9 resolves the chapter against the shell's working directory, so an absolute path, or
a cwd outside the book's repo, empties the old side.**

Location: `plugins/bookcraft/skills/updatebook/SKILL.md:249`.

**What I see:** `git show "HEAD:./$CHAPTER"`. The `./` form is relative to the cwd. Tested with
an absolute `CHAPTER`: `fatal: path '...' does not exist in 'HEAD'`. The old side is then empty,
every kept figure prints as a `>` line, and no `<` line can appear. Agent sessions are told to
use absolute paths, and `$BOOK` is whatever the operator passed, so this is the likely form, not
an edge.

**The risk:** It fails loudly, so it is not silent, and it does not block. But the check cannot
do its job in its most likely invocation, and a session reading "A `>` line is one it gained"
may misread the output before it reads the fatal line.

**Suggested fix:**

```bash
diff <(git -C "$(dirname "$CHAPTER")" show "HEAD:./$(basename "$CHAPTER")" | placed | sort) <(placed <"$CHAPTER" | sort)
```

Tested with a relative path from the repo root and with an absolute path from `/`.

**Learning note:** `git -C <dir>` pins both the repo and the base for `./`. A snippet in a
skill runs from wherever the agent happens to be, so it should not depend on that.

**3. Item 15 tells the agent to copy an inline SVG unchanged, while item 1 tells it to follow a
rule file that forbids inline HTML.**

Location: `plugins/bookcraft/skills/createbook/SKILL.md:497`, against
`createbook/reference/chapter-prose.md:262` (§ Never, **Markdown.**: "no links, footnotes,
horizontal rules or inline HTML").

**What I see:** Item 1 says "follow every rule in both" files. A raw `<svg>` block is inline
HTML. Item 15 hands the agent "an inline SVG's whole block" and says to place it "copied
unchanged". `check-book.sh` does not police inline HTML, so the two instructions meet only in
the agent's reading.

**The risk:** An agent that follows the rule file drops the figure, and names "the rules forbid
inline HTML" as its reason in the findings file. That meets the letter of "dropped by a recorded
decision", but the decision is wrong and comes from the prompt contradicting itself. Converting
to a fenced ```` ```svg ```` block would bind fine, but nothing says that either.

**Suggested fix:** One clause in item 15, after "copied unchanged": "an inline SVG included,
which is the one inline HTML a chapter carries (`reference/chapter-prose.md § Never` governs the
prose, not a figure handed over here)". Widening the rule in `chapter-prose.md` itself would
reach every chapter agent, which is a bigger change than this PR needs.

**Learning note:** A new prompt item has to be read against the rule files the same prompt
already imposes. Two instructions in one prompt that disagree are resolved by whichever the
agent read at more length, which is the failure item 1's own text warns about.

#### Suggestions

**4. Step 5's "an absent file is the all-clear" assumes no earlier findings file sits at that
path.** `updatebook/SKILL.md:239`. `outline-findings/` persists in the book folder
(`check-provenance.sh:1464` expects it there). Step 0 demands a clean folder, so an earlier one
for this chapter is committed.
- If the agent writes nothing, the old file is read as this agent's findings.
- If the agent writes one, the diff shows a file step 10's list (`:253`) does not name.
- A brand-new findings file is untracked. `git diff --stat` never shows it, but the next run's
  step 0 stops on it.

Suggested: in step 5, "a file `git status` shows unchanged is an earlier run's". In step 10,
"and the findings file, where the agent wrote one". Optionally, step 10 can also name
`assertions.json`, which step 1 or step 4 may write. § 5's first check already allows for that,
so this is wording only.

**5. Step 6 on a book with no `diagrams/README.md`.** `updatebook/SKILL.md:240`. "Record a
figure the rewrite dropped in the README" would start a one-row README. That silences the
bind's "figure decisions were never recorded" warning (`build-book.py:4455`) for every figure
the book never recorded. Suggested: "Where the book has no README, do not start one here. Name
the drop in the report, and leave the README to the figure pass."

**6. Two small gaps in step 9's reading.** `updatebook/SKILL.md:252`.
- **No fallback outside git.** Step 0 allows a book outside git (`:52`), and step 9 has no
  route for it. Suggested: "Outside a git repo, compare the new chapter against step 3's list."
- **A changed title reads as a drop.** An inline figure that step 6 corrected, and whose
  `<title>` changed, prints as a `<`/`>` pair. That contradicts "only a slide this run was
  placing should be" a `>` line. Suggested: "...or the new title of an inline figure the
  re-check corrected".

**7. Procedure references in the ten-step list mix "step N" and "§ N".**
`updatebook/SKILL.md:235, 253`.
- Steps 4 and 9 use "§ 3" and "§ 6" for procedure sections.
- Step 1 says "(step 2)" and step 10 says "the checks in step 5", and the list now has its own
  steps 2 and 5.
- The collisions predate the branch, since the seven-step list already had steps 2 and 5. But
  the PR edited step 10 and set the § convention at step 4.

Suggested: "§ 5" at step 10, and "§ 2" at step 1.

**8. Item 15's "and it opens each image to see what it shows" is not under a "Say that".**
`createbook/SKILL.md:497`. A session assembling the prompt may not pass it on. "It" can also
read as the list. Suggested: "Say that the agent opens each image to see what it shows."

None. Considered and dropped, with no entry:

  These add symmetric noise or edge misses to step 9. They are arguable, and a chapter on
  markdown or HTML is unlikely in these books. DROP.
- **`createbook § 5` never says what happens to `outline-findings/` after it is read.** This

### Questions

1. **For the operator, as a line in the PR summary rather than a change.** With the exemption
   retired, a post-recreate placing run (`§ Placing slides`) that finds a chapter needing several
   slide explanations at once will now rewrite that chapter through the chapter agent. On a
   slide-heavy guide book, that could be many of the chapters the recreate has just drafted.
   This is the alternative the operator was offered in #87 and declined only for the drop, so it
   is coherent. But the cost is new, and the operator should see it once.

### Verdict

**The branch delivers most of its objective.** A rewrite now hands the old figures and slides
to the chapter agent, records drops with reasons, and re-checks kept figures. The three sections
agree on what a rewrite does to slides, and retiring the exemption is coherent with the
operator's own #87 reasoning.

**It does not yet deliver the visibility clause for inline figures.** Step 9 is the check that
makes a loss visible, and it prints nothing when a rewrite drops an inline SVG carrying
`diagram-style.md`'s required `<title id=...>`. The same step tells the session that silence
means every figure was kept. That is a correctness defect this PR introduced, against the
objective, and it is a one-line regex fix.
