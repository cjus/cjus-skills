## PR review: [#82] bookcraft: load the book folder once, into one model every tool reads

Reviewed 2026-10-15 against `PLAN.md`'s objective, on PR #96 at `df0db16` (8 commits ahead of `main`).
This is the first review on this branch, so there is no earlier review to build on.

### Summary

The PR adds a stdlib-only `plugins/bookcraft/scripts/book_model.py` that decides what each file in a
book folder is: its kind, number, label, unit, part and title. The binder and all three checkers now
read that one module. `check-book.sh` reads it through `--tsv` and no longer uses `jq`. A new agreement
fixture runs every tool on the same filenames and checks that each classifies them as the model does.
R1 to R10 are settled operator decisions, so this review checks whether the code implements them
correctly and does not reopen them.

### What is working well

- **The `classify`/`read` split is the right seam.** `classify` is pure and works from names alone.
  That lets the `git ls-tree` baseline and the case-insensitive-disk cases in the fixture use the same
  rule as the working tree, with no files on disk.
- **The appendix opening is tried before the chapter opening.** A comment says why
  (`bk-appendix-10-` would otherwise read as chapter 10). The rule uses `[0-9]` rather than `\d`, so it
  stays ASCII, as R9 asks.
- **The binder keeps two numbers apart.** `num` is internal and `label_num`/`label`/`unit` are what
  the reader sees. This fixed two real EPUB bugs in passing: appendix figures were numbered `3.1`
  where the PDF said `A1.1`, and the EPUB index printed the running sequence.
- **`check-book.sh` refuses to fall back.** It probes `python3` for presence, for running at all, and
  for version 3.9 or later, and exits 2 if any probe fails. Its arrays and declarations are set up
  before the read loop, so `set -u` cannot turn a missing key into a dead run. This keeps the lesson
  from the old stale-`jq` incident instead of creating a second degraded mode.
- **The agreement fixture's guard section.** It fails if any tool goes back to a filename regex or a
  `-name '*.md'` walk. That is what stops the drift this ticket exists to remove from coming back
  through a later edit.
- **Comments explain the reasoning.** The `--tsv` row grammar and its "no empty field but the last"
  invariant are written down next to `tsv_rows`, where the next editor will see them.

### What I verified, against the six areas the caller flagged

1. **TSV invariant and the bash side.** I checked every row type in `tsv_rows`:
   - `decl` rows: a value is emitted only when `_tostring` makes it non-empty, and tabs and newlines
     are replaced.
   - `setting` rows: `_file_key` guarantees the value is non-empty.
   - `source` rows: empty keys are filtered out, a key holding a tab or newline raises an error, and
     the flag is `0` or `1`.
   - `file` rows: every field is non-empty except the title, which is last. Names are checked against
     `UNSAFE`.
   - `problem` rows: the text field is last.

   On the bash side, the 9-field `file` row maps `f1..f8` correctly onto kind, number, position,
   conforms, title_from, title_line, name and title. I ran these cases under `/usr/bin/python3` and
   bash 3.2, and each assigned correctly: a filename with a space, an empty H1 title (`# `), and a CRLF
   file with a mark above the H1. `IFS=$'\t'` keeps spaces and `read -r` keeps backslashes. One gap is
   in 🟢 below: `setting` values are not checked for tabs.
2. **Where the title line is.** `title_of` reads through `read_text`, which turns CRLF into LF, so
   CRLF files agree with `tail -n +N`. I checked this directly: with a mark on line 1 and the H1 on
   line 2, `title_line` is 2 and `tail -n +3` starts at the body.

   The binder agrees too. It takes `title_from` from the model and drops the first line of the
   mark-stripped text. That line is the first non-mark line, because `PROVENANCE_RE` is the model's
   `MARK_LINE`.

   When the first non-mark line is not an H1, all three tools fall back to the filename.
   `check-book.sh` reports it and reads the body from `tail -n +2`, which is unchanged from `main`.
   There is one edge where the counts can differ, in 🟢 below.
3. **Reader-facing uses versus internal `num`.** Every reader-facing use now reads the model:
   - the contents number (`unit`)
   - the chapter eyebrow, the outline and the attached-script labels (`label`)
   - the EPUB eyebrow (`label`)
   - the figure prefix, in both the PDF and the EPUB (`unit`)
   - the EPUB index link text (`units[n]`)
   - the EPUB glossary target (`by_number[label_num]`)
   - parts (`part`)

   Every lookup still keys on `num`: page ids, probes, `data-ch`, `chapter_id`, `epub_chapter_href`,
   column plans, `ATTACH_URI`, slide ids and the page lookup. `by_number[ch]` cannot raise a
   `KeyError`, because the `stray` check limits `ch` to `chapter_numbers(book)`, and that is the same
   set `by_number` is built from. The PDF glossary prints the glossary's own `ch. N`, which is now the
   model's chapter number.
4. **The `check-references.sh` baseline.** `git ls-tree --name-only` does not recurse, so
   subdirectories show up as bare names. `classify` drops them because it keeps only names ending in
   `.md`. `base_paths` maps each unit to its full listed path through `listed[leaf]`, and since the
   listing is one level deep, two leaves cannot collide. Classifying with the current `book.json` is
   the settled design.
5. **The CI `checkers-floor` job.**
   - Under `bash -e`, `out=$(...) && rc=0 || rc=$?` is correct: a failure inside an `&&`/`||` list
     does not trip `-e`, and `$?` holds the substitution's status.
   - `CI=` does turn strict mode off, because `test-fixtures.sh` tests `[ -n "${CI:-}" ]`.
   - The skip filter's strings match the harness's actual line,
     `skip  <skill>/<name>/run.sh passed with N check(s) skipped`. The `book-model` exclusion is pinned
     to exactly one skipped check, so `11 check(s)` would not match it. Under `pipefail`, the
     `|| true` covers an empty first `grep`.
6. **Python 3.9.** All of these compile under `/usr/bin/python3` 3.9.6: `book_model.py`,
   `check-provenance.sh`, `check-references.sh`, `assertions.sh` and `render-report.py`.
   `from __future__ import annotations` covers `str | None` and builtin generics in annotations.
   - With 3.14 the full suite passes 19 of 19.
   - With 3.9.6 first on PATH and `CI=`, it passes 17 with 2 skipped: `bind` and `save-scripts`.
     `book-model` did not skip locally only because the binder's venv exists on this machine.

#### Suggestions

🟢 **`setting` values are not tab-checked, unlike every other TSV field**

📍 Location: `plugins/bookcraft/scripts/book_model.py:L106-L112`, `L328-L329`

**What I see:**
`_file_key` checks that `glossary_file` and `front_matter_file` are non-empty strings, but does not
check them against `UNSAFE`. I ran `"glossary_file": "g\tx.md"`. It produced
`setting\tglossary_file\tg\tx.md`, and `check-book.sh` read `gloss_name` as `g`.

**The risk:**
Almost none in practice, since nobody names a glossary with a tab in it. But the row grammar promises
that no field holds a tab, and this is the one path where that promise rests on luck rather than a
check.

**Suggested fix:**
In `_file_key`, add `or UNSAFE.search(val)` to the existing rejection, so the bad value fails as a
`ModelError` like a bad filename does.

**Learning note:**
Once a format states an invariant, enforce it where values enter the format rather than where they
are read, so every producer is covered.

---

🟢 **`profile: 0` now reads as absent**

📍 Location: `plugins/bookcraft/scripts/book_model.py:L326`

**What I see:**
`cfg.get("profile") not in (None, False)` is meant to mirror jq's `// empty`. But in Python, `0 == False`,
so `"profile": 0` (and `0.0`) is dropped. I confirmed that no `decl profile` row is emitted for it.
jq treats `0` as truthy, so on `main` this value reached the `case` block and was rejected as an
unknown profile. Now it quietly gets the narration rules.

**Suggested fix:**
`val = cfg.get("profile"); if val is not None and val is not False and _tostring(val): ...`

**Learning note:**
In Python, `x in (None, False)` compares with `==`, and `0 == False`. Use `is` to test for these
singletons.

---

🟢 **An empty mark above the H1 escapes `check-book.sh`'s comment-grammar sweep**

📍 Location: `book_model.py:L82` versus `check-book.sh:L1216`

**What I see:**
`MARK_LINE` accepts `src:.*?-->`, which includes `<!-- src: -->`. `check-book.sh`'s grammar check
requires a non-space after `src:`. The body now starts below the H1, so a mark sitting above the H1
is never swept. On `main`, any such line failed as "first line is not an H1".

**The risk:**
Low. The binder strips that line, so it never reaches the reader. This is R10 doing what it was meant
to do, apart from that one malformed shape.

**Suggested fix:**
Optional: tighten `MARK_LINE` to `src:[ \t]*\S.*?-->`, or have `check-book.sh` run its grammar check
on lines `1..title_line-1` as well. Dropping this is also reasonable.

---

🟢 **`title_line` counts lines the way Python does, and `tail` does not**

📍 Location: `book_model.py:L245-L256`

**What I see:**
`read_text` turns a lone `\r` into a newline, and `str.splitlines` also splits on `\f`, `\x85`,
U+2028 and similar characters. `tail -n +N` counts only `\n`. On a file with old Mac line endings
(CR only), or with one of those characters in a mark above the H1, `check-book.sh` would start its
body at the wrong line.

**Suggested fix:**
Optional: count lines with `text.split("\n")` after the universal-newline read, or open the file with
`newline=""` and split on `\n`. A file with CR-only line endings is rare enough that dropping this is
reasonable.

### Questions

1. **Which file should keep a duplicated unit in `check-references.sh`?** `units_of` keeps the first
   file. In a folder holding an unnumbered `README.md` beside `bk-01-...md`, `README.md` sorts first:
   uppercase sorts before lowercase. It is numbered 1 by position and takes unit `1`, so citations of
   chapter 1 are read against it, with a note printed. Should a file whose name carries the number win
   over one numbered by position? This cannot happen in a book that passes `check-book.sh`, so it is
   not a finding.
2. **Has the `checkers-floor` job run green on GitHub yet?** CI was still pending when I reviewed. I
   checked it by reading the workflow and by a local 3.9.6 run. I did not see a real run on a
   `macos-latest` image, and in particular I have not confirmed that image's `/usr/bin/python3` is
   still 3.9.

The PR delivers its objective: one model that every tool classifies files through, and a fixture that

optional, and the ⏭️ items go to `/pr:close` triage.
