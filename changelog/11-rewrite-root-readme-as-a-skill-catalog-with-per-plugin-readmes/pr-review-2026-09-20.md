### Suggestions

🟢 **The session-start hook row overstates what gets loaded**

📍 Location: `plugins/pr/README.md:384`

**What I see:**

```markdown
| `on-session-start.sh` | `SessionStart` | Loads the branch's plan folder and newest summary
into context, so a session after a compaction does not resume blind. Silent on the default
branch. |
```

**The risk:**

`on-session-start.sh:92-125` does something slightly different. It always prints the branch
folder's **file listing**, then branches: if any `pr-summary-*.md` exists it cats **all** of
them (`ls -t` order, so newest first, but not only the newest) and **skips `PLAN.md`
entirely**; only when no summary exists does it load `PLAN.md` plus the last 100 lines of
`CHANGELOG.md`. The comment at line 101 is explicit that the summary is loaded *instead of*
the plan. A reader who trusts "plan folder and newest summary" will expect `PLAN.md` in
context on a branch that has a summary, and will not expect several summaries at once. This
is the kind of thing someone debugging "why didn't the hook give me my plan" would hit.

**Suggested fix:**

```markdown
| `on-session-start.sh` | `SessionStart` | Lists the branch folder and loads its summaries if
any exist, otherwise `PLAN.md` and the tail of `CHANGELOG.md`, so a session after a compaction
does not resume blind. Silent on the default branch. |
```

**Learning note:** in docs, an `or` collapsed into an `and` is the most common way a true
sentence becomes a wrong one. When a code path branches, the doc has to branch or explicitly
say "one of".

🟢 **The `/pr:start` prose lists its steps out of the order the skill runs them**

📍 Location: `plugins/pr/README.md:160`

**What I see:**

> Creates the branch … **installs dependencies, carries over what a fresh checkout does not
> bring** (untracked local config and the like), initializes the plan folder, **enriches
> `PLAN.md` from the issue body, reads the recent continuity entries**, and moves the issue to
> `status:in-progress`.

**The risk:**

`start/SKILL.md` runs: Step 2 create branch → Step 3 carry over → Step 4 install deps →
Step 5 init plan folder → Step 6 read continuity → Step 7 enrich `PLAN.md` and move the issue.
The README transposes two pairs. A comma-list introduced by "Creates the branch … then" reads
as a sequence, and this section of the README is otherwise scrupulous about order (the
`/pr:close` list is exact, and even preserves "a merge-conflict check placed before the
expensive work"). The inconsistency is what makes it worth a line: readers will assume the
order is meaningful here because it is meaningful three sections down.

**Suggested fix:** swap the two pairs — "carries over what a fresh checkout does not bring,
installs dependencies, initializes the plan folder, reads the recent continuity entries,
enriches `PLAN.md` from the issue body, and moves the issue to `status:in-progress`."

**Learning note:** ordered prose inherits the authority of the ordered prose around it. Either
all sequences in a document are faithful or none should read as one.

🟢 **The page states a prefix convention it does not follow**

📍 Location: `plugins/pr/README.md:37`

**What I see:**

> This page writes the prefix out in every command you would type, and drops it when naming a
> skill in prose.

**The risk:**

The sentence is carried over from `plugins/bookcraft/README.md:33`, where it is true —
bookcraft's headings are `## /createbook` and its prose says `/makebook` bare. Here the
headings are `### /pr:init` and the prose is overwhelmingly prefixed ("`/pr:close` runs it as a
step", "`/pr:close` invokes it", "`/pr:close` also calls it"). Only `The lifecycle spine`
intro and the `Contents` line drop it. A convention stated and not kept is a small credibility
leak in a document whose whole value is that its claims hold.

**Suggested fix:** the document's actual behaviour is the better one at this size — say so:
"This page writes the prefix out everywhere, since at 22 skills a bare name is ambiguous."

**Learning note:** copying a sibling document's structure is good; copying its self-description
is how a house style claim outlives the house style.
