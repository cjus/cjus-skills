### Summary

`/pr:abort` and `/pr:sync` now resolve an explicit ticket number with the anchored branch-name match that `25-fix-cleanup-s-close-check-pathspec-overmatching-ticket-numbers` gave `/pr:cleanup`, instead of an unanchored worktree-path substring. With `worktrees.enabled: false`, `/pr:cleanup` now works on the branch step 0 resolved rather than the session's checkout. It stops when that branch is checked out in the main checkout, reads the branch's committed tree plus the main checkout's untracked files, and fixes `BRANCH` at step 0. Step 8 pulls only when the main checkout is on the default branch.

This is the first review of this branch. No earlier `pr-review-*.md` exists in the plan folder. The two `## Deferred` items in `PLAN.md` are out of scope by decision and are not re-raised here.

### What is working well

- **One rule, one place, and the command kept where it runs.** Each skill carries the two-line `for-each-ref | grep` command and points to `config.md` for the escaping, examples and row semantics. That follows the Open Question decision exactly, and it stops the three skills drifting apart.
- **Cleanup step 0's row-kind table.** It turns `worktrees.enabled` × second field into a 2×3 matrix. The old prose bullet mixed two cases in one sentence. The derived bullet, "Rows, none usable" with worktrees off, necessarily means the main checkout, and the table makes that inference easy to follow.
- **`BRANCH` is fixed at step 0, and step 3's re-derivation is gone.** This closes the real hole from the ticket. With `WORKTREE_PATH` empty, `git -C ""` answers for the session's checkout, so steps 4 and 6 could check and delete the wrong branch. The skill now says why, in words that will stop the step from being added back.
- **The main-checkout stop rests on a real git constraint.** I confirmed `git branch -D` refuses a branch checked out in the main checkout (`cannot delete branch … used by worktree at …`). Stopping at step 0 in both cleanup and abort, before anything closes, is the right place. "Do not switch it for them" gives the correct reason: a switch carries uncommitted changes with it.
- **The `ls-tree` glob trap is caught and documented.** A `pr-summary-*.md` pathspec lists nothing and exits 0. I reproduced that, and listing the folder then filtering by name is the right workaround.
- **Step 1's second half covers the halted close.** Untracked files survive a branch switch, so reading `ls-files --others` in the main checkout finds what a halted close left behind. That case would otherwise read as "never closed".
- **Step 5's skip explains `grep -q ""`,** which matches every line. Without the skip, step 5 would report a worktree that does not exist as still registered. That explanation keeps the skip from being "simplified" away.
- **The no-match hint keys on the cause** (a word before the number), not on whether the config is absent, and it says not to act on the hit.

#### Suggestions

🟢 **1. Abort's rule 1 compares each row to the main checkout, but abort never says how to set `MAIN_CHECKOUT`**

📍 Location: `plugins/pr/skills/abort/SKILL.md:L61-L64` (used again at L135, L217-L218)

**What I see:**
Rule 1 now decides "a worktree of its own" versus "the main checkout" from the row's second field. The old rule 1 ran `git worktree list --porcelain`, and the new one does not. Nothing in abort defines `MAIN_CHECKOUT`. `config.md` does define it ("the first `worktree` entry of `git worktree list --porcelain`"), and rule 1 points there.

**The risk:**
Low, because a model usually knows the repo root. But this is the one comparison that separates the new safety stop from "worktree path = main checkout". Getting it wrong means steps 5 and 6 close the PR and the issue, and then step 7 halts on `is a main working tree`. That is the outcome the stop exists to prevent.

**Suggested fix:**
Mirror cleanup L45 right after the command:

```markdown
Set `MAIN_CHECKOUT` to the first `worktree` entry of `git worktree list --porcelain`. A row whose second field equals it is the main checkout.
```

**Learning note:**
When a safety gate is a comparison, name both sides in the skill that runs it. A definition one cross-reference away gets skipped exactly when the model is working quickly.

🟢 **2. Cleanup step 1's no-workspace pipeline prints a stderr warning on the usual success path, and exits 1 when nothing is found**

📍 Location: `plugins/pr/skills/cleanup/SKILL.md:L80-L84`

**What I see:**
In the usual worktrees-off case, the branch has merged and the main checkout is on `main` but not yet pulled, so the folder does not exist there. The `ls-files --others` half then prints `warning: could not open directory '<changelogRoot>/<slug>/': No such file or directory` on stderr, next to the correct `COMMITMSG.md` row. With no artifacts at all, grep exits 1 and the only other output is that warning.

**The risk:**
Cosmetic, and a misread fails in the safe direction ("ask, default no"). But "No such file or directory" beside a nonzero exit reads like a failed command, and a model may report an error instead of mapping it to the table's "No artifacts at all" row.

**Suggested fix:**

```bash
{ git -C "$MAIN_CHECKOUT" ls-tree -r --name-only "$BRANCH" -- "<changelogRoot>/<slug>/"
  git -C "$MAIN_CHECKOUT" ls-files --others --exclude-standard -- "<changelogRoot>/<slug>/" 2>/dev/null
} | grep -E '/(COMMITMSG|pr-summary-[^/]*|pr-review-[^/]*)\.md$'
```

Then add one clause: "No output, with grep exiting 1, is the 'No artifacts at all' row."

**Learning note:**
In a skill run by a model, the exit code and stderr are part of the output it reads, so a success path should be quiet.

🟢 **3. Cleanup step 2 says the check "holds by construction" but never says to skip the command**

📍 Location: `plugins/pr/skills/cleanup/SKILL.md:L100-L106`

**What I see:**
Steps 5 and 7 open with "Skip when `WORKTREE_PATH` is empty". Step 2 shows `git -C "$WORKTREE_PATH" status --porcelain` and then says "this holds by construction … Do not run the command in the main checkout instead". With an empty path the command runs in the session's own checkout, which can be the main checkout.

**The risk:**
Only a false STOP on unrelated work, which is the safe direction. The wording is still less direct than in the neighbouring steps.

**Suggested fix:**
Open the paragraph with `**Skip when WORKTREE_PATH is empty:** this holds by construction …`.

**Learning note:**
Say the same thing the same way across steps. "Skip" in steps 5 and 7 but a longer explanation in step 2 makes the reader wonder whether the difference means something.

🟢 **4. Abort's remote lookup does not say what to do with several remote rows**

📍 Location: `plugins/pr/skills/abort/SKILL.md:L73-L80`

**What I see:**
Rule 1's "Multiple rows list and stop" covers local rows. The remote fallback then says "A branch exists … set the worktree path empty and carry on", which assumes a single row. In my test, ticket 6 against remote refs alone returned `feature/6-x`, `feature/owner/6-y` and `release/6-r`.

**The risk:**
Small. Step 1's slug check and step 4's typed-slug confirmation would catch a wrong pick. But the skill leaves the model to pick one row.

**Suggested fix:**
Append: "One remote row resolves; several list and stop, as in rule 1."

**Learning note:**
When a fallback reuses a rule's pattern, carry over its cardinality handling too, not just the regex.
