## PR review: build-book.py: anchor the appendix pattern, key colgroups on one number, drop the duplicate EPUB cover

Scope: committed diff `main...10ce213` plus the uncommitted working tree (SKILL.md and
build-book.py wording fixes, the PLAN.md Deferred additions, the new `pr-summary-2026-09-25.md`).
Ticket: `cjus/cjus-skills#37` (consolidates #19, #20, #35). Assertions: disabled
(`.claude/pr-config.json` has `docs.assertionsFile: null`). No earlier `pr-review-*.md` in the
plan folder. The pre-test review's three wording suggestions are confirmed below and not re-raised.

### Summary

The PR anchors `APPENDIX_FILE_RE` the way the three createbook checkers anchor it, so a chapter
slug that contains `-appendix-N-` binds as a chapter. Table measurement and colgroup injection
are now both keyed on the binder's sequential `num`, which reaches the page as
`data-ch="{num}"` on `section.chapter`, so appendix tables get repaired. In the EPUB,
`cover.xhtml` is no longer built when the cover art was rasterised from it. All three parts of
the objective in PLAN.md are delivered, and none of the changes regresses `main`.

### What is working well

- **One source for the key.** `inject_colgroups(body, ch["num"], ...)` and
  `data-ch="{ch["num"]}"` both read `ch["num"]` in the same loop iteration (build-book.py:1971-1973).
  The measurement and the lookup therefore cannot drift apart again. The display label still
  travels with each table, but only for the warning. Separating the lookup key from the display
  string is the right fix, and it removes a whole class of collision rather than just the case
  that was reported.
- **The anchor matches the checkers exactly.** I ran the new pattern, the old one and the
  checkers' `^[a-z]+(?:-[a-z]+)*-appendix-(\d+)-` against 12 names. They agree on every
  chapter-versus-appendix decision: `sql-02-appendix-1-...`, `09-...`, `Guide-...`, `web3-...`
  and `sql--...` are all chapters now. The only disagreement is `sql-appendix-1-.md`, which is
  the tail difference already logged under Deferred. `.search` with a leading `^` and no
  `re.M` anchors correctly.
- **The cover page is not built at all, rather than built and then hidden.** The comment
  explains why: `page()` writes to the manifest. Moving the call after the cover-art decision
  has no side effects. `epub_cover_body` does not touch `assets`, so running it after the
  asset loop cannot orphan an image. Nothing else refers to `cover-page` or `cover.xhtml`
  (`epub_toc` builds only from `front`, chapters and `back`). The `description_file` check it
  skips has already run in the PDF build.
- **Comments say why.** The `APPENDIX_FILE_RE`, `plan_columns`, `TABLE_FIT_JS` and cover
  comments each name the failure the code prevents, which matches the style of the rest of the
  file.
- **No stale JS.** Removing `m` leaves no dangling reference in `TABLE_FIT_JS`. The only
  consumers of `t["ch"]` are `plan_columns` and the warning, and both were updated.
- **The file still parses.** `ast.parse` succeeds, and the new f-string mixes quote styles, so
  it does not add another PEP 701 dependency.

**The pre-test wording fixes are correct.** The regex really is `[a-z]` only, so "lowercase
letters and dashes" is accurate in both SKILL.md § Appendices and the build-book.py comment. The
Cover row matches the code: `generated_cover` drops the page, and declared art keeps it. If
rasterising fails, the text page is kept, so "opens on one cover" still holds. The warnings row,
"chapter or appendix", matches `t.get("label")`, which is always "Chapter N" or "Appendix N".

#### Important

🟡 **bookcraft's version is not bumped, so installed copies will not receive these fixes**

📍 Location: `plugins/bookcraft/.claude-plugin/plugin.json:5` (unchanged at `1.7.0`)

**What I see:**
The PR changes `build-book.py` and makebook's `SKILL.md`, and leaves `plugin.json` at `1.7.0`.
Every earlier PR that changed bookcraft's behaviour bumped this file: #14, #15, #17, #31 and #33.
The only exception, #22, changed a README and nothing else. The convention comes from #12
("bump bookcraft and pr so installed copies refresh"). The #16 plan folder's CHANGELOG spells
it out: "installed copies do not refresh without it, and the repo bumps minor for a behavior
change."

**The risk:**
The installer uses the version number to decide whether anything changed. A machine running
1.7.0 would see the same number after merge and fetch nothing. It would go on binding
look-alike slugs as appendices, skipping appendix tables and opening EPUBs on two covers. The
fix would sit in the repo but never reach an installed copy. This is not a regression against
`main`, so it does not block. It is a gap in shipping the objective, and closing it takes one
line.

**Suggested fix:**
Bump `"version": "1.7.0"` to `"1.8.0"`. The summary lists two behaviour changes, and the repo's
rule is a minor bump for a behaviour change. Also list `plugin.json` under "Key changes" in
`pr-summary-2026-09-25.md`, and correct "Two plugin files changed" to three.

**Learning note:**
In a plugin marketplace the version is the release signal. Committing the code is not the same
as shipping it. Treat the manifest bump as part of any change that should reach a user.

#### Suggestions

🟢 **The creation-stamp paragraph now says "the EPUB's cover", which is loose when art is declared**

📍 Location: `plugins/bookcraft/skills/makebook/SKILL.md:116`

On `main`, "the EPUB's cover page" was always true. The branch's "the EPUB's cover" is true for
generated art. With a declared `cover_image`, though, most readers take "the EPUB's cover" to
mean the art, and that art carries no stamp. Only the text page behind it does. Line 279 does
clear this up, so this is optional. For example: "the PDF cover and the EPUB's cover (the
generated art, or the text cover page behind declared art) both print...".

🟢 **Two claims in the PR summary have no entry in CHANGELOG.md**

📍 Location: `pr-summary-2026-09-25.md`, § Testing

- "The new pattern also agrees with the checkers' pattern on seven sample names." CHANGELOG.md

  PDF text, the page count and the spine, but not an epubcheck run. The epubcheck line in the

Either add a line to CHANGELOG.md for each, or cut the claims from the summary. I checked every
other claim in the summary against the code, CHANGELOG.md, `gh pr checks` (fixtures pass on
macos-latest and ubuntu-latest) and the repo, and they all hold. That includes "nothing in the
repo parses that text": no file other than build-book.py and the changelog greps the warning.
One small point: "one line after `inject_colgroups`" is really the next statement, two physical
lines later. It is harmless.
