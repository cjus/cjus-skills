# PR review: give the fixture folders a runner and the repo its first ci

Reviewed 2026-09-23 against `origin/main`. PR #23, ticket
[#6 — Fixture health for createbook's checker](https://github.com/cjus/cjus-skills/issues/6).
First review of this branch; no prior `pr-review-*.md` exists in this folder, so nothing here
re-raises a settled finding.

## Summary

Adds `plugins/bookcraft/scripts/test-fixtures.sh`, a runner that grades all nine bookcraft
fixture folders against both an expected exit code and a string the output must carry, plus
`.github/workflows/fixtures.yml`, the repo's first CI. `fixtures/provenance/` is fixed so
`check-book.sh` exits 0 on it while `check-provenance.sh` still exits 1, by giving both chapters
the two-part shape the structural rule requires — no checker was modified. A third half is added
to `fixtures/jq-unrunnable/run.sh` covering absent `jq` as distinct from unrunnable `jq`.

The objective in `PLAN.md` is delivered and the evidence behind it is real, not asserted.

## What is working well

- **The substring assertion is the right lesson drawn from the right evidence.** The measured
  fact — silencing the H3 rule left `guide-under-narration/` still exiting 1 on its remaining
  four failures — is exactly the argument for pairing every expectation with a message, and the
  header comment at `test-fixtures.sh:22-28` records it where the next maintainer will read it.
- **The completeness check works; I reproduced it.** Creating an empty
  `createbook/fixtures/zz-uncovered/` produced
  `FAIL  createbook/fixtures/zz-uncovered/ is asserted by nothing`. The `for d in
  "$ROOT"/skills/*/fixtures/*/` glob degrades correctly to a no-op when a skill has no
  `fixtures/`, and `fixtures/provenance/sources/` is not mistaken for a fixture, because the glob
  is one level deep.
- **Invoking the checkers through their shebangs rather than a named interpreter.** Given
  `check-provenance.sh` and `check-references.sh` are Python behind a `.sh` extension, this turns
  a lost executable bit into a clean failure instead of pages of bash parse garbage, and the
  CI step at `fixtures.yml:39-46` asserts the bit survives checkout. That is a packaging defect
  class most suites never see.
- **bash 3.2 clean, and I verified it rather than read it.** `/bin/bash` here is 3.2.57
  (arm64-apple-darwin26) and is the only `bash` on `PATH`; the whole suite ran under it — 11
  checks, 0 failed, 6.0s wall. No `[[ ]]`, no associative arrays, no `mapfile`, no `${v,,}`.
  `n_skipped=$(... | grep -c '^skip ' || true)` correctly yields `"0"` under `pipefail` rather
  than aborting, which is the usual 3.2 trap here.
- **The symlink farm holds up under the two hazards I went looking for.** I confirmed on this
  machine that BSD `ln -s src farm/` refuses to clobber (`File exists`) *and* does not follow an
  existing `farm/<name>` that is itself a symlink to a directory — so the "earlier directories
  win, PATH precedence survives" claim is true, and there is no path by which the farm writes
  outside `$tmp`. The `PATH="$tmp/nojq" command -v jq` post-condition is the correct safety net:
  if the farm ever fails to be `jq`-free the half degrades to a loud `skip`, which `--strict`
  turns into a CI failure rather than a false green.
- **`jq` asserted to *run*, not to exist, at both layers** — the CI step and
  `test-fixtures.sh:88-91` — with the three-way distinction between working, unrunnable and
  absent `jq` made explicit and separately covered. The reasoning for *refusing* to grade the
  manifest without `jq` (rather than grading it and reporting failures that are not defects) is
  the correct call and is written down at `test-fixtures.sh:78-86`.
- **The provenance fix is minimal and does not move the subject.** Two part headings added, the
  `book.json` expectation sentence updated in the same edit, and the fixture's own contract
  ("chapter 1 reports nothing") preserved — a chapter-1 regression would push the count past
  `6 failure(s)` and be caught.
- **Commit messages and docs are in the repo's voice**, lowercase imperative, no tool branding,
  and `NOTES.md` distinguishes what was *measured* from what was *asserted*. That distinction is
  what makes the entry worth keeping.
- **The `ROOT` argument** means the same suite grades an installed copy, which is the only way
  the packaging claims above are testable.

## Issues found

### Critical

None. Nothing in this branch introduces a correctness, security or data-loss defect, and neither
checker was touched.

### Important

🟡 **A manifest row with no required-substring field silently reverts to exit-code-only**

📍 Location: `plugins/bookcraft/scripts/test-fixtures.sh:94-141`

**What I see:**

```bash
while IFS='|' read -r rel checker want must; do
  ...
  saved=$IFS; IFS='~'
  for s in $must; do
    printf '%s\n' "$out" | grep -qF -- "$s" || missing="$missing
      missing from the output: $s"
  done
```

**The risk:** `read` assigns an empty string to `must` when a row has only three fields, so
`for s in $must` iterates zero times, `missing` stays empty, and the row passes on its exit code
alone. I measured this: a row `c/d|check-book|0` parses to `must=[]` and yields `assertions=0`.
That is precisely the failure mode this runner exists to end — the header at lines 22-28 promises
"every non-zero expectation below also names a string the output must carry", and nothing enforces
it. The next person adding a fixture in a hurry gets the old behaviour back with no signal.

**Suggested fix:** make the guarantee structural rather than editorial.

```bash
    if [ -z "$must" ]; then
      fail "$rel: manifest row names no required output; an exit code is not an assertion"
      continue
    fi
```

**Learning note:** an invariant a comment states is a convention; an invariant the code checks is
a guarantee. When a script's whole reason for existing is one rule, that rule is the first thing
it should assert about itself.

🟡 **"Linux cannot fail the branch" is true of the workflow run and false of the check run, and
the repo's own tooling reads the check run**

📍 Location: `.github/workflows/fixtures.yml:22`, plus `README.md` § The fixture suite, and CI and
`plugins/bookcraft/README.md`

**What I see:**

```yaml
continue-on-error: ${{ matrix.blocking == false }}
```

**The risk:** the expression itself is correct and the run-level claim is real — I confirmed on
run `35918559775` that the workflow conclusion was `success` while `fixtures (ubuntu-latest)`
failed. But the *check run* for that job still carries `conclusion: failure`:

```
fixtures (ubuntu-latest) => failure
fixtures (macos-latest)  => success
```

`gh pr checks` reports that as a `fail` bucket, and this repo's own lifecycle script does:

```js
const checks = parseJson(gh("pr", "checks", ..., "--json", "name,bucket"));
pr.ci = buckets.includes("fail") ? "fail" : ...
if (pr?.ci === "fail") return [null, "CI is red. Fix the failing check before anything else."];
```

So a Linux-only failure **does** gate `/pr:close`, and shows a red X in the PR checks list. Phase
5 verified the run conclusion, which is why this was missed. The docs state the stronger claim
than the mechanism delivers, and the operator meets it as a confusing block rather than as
information.

**Suggested fix:** pick one of two, and make the prose match.

Keep it truly non-blocking by moving `continue-on-error` to the step, so the job conclusion is
`success`:

```yaml
      - name: Run the fixture suite
        continue-on-error: ${{ !matrix.blocking }}
        run: plugins/bookcraft/scripts/test-fixtures.sh --strict
```

Or keep the current visible-red behaviour and soften the wording — "Linux cannot fail the
workflow run, but it does show red in the PR checks list and `gh pr checks` reads it as a
failure" — so nobody is surprised at close time.

**Learning note:** GitHub Actions has two independent notions of "did it pass": the workflow run
conclusion and the per-job check run conclusion. Job-level `continue-on-error` moves only the
first. Which one matters depends entirely on who is reading, and here the reader is this repo's
own automation.

🟡 **The provenance row asserts half of what the fixture documents**

📍 Location: `plugins/bookcraft/scripts/test-fixtures.sh:102`

**What I see:**

```
createbook/provenance|check-provenance|1|6 failure(s)
```

**The risk:** the fixture's `book.json` asserts "6 failures and 1 review, exit 1", and the updated
sentence tells the reader to "update this sentence and the manifest there in the same edit". The
manifest covers the failure count and not the review verdict. The output carries exactly one
`REVIEW ` line; a regression that stopped emitting the review verdict altogether leaves
`6 failure(s)` intact and exit 1 intact, and passes. That is the same shape as the defect this
whole branch was written about.

**Suggested fix:**

```
createbook/provenance|check-provenance|1|6 failure(s)~REVIEW provenance-fixture-02
```

**Learning note:** when a fixture states its expectation in prose, that sentence is the
specification. An assertion that covers part of it leaves the uncovered part looking checked,
which is worse than an obvious gap.

🟡 **Two cross-repo ticket citations land in a committed public artifact**

📍 Location: `changelog/6-fixture-health-for-createbook-s-checker/PLAN.md:25` and `:41`

**What I see:** both lines cite a bare `#NN` as evidence ("Surfaced during …, where both were
deferred", "… alone produced three defects"). That number resolves to nothing in this repo — the
highest issue or PR number here is 23 — so it is another project's ticket number, quoted along
with details from it, in a tracked file in a public repo.

**The risk:** `CLAUDE.md` is explicit that `changelog/**` artifacts are the main source of this
leak class and that another repo's ticket must never be cited as evidence or precedent. It also
renders as a dead reference for any reader who follows it. Mitigating context, and why this is not
Critical: the same pattern already exists on `main` at
`plugins/bookcraft/skills/createbook/NOTES.md:364`, so this PR is not introducing a new class of
leak, and the bare number names nothing on its own. It is also already published in the ticket
body upstream of this branch.

**Suggested fix:** state the underlying fact generically — "surfaced during an earlier bookcraft
hardening ticket, where both were deferred" — in both lines. One edit, before merge, since the
file is about to become permanent public history.

**Learning note:** the rule reaches artifacts, not just code. Anything the PR lifecycle enriches
from an issue body is the highest-risk surface precisely because it is generated rather than
written.

🟡 **The repo's first workflow ships with no `permissions:` block**

📍 Location: `.github/workflows/fixtures.yml:11-32`

**The risk:** with no explicit block, `GITHUB_TOKEN` gets the repository or org default, which on
many repos is still read *and write*. This job needs nothing but `contents: read`. Fork PRs are
already forced read-only by GitHub, so the exposure is limited — but this is the file every future
workflow in the repo will be copied from, and the default it establishes is the one that matters.

**Suggested fix:**

```yaml
permissions:
  contents: read
```

**Learning note:** least privilege on a CI token is cheapest at the moment the first workflow is
written, because from then on it is inherited rather than decided.

### Suggestions

🟢 **`--help` truncates mid-sentence.** `test-fixtures.sh:41` prints `sed -n '3,30p'`, but the
header comment runs to line 32, so help ends at "Every fixture folder must be covered by a
manifest row or carry its own" — cutting off the completeness rule, which is one of the two things
a reader most needs. A line-range coupling like this drifts on every header edit; prefer stopping
at the first non-comment line:
`sed -n '3,${/^[^#]/q;p;}' "$0" | sed 's/^# \{0,1\}//'`.

🟢 **No `timeout-minutes` or `concurrency` on the workflow.** The suite runs in six seconds, so a
`timeout-minutes: 10` costs nothing and bounds a hung `run.sh` at ten minutes instead of six hours
of runner time. A `concurrency` group keyed on the ref with `cancel-in-progress: true` stops
superseded pushes piling up — though note this repo's lifecycle script deliberately treats a
cancelled check as *not* green, so that is a trade, not a free win.

🟢 **An empty `PATH` directory leaves a dangling `*` symlink in the farm.**
`jq-unrunnable/run.sh:113` — `ln -s "$d"/* "$tmp/nojq/"` with an unmatched glob links the literal
pattern. Cosmetic today (nothing looks up a command named `*`), and `2>/dev/null` hides it. A
`set -- "$d"/*; [ -e "$1" ] || continue` guard would make the farm exactly what the comment says
it is.

🟢 **The substring split is unquoted, so a future glob character would be pathname-expanded.**
`test-fixtures.sh:131-136` — `for s in $must` under `IFS='~'` still undergoes pathname expansion.
Every current row is safe (`(`, `)` and `:` are not glob metacharacters), and a `*` in a required
string would only misbehave if it happened to match a file in the invoking directory. Worth a
`set -f` around the loop, or a note, so the next row added is not the one that finds out.

🟢 **A second positional argument silently overrides the first.** `test-fixtures.sh:45` —
`*) ROOT="$1"` assigns unconditionally. A typo'd invocation grades a tree the operator did not
name. One `[ -z "$ROOT" ] || { echo "error: give at most one plugin path" >&2; exit 2; }` closes it.

### ⏭️ Deferred to follow-up

These fail the in-scope test — each would exist on `main` had this PR never been written — so none
of them affects the verdict.

- **`command -v -a jq` is not valid bash, so the jq-candidate probe never consults `PATH`** —
  `plugins/bookcraft/skills/createbook/fixtures/jq-unrunnable/run.sh:45`. `command` takes only
  `-p`, `-V` and `-v`; I measured `command: -a: invalid option`, rc 2, no output. The loop
  therefore falls back to the three hardcoded paths, and the comment's intent ("the one on PATH is
  not assumed to be it") is not achieved. *Symptom:* on a machine whose only working `jq` is
  outside `/usr/bin`, `/opt/homebrew/bin` and `/usr/local/bin`, half one skips — and now that CI
  runs `--strict`, a skip is a failure. *Occasion:* next change to the jq guard or this fixture.
  Fix is `type -aP jq` or a `$PATH` walk. theme: jq probe robustness.
- **`check-references.sh` has no fixture coverage at all** — it carries the same `.sh`-extension-
  but-Python shebang hazard the new suite was built to catch for the other two, and neither the
  suite nor the CI executable-bit step mentions it. *Symptom:* a citation-checker regression, or a
  lost executable bit on it, ships unnoticed. *Occasion:* next change to `check-references.sh`.
  theme: checker coverage.
- **A pre-existing bare cross-repo ticket citation on `main`** —
  `plugins/bookcraft/skills/createbook/NOTES.md:364`. Same class as the Important item above, but
  it predates the branch. *Symptom:* a public file cites a ticket that resolves to nothing here.
  *Occasion:* next `NOTES.md` edit or cross-reference sweep. theme: cross-repo citation scrub.

Noted and **dropped**, not deferred: the runner reads only a `run.sh`'s exit code and `^skip `
count, so a `run.sh` printing `FAIL` while exiting 0 would pass — but all three existing `run.sh`
scripts exit on their failure count, so there is no live risk and no occasion to change it.

## Questions

1. `fixtures/ledger/` exits 2 under `check-book.sh` because it is not a book folder. It is covered
   by its own `run.sh` and so satisfies the completeness check — was leaving it out of the manifest
   deliberate, or would a row asserting the exit-2 "not a book folder" message add anything you
   want?
2. The `push` trigger is limited to `main`. Was that to avoid double runs on PR branches, or would
   you want pushes to a branch with no PR yet to run too?
3. For the Linux job — is the intent "see the result, never be blocked by it", or "be blocked but
   know it is advisory"? That decides which of the two fixes above is right.

## Verdict

The objective is delivered and independently verifiable: the provenance folder's exit code now
carries signal under both checkers, all nine folders are asserted, the completeness check
demonstrably fires, the suite runs clean under macOS's own bash 3.2, and CI executes it on every
pull request. No Critical issue was introduced and nothing regressed — `main` had no CI and no
runner at all, so every Important item above is a refinement of new ground rather than a
regression from old.

The five Important items are all cheap; the cross-repo citation in `PLAN.md` and the Linux wording
are the two worth doing before merge, since both become permanent the moment this lands.

VERDICT: APPROVE

Scrub the two `PLAN.md` citations and reconcile the Linux non-blocking wording with the check-run
behaviour, then close.
