# PR review: [#1] guard-default-branch.sh under-matches a truncated payload when jq is absent

PR #53 (draft) · branch `feature/1-guard-default-branch-sh-under-matches-a-truncated-payload-when-jq-is-absent`
· base `main` · reviewed 2026-09-30 · one commit, `105ee29`

## Summary

When jq is missing, the no-jq branch of `plugins/pr/hooks/guard-default-branch.sh` now checks that
the payload arrived whole before it matches anything. Whole means two things: a `"command"` key
whose string value closes on an unescaped quote (`PAYLOAD_CMD_RAW`), and a payload that ends in
`}` (`PAYLOAD_END_RAW`). A payload that fails either test goes to `gate()` with `MODE` still
empty, so it is denied in every mode. The check runs before the approval token and before the mode
is recovered from the payload. The suite grows from 73 to 91 cases with three no-jq sections, and
the hook comments, the header's decision table and the hooks README are updated. The version goes
to 0.2.10.

**Scope, as applied.** This is the first review on the branch; no earlier `pr-review-*.md` exists.
The objective in `PLAN.md` is the acceptance bar. The three items already under the PLAN's
`## Deferred` heading are not re-raised here, and I agree with all three. There is no assertions
file to audit: `docs.assertionsFile` is `null`.

**What I verified rather than assumed:**

- **Suite.** 91/91 on macOS (bash 3.2.57). Against `main`'s hook it gives 85/6, and the six
  failures are exactly the six truncation cases that expect `deny`. Both results are the same on
  Ubuntu 24.04 (bash 5.2.21, glibc regex, in a Docker container). CI does not run this suite, so
  that is the first glibc data point.
- **Fail-open sweep, beyond the author's own.** I built 11 payloads in the harness key order,
  including every documented `tool_input` key. They cover a chain with a `}` in a message, escaped
  quotes, emoji and other non-ASCII text, a trailing backslash, pretty-printed JSON, a
  `"command":"ls"}` forgery in the description, the same forgery inside the command, a
  `permission_mode` forgery, JSON escapes, and a token followed by a second assignment. I ran
  **every byte prefix** of each through the hook with jq hidden, under `C` and `en_US.UTF-8` on
  macOS, and under `C` and `C.UTF-8` on Linux. Byte cuts land inside multibyte characters.
  **No prefix of a payload that gates exited 0, and no prefix weakened a `deny` to an `ask`.**
- **Why that holds, not only that it held.** Inside a JSON string every `"` arrives as `\"`, so
  `d"` followed by `:` occurs only where a key ends. `"command"[[:space:]]*:` can therefore match
  only a key named `command`. From that key's opening quote, `([^"\\]|\\.)*"` can read the value
  only one way: every `\` must pair with the character after it, and the value cannot run past an
  unescaped `"`. The match ends at the real closing quote or not at all. So once the closing-quote
  half passes, the command is whole, and the approval token, the mode (which comes ahead of
  `tool_input`) and GIT_VERB all see what the whole payload would show them. A cut that ends in
  the middle of a UTF-8 character has no closing quote after it and does not end in `}`, so it is
  denied in every locale.
- **Mutation table.** The four rows I re-ran match the CHANGELOG: brace half only, quote half only,
  any `"` closes the value, and check removed. The claim "each half is pinned by a case that only
  it catches" is accurate. I added one mutant of my own, a value that allows no escapes at all. It
  is caught by three of the false-positive cases ("escaped quotes, trailing backslash",
  "multi-line command passes", "message forging the token still gates"). So those cases guard
  against a check that is too strict, not only against coverage padding.
- **README counts.** 91, and 89 with 2 skipped, both match. I reproduced all three mass-failure
  shapes: a broken jq gives 33/58 from a configured and from an unconfigured directory; a missing
  jq gives 33/58 outside a configured repo and 6/85 inside one.
- **False-positive exposure.** The Claude Code hooks docs say the `Bash` matcher is an exact match,
  so `BashOutput` and similar tools never reach this path. The documented payload has no
  `command` key other than `tool_input.command`, and it always ends in `}`. On Linux, whole
  payloads pass the check under both `C` and `C.UTF-8`.
- **Cost.** A 1MB command takes 0.15s on macOS and 0.13 to 0.2s on Linux for the whole hook run,
  and 4MB takes 0.47s. Time grows roughly linearly with size, and the hook comment's figure (under
  0.1s for the check alone under bash 3.2) is consistent with this.
- **Whole-payload behaviour is unchanged.** I compared `main`'s hook and the branch's hook on
  whole payloads with jq hidden. Every one got the same decision from both, including the ones in
  the pre-existing finding below.
- **Commit message.** Imperative, lowercase, no period and no AI attribution, per
  `git-conventions.md`.

## What is working well

- **The check is the true counterpart of the jq sentinel.** "The command's value closed" is the
  property that matters for GIT_VERB, and "the object closed" is the parity rule with the jq path's
  deny for a payload it cannot parse. Treating both halves as required, and giving each a probe
  that only it catches, is exactly the discipline the header asks for.
- **The ordering was reasoned about, and it is pinned.** Running the check before the token and
  before mode recovery, then gating with `MODE` empty, means a fragment can never carry authority
  the whole object did not confirm. The "cut after the approval token" case and the mode-first
  mutant (86/91) prove that the ordering, and not luck, decides the result.
- **The jq-hidden precheck.** On macOS, dropping a directory from `PATH` does not hide jq, because
  `/usr/bin/jq` exists. Without the precheck, every no-jq case would pass vacuously through the jq
  path, which also denies a truncated payload. Catching that before it could mislead is the kind
  of thing that keeps a suite honest.
- **The probes were reshaped until the mutants died.** Adding the leading `echo "a"` to the `}`
  case, and putting the command last in the trailing-backslash case, are both changes the
  CHANGELOG says were made because a sloppier check survived. That is how probe design should go.
- **The blind spot is named and pinned, not hidden.** "cut after tool_input closes still gates"
  turns the one class of cut the check cannot see into a tested, documented property.
- **The README's mass-failure shapes were measured, not guessed.** The author re-derived the old
  31/42 from `main` before trusting the method, and all three new shapes reproduce exactly.

#### Important

🟡 **The README claims a whole payload without jq behaves as it does with jq, and it does not**

📍 Location: `plugins/pr/hooks/README.md:L139-L140`

**What I see:**

```
... and the raw-payload path the hook takes without `jq`: a
whole payload behaves as it does with `jq`, and a payload cut short or empty is denied.
```

**The risk:**
This sentence is new in this PR, and it is false in two measured ways:

1. The no-jq path gates a commit on **every** branch. Your own Phase 1 table shows a
   feature-branch commit answering `ask` without jq, where the jq path passes it.
2. The no-jq path **under-matches** some whole payloads that the jq path gates. I measured these,
   and the results are the same on `main` and on the branch:

   | command | jq | no jq |
   |---|---|---|
   | `git commit -m x` | ask | ask |
   | `git push` | ask | **pass** |
   | `git commit` | ask | **pass** |
   | `cd /x && git push` | ask | **pass** |
   | `git add -A` then a newline then `git commit -m x` | ask | **pass** |
   | `ls` then a newline then `git push origin main` | ask | **pass** |

The suite's section header says the accurate thing: "a whole payload behaves **as it always
did**". The README turns that into a claim of parity with jq, in the one document an operator
reads to decide how much to trust the degraded path. This is a guard whose header warns that
reading it is not evidence, so its docs should not state a safety property that fails under
measurement.

This is not a behavioural regression, which is why it does not block. The under-match itself is
pre-existing and is deferred below.

**Suggested fix:**

```
... and the raw-payload path the hook takes without `jq`: a whole payload gets the decision it
always did, and a payload cut short or empty is denied.
```

**Learning note:**
The claim a document makes should be the claim the test proves. The suite proves "unchanged by
this fix", not "equivalent to jq". Keeping the two words apart is what stops a later reader from
leaning on a property no one measured.

#### Suggestions

🟢 **The mass-failure explanation is slightly off for the new no-jq sections, though the counts are
right**

📍 Location: `plugins/pr/hooks/README.md:L167-L172`

**What I see:** "A `jq` that cannot run … is still found by the hook, which then emits nothing at
all, so only the cases expecting no output pass." Later: "activation resolves from the directory
the suite was run in … only the unconfigured-repo cases pass".

**The risk:** In the broken-jq shape, the no-jq sections hide jq from the hook, so the hook does
**not** find it. It takes the no-jq path on the empty payloads and prints a deny through `printf`.
Six of those sections' `pass`-expecting cases therefore fail, and only two pass ("jq is hidden
from the hook" and "truncated, unconfigured repo is inert"). In the 6/85 shape, one of the six
passes is the jq-hidden check, which is not an unconfigured-repo case. Activation also resolves
from `CLAUDE_PROJECT_DIR` when it is set, and falls back to the directory only when it is not.
None of this changes a number, but someone reading 33/58 against this paragraph case by case will
find six "no output" cases failing.

**Suggested fix:** Make the causal sentence "…so only the cases expecting no output pass, apart
from the no-`jq` sections, which hide `jq` from the hook and where two cases pass." Make the
activation sentence "…activation resolves from `CLAUDE_PROJECT_DIR`, or failing that the
directory the suite was run in…".

**Learning note:** Once a suite has two harnesses, `t()` and `nj()`, every sentence that explains
how the suite fails needs to say which harness it describes.

🟢 **The blind-spot comment describes one cut where there is a class of them, and "a commit still
gates" says more than the check guarantees**

📍 Location: `plugins/pr/hooks/guard-default-branch.sh:L254-L256`

**What I see:** "The one cut both halves pass is just after a nested `}` that follows the command,
such as tool_input's own. The command is whole there, so GIT_VERB still reads all of it and a
commit still gates."

**The risk:** Your own prototype in the CHANGELOG found two such cuts: one after tool_input's `}`,
and one after a `}` inside the description. The class is "any `}` after the command's closing
quote", including a `}` inside a later string value. And "a commit still gates" is only as true
as GIT_VERB on the raw text, which misses the cases in the table above. What the check actually
guarantees is narrower and stronger: in that blind spot, the verb test reads exactly what it would
read in the whole payload.

**Suggested fix:** "Cuts that both halves pass land just after a `}` that follows the command's
close: tool_input's own, or one inside a later value. The command is whole there, so every later
test reads exactly what the whole payload would give it, which the suite pins."

**Learning note:** State the invariant, "same input as the whole payload", rather than one outcome
of it, "a commit gates". The invariant stays true when the downstream test changes.

🟢 **Name the uniqueness assumption the closing-quote half relies on**

📍 Location: `plugins/pr/hooks/guard-default-branch.sh:L246-L249`

**What I see:** The closing-quote half proves the **command** closed only because
`"command"[[:space:]]*:` can match nothing except the `tool_input.command` key. In the documented
payload that is true today.

**The risk:** Suppose a future payload field carried a nested object with its own `command` key
ahead of `tool_input`. Then a cut just after a `}` inside the real command would pass both halves.
Nothing in the comment would tell the next editor that this assumption holds the check up.

**Suggested fix:** Add one sentence: "This relies on `command` being the only key of that name in
the payload, which is true of every documented PreToolUse shape. Inside a string value a `"` is
always `\"`, so the pattern cannot match text within a value."

**Learning note:** A regex over raw JSON is sound only relative to a schema. Writing the schema
assumption down beside the regex is what lets someone notice when the schema moves.

  occurrence. theme: guard degraded-jq fail-open. **Clears TICKET under the same escalation.**
  *Symptom:* with a broken jq first on `PATH`, a commit on the default branch runs unguarded and
  the operator sees nothing. *Occasion:* file now alongside the item above, as one issue with two
  checklist items.
