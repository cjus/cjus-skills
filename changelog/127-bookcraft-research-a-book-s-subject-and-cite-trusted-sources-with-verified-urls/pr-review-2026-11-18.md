### Important

🟡 **1. A link inside parentheses is read with the closing parenthesis attached, so a correct citation fails**

📍 Location: `plugins/bookcraft/skills/createbook/scripts/check-provenance.sh`, the `LINK_TARGET` regex in the block added after `WEB = re.compile(...)`

**What I see:**

```python
LINK_TARGET = re.compile(r"\]\((https?://\S+?)\)(?=[\s.,;:!?*_]|$)", re.M)
```

The lazy match stops at the first `)` followed by whitespace, punctuation or the end of the line. In `(in short, [a cache hit skips the step](https://docs.example.org/guide/caching)), so ...`, the first `)` is followed by `)`. That does not satisfy the lookahead, so the match extends one character and captures `https://docs.example.org/guide/caching)`.

**The risk:** I changed research fixture 01's first `web 1` sentence to wrap the link in a parenthetical. `check-provenance.sh` then fails with:

```
FAIL  research-fixture-01-...md: links https://docs.example.org/guide/caching), which is not in research/ledger.json; ...
```

A parenthetical aside ending in a link is ordinary prose, and the citation is correct. This fails closed, so no unverified URL gets through, and the book does not regress against the base branch, which banned links outright. But the message tells the author that a ledger URL is not in the ledger, which sends them looking for a fault that is not there. In a chapter whose closing list did not already link the same URL, it would also report "never links its URL", a second false failure. This bug came in with the fix for prior suggestion 6, so it is in scope.

**Suggested fix:** match one level of balanced parentheses explicitly instead of relying on the lookahead:

```python
LINK_TARGET = re.compile(r"\]\((https?://(?:[^\s()]|\([^\s()]*\))+)\)")
```

I checked this against three inputs. `(in short, [a](https://d/x)), so` gives `https://d/x`. `[b](https://w/Cache_(computing)).` gives `https://w/Cache_(computing)`. `[c](https://d/y) and (z)` gives `https://d/y`. Add the parenthetical form to research fixture 01 so the manifest row pins it.

**Learning note:** a lookahead that guesses where a construct ends from the next character breaks when constructs nest. If the grammar is "balanced parentheses", the regex should encode the balance, not infer it.

### Suggestions

🟢 **2. Trusted containment still accepts a host followed by `?`, `#` or `\`, and `..` path segments**

📍 `research-ledger.sh`, `trusted()` and `_rest()`

`_rest(url).split("/", 1)[0]` treats everything up to the first `/` as the host. So `https://evil.test?.docs.example.org` and `https://evil.test#.docs.example.org` both pass `URL.match` and are accepted for `docs.example.org`. `urllib.parse.urlsplit` gives `.hostname == "evil.test"`, and `verify` would fetch from there. Its redirect check compares `geturl()`, which equals the original URL when there is no redirect, so it passes too. `https://github.com/example-org/../other/x` is still accepted for `github.com/example-org`. A model is very unlikely to write any of these, so this is hardening, not a live defect. The fix the first review suggested still applies and covers all of them at once: take the host from `urlsplit(url).hostname`, refuse userinfo and any `..` segment, and compare the path prefix against `urlsplit(url).path`. That also removes the explicit-port false refusal (`github.com:443/example-org`).

🟢 **3. `list` crashes on a ledger whose top level or entries are not objects**

📍 `research-ledger.sh`, `cmd_list`

For `[1, 2]` or `"entries": ["x"]`, `load` returns the document together with its problems. `cmd_list` reports neither and calls `.get` on a list or a string, which raises `AttributeError`. `check` and `check-provenance.sh` report both cases correctly. This is the same class as prior finding 2, but in a display command, so it is low stakes. Print the problems and return 1 when there are any, before listing.

🟢 **4. Two wording leftovers from the first review, plus one in NOTES.md**

- `createbook/SKILL.md` § Research the subject still says "every checker and `/makebook` read the book folder one level deep, so `research/` is invisible to them". `check-provenance.sh` and `research-ledger.sh` read `research/` now. Narrow it to "the notes are never bound, and no checker reads them".
- The `fixtures/research/run.sh` header still says entry 3's quote is found "whatever its HTML, entities and typographic quotes". `research/pages/3.html` has no entities or typographic quotes. The separate `visible_text` case covers those, so soften the header or add an `&rsquo;` to the page.
- NOTES.md § Research and verified citations says the check fails "any URL in a chapter the ledger does not hold". Since the fix, that is any URL in a chapter's **prose**. Adding that one word keeps the design record accurate.
