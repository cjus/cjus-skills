# PR review: Ship the hooks with the plugin instead of per-repo settings

PR #4, ticket #3, base `main`, 3 commits (`0038dab`, `e443d9b`, `e2b7116`).

## Summary

The branch declares the plugin's three hooks in `plugins/pr/hooks/hooks.json`, where
`${CLAUDE_PLUGIN_ROOT}` actually resolves, replacing a per-repo `.claude/settings.json`
procedure that produced hooks which never fired. Because a plugin enabled at user scope
reaches every repo on the machine, it adds an activation rule: the hooks are inert unless
`.claude/pr-config.json` exists at the **main checkout's** root. Docs, `/pr:init`,
`reference/config.md` and both test suites are updated, and the plugin version is bumped
to `0.2.0`.

The objective is delivered. One fail-open remains on the guard's own new activation path,
measured below, and it is the same defect class the ticket exists to remove.

## Prior round

The earlier blocking finding — `pr_repo_configured()` resolving the repo from
`${CWD:-$PWD}`, which fails open on the unparseable-payload path where `$CWD` is
unassigned — is **fixed and sound** in `e2b7116`:

- `CWD=""` at `guard-default-branch.sh:53` runs before any function definition and before
  any `gate()` call, so no inherited `CWD` can steer the check.
- `pr_repo_configured()` now reads `${CWD:-${CLAUDE_PROJECT_DIR:-$PWD}}`.
- Verified live: an empty payload with `CLAUDE_PROJECT_DIR` pointing at a configured repo
  and `$PWD` outside it returns `deny`; the same payload with `CLAUDE_PROJECT_DIR`
  pointing at an unconfigured repo returns nothing. Both directions are now asserted in
  the suite.

This review covers the delta plus a focused re-audit of the two paths the fix touched. It
is not a re-audit of the whole PR.

## What is working well

- **`gate()` as the single activation chokepoint** (`guard-default-branch.sh:119-124`) is
  the right call and the reasoning in the comment is exactly right: the degraded no-jq and
  no-grep paths, the undeterminable-branch path and anything added later all inherit the
  rule for free, without a second place to forget.
- **`pr_repo_configured()` needs neither `jq` nor `grep`.** That is not an accident, it is
  what lets it guard the very paths that exist *because* one of those is missing. Cheap
  and correct.
- **Resolving the config through `git rev-parse --git-common-dir`** rather than a
  cwd-relative test, with a linked-worktree fixture in the suite proving it. The obvious
  spelling (`[ -f .claude/pr-config.json ]` in the `hooks.json` command, as
  `understand-anything` does) would have silently disarmed the guard inside every linked
  worktree — the very environment this branch was developed in. The Open Questions section
  rules it out on its merits rather than by preference.
- **Phase 4 is the standout.** The plan asserted `on-session-start.sh` was already safe
  because of the changelog-folder test; the probe proved otherwise (176 bytes of context
  leaked into an unconfigured repo) and the plan records the wrong premise instead of
  quietly editing it. That is how a plan should read.
- **Mutation testing of the new acceptance phase 0.** Removing the executable bit,
  deleting `hooks.json`, dropping the `Bash` matcher, undeclaring `Stop` and re-adding a
  README fragment each turn the suite red. A check that cannot fail is worthless, and this
  one was proven able to fail.
- The phase-0 executable-bit loop is fed by redirection (`done < "$HOOKLIST"`), not a
  pipe, so its `PASS`/`FAIL` increments survive — the classic subshell trap, avoided.
- `hooks.json` invokes each script **directly** rather than through `bash`, preserving the
  fail-closed executable-bit property the suite then asserts. The two decisions reinforce
  each other.

## Issues found

### Critical

🔴 **The activation check still fails open when the payload carries no `cwd`**

📍 Location: `plugins/pr/hooks/guard-default-branch.sh:274` (interacting with
`pr_repo_configured()` at `:96-112`)

**What I see:**

```bash
# line 274, on the parsed path, after the jq extraction
[[ -n "$CWD" ]] || CWD="$PWD"
```

`pr_repo_configured()` prefers `$CWD` over `$CLAUDE_PROJECT_DIR`:

```bash
local dir="${CWD:-${CLAUDE_PROJECT_DIR:-$PWD}}" common
```

So when a **well-formed** payload has `.cwd` empty or absent, line 274 assigns `$PWD` to
`CWD`, and `$PWD` then *shadows* `CLAUDE_PROJECT_DIR` inside the activation check. The
fallback the previous fix installed is unreachable on this path.

**The risk:** measured just now, not inferred. A configured repo on `main`, hook process
`cd`-ed outside it, `CLAUDE_PROJECT_DIR` correctly set:

| Payload | This branch | `main`'s guard |
|---|---|---|
| `{"cwd":"<repo>","permission_mode":"default",...}` (control) | `ask` | `ask` |
| `{"cwd":"","permission_mode":"default",...}` | **no output, exit 0** | `ask` |
| `cwd` key absent entirely | **no output, exit 0** | `ask` |

`main` emits `"Could not determine the branch in …"` and asks. This branch silently allows
the commit. That is a fail-open **introduced by this PR**, in the one file designed to fail
closed, on the same axis as the finding fixed in `e2b7116` — one path over.

Reachability is the honest caveat: the live harness always sends `cwd`, so this is a
defence-in-depth path rather than a live hole. I am still calling it Critical for three
reasons. This file's stated doctrine is that every undeterminable state fails toward the
operator and that reading it is not evidence it works. The prior round's finding was
equally unreachable in a healthy harness and was treated as blocking. And the fix is one
line that the codebase has **already written elsewhere**.

**Suggested fix:** adopt the spelling the sibling hook already uses at
`verify-close-landed.sh:142`, under a comment that says the same thing:

```bash
[[ -n "$CWD" ]] || CWD="${CLAUDE_PROJECT_DIR:-$PWD}"
```

Verified: with that single change the two rows above return `ask`, and
`test-guard-default-branch.sh` stays green at 52 passed, 0 failed.

Then add the case that would have caught it, next to the malformed-payload block:

```bash
echo "== a well-formed payload with no cwd still gates =="
for p in '{"cwd":"","permission_mode":"default","tool_input":{"command":"git commit -m x"}}' \
         '{"permission_mode":"default","tool_input":{"command":"git commit -m x"}}'; do
  out=$( (cd "$NOCFG" && printf '%s' "$p" | CLAUDE_PROJECT_DIR="$MAINREPO" "$HOOK") )
  got=$(echo "$out" | jq -r '.hookSpecificOutput.permissionDecision' 2>/dev/null)
  ...expect ask...
done
```

**Learning note:** when a value has two sources of truth and one is preferred, the
preference has to hold at **every** assignment, not just at the read. `CWD` here is read
once but written twice, and the second write was authored before the preference existed.
A `resolve_repo_dir()` helper that both sites call would make the ordering impossible to
state in two different ways — worth considering, though the one-line fix is sufficient and
lower risk for this PR.

### Important

🟡 **The new "cwd outside the repo" case fails under the suite's own documented invocation**

📍 Location: `plugins/pr/hooks/test-guard-default-branch.sh:189` (and `:6`)

**What I see:**

```bash
HOOK="$1"                                    # line 6, used verbatim
...
out=$( (cd "$NOCFG" && printf '' | CLAUDE_PROJECT_DIR="$MAINREPO" "$HOOK") )   # line 189
```

Every other case invokes `$HOOK` from the suite's own cwd. This one `cd`s first, so a
relative `$HOOK` no longer resolves.

**The risk:** the suite's header documents exactly that invocation —
`./test-guard-default-branch.sh ./guard-default-branch.sh` — and under it the suite is
**red today**:

```
./test-guard-default-branch.sh: line 189: ./guard-default-branch.sh: No such file or directory
  FAIL cwd outside the repo does not disarm the guard           got=<none> want=deny
passed 51, failed 1
```

With an absolute path it is 52 passed, 0 failed. Two costs, and the second is the
expensive one. A suite that is red on its documented invocation trains the reader to
discount its output. And the failure mode is **indistinguishable from the real defect**:
no output, `want=deny`, which reads precisely as "the guard was disarmed by cwd". The next
person to see this will either dismiss a genuine regression or chase a path bug for an
hour.

**Suggested fix:** absolutise once, at the top, where it protects every future case rather
than this one:

```bash
HOOK="$1"
[[ -n "$HOOK" ]] || { echo "usage: $0 <path-to-guard-default-branch.sh>" >&2; exit 2; }
HOOK="$(cd "$(dirname "$HOOK")" && pwd)/$(basename "$HOOK")"
```

**Learning note:** the moment a test harness changes directory, every path it holds becomes
a liability. Normalise inputs at the boundary, once, rather than at each use — and be
especially wary when a harness bug can counterfeit the exact signal the test exists to
detect.

🟡 **"The close gate is inert with no config" passes for a reason unrelated to config**

📍 Location: `plugins/pr/scripts/test-acceptance.sh`, phase 1

**What I see:**

```bash
OUT=$(echo "{\"cwd\":\"$R\",\"stop_hook_active\":false}" | "$P/hooks/verify-close-landed.sh")
chk_empty "the close gate is inert with no config"   "$OUT"
```

**The risk:** `verify-close-landed.sh:153` returns before any config read unless the
sentinel file exists, and this fixture never arms one. The case therefore produces empty
output in a configured repo too, so it asserts nothing about the activation rule its label
claims to cover. Per Phase 3 that hook is sentinel-scoped by design and needs no gate —
which is fine — but the label tells a future reader that activation *is* covered here. If
someone later adds a pre-sentinel code path, this case will keep passing.

**Suggested fix:** either rename it to what it actually proves —
`"the close gate stays silent with no sentinel armed"` — or arm the sentinel in the
unconfigured repo and assert the behaviour you actually want there. The rename is cheaper
and honest; I would take it.

**Learning note:** a green assertion whose label overstates it is worse than no assertion,
because it occupies the slot where the real one would have gone. Name a test after the
mechanism it exercises, not the property you hope it implies.

### Suggestions

🟢 **`chk "commands resolve through the plugin root"` inspects only the first command**

📍 Location: `plugins/pr/scripts/test-acceptance.sh`, phase 0

```bash
chk "commands resolve through the plugin root" '${CLAUDE_PLUGIN_ROOT}' \
  "$(jq -r '.hooks[][].hooks[].command' "$HJ" 2>/dev/null | head -1)"
```

The plural label covers a singular assertion. In practice the executable-bit loop below
catches a non-`${CLAUDE_PLUGIN_ROOT}` command indirectly — the substitution leaves a path
that is not executable — so the coverage exists, just not where the label promises.
Dropping `head -1` and looping, or asserting the count of matching commands equals the
count of commands, closes the gap for the cost of two lines.

🟢 **`CHANGELOG_DIR` is resolved from `$PROJECT_DIR` while the config comes from the main
checkout**

📍 Location: `plugins/pr/hooks/on-session-start.sh:58`

This is correct as written — the branch folder lives in the worktree, the config at the
main checkout — but the two now sit eight lines apart under a comment that emphasises the
main-checkout resolution. One clause noting that the *folder* is deliberately
worktree-local would stop a future reader from "fixing" the asymmetry.

## Questions

1. Is a payload without `cwd` considered in-contract for this hook? The file defends
   against non-object payloads and empty stdin, which suggests yes — but if you have
   measured that the harness always sends it, say so in the comment at line 274 and the
   Critical finding becomes a one-line comment instead of a one-line fix. Either way the
   asymmetry with `verify-close-landed.sh:142` should not survive.
2. Phase 8 records the guard suite at 48 cases; it now runs 52. Worth reconciling the
   number in `PLAN.md` before close, since the root `README.md` was corrected in this very
   PR for quoting a stale case count.
