## Verification of the round-1 findings

### 1. Critical — parseable-payload-with-empty-`cwd` fail-open: **fixed**

`guard-default-branch.sh:280` now reads:

```bash
[[ -n "$CWD" ]] || CWD="${CLAUDE_PROJECT_DIR:-$PWD}"
```

matching `verify-close-landed.sh:142` and `pr_repo_configured()`'s own
`${CWD:-${CLAUDE_PROJECT_DIR:-$PWD}}` at `:107`. The asymmetry the last round objected to
is gone, and the comment above the line states *why* the chain has to be spelled twice
(the assignment runs before the activation check, so a bare `"$PWD"` shadows
`CLAUDE_PROJECT_DIR` inside the function and the chain there is never reached). That is the
right comment: it names the failure mode, not the mechanics.

**Mutation-verified, both halves.** Reverting the line to `CWD="$PWD"` yields
**52 passed / 2 failed**, exactly as claimed:

```
FAIL empty payload cwd resolves to the project dir       got=<none> want=ask
FAIL empty payload cwd, unconfigured project dir         got={"...decision":"ask"...} want=<no output>
```

Reverting the *other* half — `pr_repo_configured()`'s `local dir` back to `${CWD:-$PWD}` —
yields **50 passed / 4 failed**, re-opening the round-1 hole on the unparseable-payload
path. Both spellings are therefore load-bearing and both are independently pinned. That is
the property that matters: a future reader who "simplifies" either one gets a red suite
rather than a silent fail-open.

The two new cases are the right shape. They assert in **both directions** from the same
process cwd (`cd "$NOCFG"` / `cd "$MAINREPO"` with `CLAUDE_PROJECT_DIR` pointed the other
way), so they prove the verdict comes from the project dir rather than from the process's
working directory — which is the actual invariant, not a proxy for it.

### 2. Important — relative `$HOOK` under a `cd`: **fixed**

`test-guard-default-branch.sh:8-14` resolves `$HOOK` to an absolute path once, before the
`-x` check, so the executable-bit assertion still runs against the right file.

**Mutation-verified.** Deleting the `case` and invoking the suite the documented way
(`./test-guard-default-branch.sh ./guard-default-branch.sh`) yields **52 passed / 2 failed**:

```
FAIL cwd outside the repo does not disarm the guard      got=<none> want=deny
FAIL empty payload cwd resolves to the project dir       got=<none> want=ask
```

Note what those failures *look* like: `got=<none>`, textually identical to the fail-open
the cases exist to catch. That is exactly the trap the comment now calls out, and calling
it out is worth more than the two-line fix. A test that fails for the wrong reason is worse
than no test, because it trains you to distrust a red suite.

### 3. Important — the acceptance case that asserted nothing: **fixed, honestly**

`test-acceptance.sh` now reads `the close gate is silent with no close in flight`, with a
comment that explicitly says this is **not** an activation assertion and points at phase 6
as the place the sentinel is actually exercised.

I checked the claim rather than taking it: `verify-close-landed.sh:145-151` scopes itself
by `${GIT_DIR}/${SENTINEL_NAME}` and exits 0 when that file is absent. The sentinel is
per-repo and only `/pr:close` arms it, so an unconfigured repo can never have one — the
hook genuinely needs no config gate, and the relabel is the correct fix rather than a
weaker substitute for adding an assertion.

Relabelling instead of strengthening was the right call here, and it is worth naming why:
the case's value was never the assertion, it was the *claim* in its name. A test whose name
overstates what it proves is a false negative waiting to happen, because the next person to
audit activation coverage will tick that box and move on.

## Re-audit: is there a remaining fail-open?

The brief asked for this specifically, since two rounds have each found one more. I walked
every path that reaches `gate()` or bypasses it.

| Path | `$CWD` at the time | Resolves activation from | Verdict |
|---|---|---|---|
| Unparseable payload / empty stdin (jq present) | `""` (cleared at `:56`) | `CLAUDE_PROJECT_DIR` → `$PWD` | correct |
| Parsed, empty `cwd` | `""` → assigned at `:280` | `CLAUDE_PROJECT_DIR` → `$PWD` | correct, newly pinned |
| Parsed, `cwd` present | payload `cwd` | payload `cwd` | correct |
| No jq (degraded raw match) | `""`, never assigned | `CLAUDE_PROJECT_DIR` → `$PWD` | correct |
| No grep | assigned at `:280` | same chain | correct |
| Undeterminable branch | assigned | same chain | correct |

`CWD=""` at `:56` runs before every function definition and every `gate()` call, so an
inherited environment variable cannot steer the check — confirmed by reading the order,
and the two new cases exercise it from a foreign process cwd.

`gate()` remains the single chokepoint (`pr_repo_configured || exit 0` is its first
statement), so any gating path added later inherits the rule rather than having to remember
it. That design decision is why this round's fix was two one-liners instead of an audit of
six call sites, and it is the reason I am comfortable that the class is now closed rather
than merely this instance of it.

**One residue, and I am calling it a DROP rather than passing it along.** With `jq` absent
*and* a payload truncated mid-command (`..."command":"git com`), the degraded path's raw
`GIT_VERB` match finds no verb and the hook exits 0. I probed it: with jq off `PATH`, an
empty payload and `{"cwd":` both pass silently. But this is the pre-existing contract of the
no-jq branch (match raw text, over-match, never under-match), unchanged by this PR — it
fails the in-scope test — and it requires two simultaneous unlikely conditions. Any payload
truncated *after* the verb still gates. Recording it so it is not rediscovered as novel in
round 3; it is not worth a ticket.

## What is working well

- **Mutation testing as the acceptance standard for the fix itself.** The claim in the
  commit message ("reverting now yields 52 passed / 2 failed") is precise, falsifiable and
  true. That is the difference between a fix and a fix you can trust six months later.
- **The comment at `:275-280` explains the shadowing**, not just the substitution. Someone
  will eventually look at two identical-looking fallback chains and want to DRY them; the
  comment is what stops them.
- **Both directions asserted.** It would have been easy to add only the "must gate" case.
  Adding "must stay inert" too is what keeps the fix from being over-corrected later into a
  guard that fires in every repo on the machine — the failure mode this whole ticket exists
  to prevent.
- Suites re-run clean at HEAD: guard suite **54 passed / 0 failed**, acceptance suite
  **39 passed / 0 failed** (phase 0 included). Worktree is clean.

### Suggestions

🟢 **The documented case count is stale in three places**

📍 Location: `README.md:67`, `plugins/pr/hooks/README.md:125`,
`changelog/3-ship-the-hooks-with-the-plugin-instead-of-per-repo-settings/PLAN.md:82`

**What I see:**

```
README.md:67              Ships with a 48-case probe suite; ...
hooks/README.md:125       48 cases covering the refspec forms, ...
PLAN.md:82                went from 39 cases to 48, all passing
```

The suite now runs **54**. This was Question 2 last round (recorded then as 52); `c7ab628`
added two more cases without touching the counts.

**The risk:** low, but self-inflicted and slightly ironic — this PR corrected the root
`README.md` precisely *because* it quoted a stale case count. A number that drifts twice in
one branch teaches readers to ignore it, which costs you the one signal that tells a
reviewer whether the suite they just ran is the suite the docs describe.

**Suggested fix:** update all three to 54 before close, or drop the number from the two
READMEs and let the suite's own `passed N` line be the source of truth. The second is
sturdier — prose that restates a computed value will drift again.

**Learning note:** documentation that duplicates a value the code can compute is a cache
with no invalidation. Either automate the refresh or stop caching it.
