🟡 **I-A. The chapter-1 "no clustering" assertion is still vacuous: the chapter has nine paragraphs, not eight**

📍 Location: `plugins/bookcraft/scripts/test-fixtures.sh:89` (the `!primer-fixture-01-what-a-primer-chapter-may-carry.md: 1 of 8` term); `fixtures/primer/primer-fixture-01-what-a-primer-chapter-may-carry.md:11`

**What I see:**
The new negative term is `!...may-carry.md: 1 of 8`, and the chapter's own prose says "It also has eight paragraphs". The checker counts nine. The closing "The closing section names the sources..." is paragraph 9, after the 102-word paragraph 8. With the share threshold lowered to 5% on a scratch copy, the checker prints:

```
REPORT  primer-fixture-01-what-a-primer-chapter-may-carry.md: 1 of 9 paragraphs run 85 words or more, ...
```

The `1 of 8` term doesn't match that, so the suite would still pass.

**The risk:**
This is the exact defect I4 named: a negative assertion that holds by construction. A regression in the share threshold (40 dropped toward 10, or a `-ge` comparison inverted) would pass the suite unchanged. The PR summary and CHANGELOG repeat the "eight paragraphs" claim, so the record describes a guard that isn't there.

**Suggested fix:**
Make the term count-independent and correct the prose:

```
...~!primer-fixture-01-what-a-primer-chapter-may-carry.md: 1 of~!appendix
```

(The paragraph-ceiling report for this chapter reads "may-carry.md: paragraph 8 runs ...", so `: 1 of` can only match a clustering line.) Change "eight paragraphs" to "nine paragraphs" in the chapter and in `pr-summary-2026-11-18.md`. To test the share at its boundary as well, make three of the nine paragraphs run 85 words or more (33%, quiet; four would be 44%, which fires) and assert `!...may-carry.md: 3 of`.

**Learning note:**
Before trusting a negative assertion, make the code emit the thing it forbids (lower a threshold on a scratch copy, as here) and confirm the suite goes red. If it stays green, the assertion is guarding a string the code never prints.

🟡 **I-B. Three handbook restatements the first review named are still unscoped**

📍 Location: `plugins/bookcraft/skills/createbook/SKILL.md:530`, `:229`; `plugins/bookcraft/skills/updatebook/SKILL.md:242`

**What I see:**
- `SKILL.md:530`, in the `overview` paragraph of step 4: "Set it `true` for every new book." The primer template forty lines above says `overview` is left out, and so does § Under the primer profile. The first review listed this line explicitly under C1.
- `SKILL.md:229`: the `chapter-prose.md` reading posture "is fixed by design for every book this skill writes". Item 2 now correctly gives a primer `primer.md § The reader` instead.
- `updatebook/SKILL.md:242`, § Rewriting one chapter step 8: "Redo the chapter's header, `## In short` and concept list". A primer has neither of the first two.

**The risk:**
Probe (c) shows what happens if the `:530` sentence wins: every primer chapter fails with "book.json declares overview but the chapter has no `## In short` section". An orchestrator in a fix loop is as likely to add `## In short` to primer chapters as to drop the key. That is the handbook drift the PR exists to stop. The explicit primer template governs step 4, so this is not blocking. But it is a one-word fix to a sentence the first review already pointed at.

**Suggested fix:**
- `:530`: "Set it `true` for every new guide book; a primer leaves it out."
- `:229`: "... is fixed by design for every handbook this skill writes; a primer's reader is `primer.md § The reader`."
- `updatebook:242`: "Redo the chapter's header, `## In short` and concept list (under `primer`, only `## Sources and further reading`) ..."

**Learning note:**
After a default changes, the last restatements to go stale are the ones inside paragraphs about *other* keys. A grep for "every new book" / "every book this skill" catches them in one pass.
