## What is working well

- **The phase-2 de-privatization is genuinely thorough, not a find-and-replace.** Diffing
  `skills/ask/SKILL.md` against cjus-dev's `council/SKILL.md` shows each private passage
  *rewritten* rather than deleted: the hash-verified same-secret note becomes "council
  spend stays separable from whatever else on the machine uses OpenRouter"; the inherited
  ZDR claim becomes "attach whatever retention guardrail the account offers, because
  guardrails bind per key". The generic warning survives every time the attribution dies.
  That is the hard version of this work.
- **`roster.example.json`'s retention note now teaches the method instead of asserting a
  measurement.** It gives the two endpoints to join, tells the reader to count safe
  endpoints, warns that a single safe endpoint 404s when that provider is down, and says
  outright that any such measurement goes stale. A dated figure would have been easier and
  wrong within a month.
- **`skills/status` is the right shape.** `Bash(sh:*), Read`, "this skill writes nothing,
  anywhere", and "pass the script's output through" — it is a reader over
  `council-state.sh`, not a second implementation of the join. Its *What this skill must
  not claim* section is the honesty contract applied to a skill that could very easily
  have grown its own opinions.
- **`1555e05`'s XDG fix is complete across the surface this branch owns.** All five sites
  now name `$XDG_CONFIG_HOME/council/.env` ahead of `~/.config/council/.env`, matching
  `env.mjs:configDir`. I checked for missed sites: `grep` for `config/council` across
  `skills/`, `reference/` and `openrouter.mjs` returns exactly those five, and the roster
  paths in `ask:90-91` and `setup:84-85` correctly name `$COUNCIL_ROSTER` first, which is
  what `council_roster_path` actually does. Nothing was missed.
- **The `status` corrections are accurate against the script, both of them.** The absent-
  roster bullet (`status:35-38`) matches `council-state.sh:104/161-163/179-180`, where an
  absent roster seats nobody and classes `NONE`. The unconfirmed-suffix correction
  (`status:62-66`) matches `council-state.sh:256-262` exactly — `UNCONFIRMED` is
  interpolated only into the `CROSS-VENDOR` branch, so `HOMOGENEOUS (local)` carries
  nothing. The skill documents the gap rather than asserting the annotation. That is the
  correct call: a skill that promised the suffix would be over-claiming on the script's
  behalf.
- **The detection-unavailable rewrite reasons correctly about what gates what.**
  OpenRouter is gated on `external.openrouter.enabled` plus the key chain
  (`council-state.sh:112-119`), not on any local probe; `codex` needs a binary
  (`:157-159`) and `ollama` needs an endpoint (`:124-153`). The new bullet says precisely
  that, and hands the caller the `exit 3` fallback for the key case.

### Important

🟡 **The detection fallback still tells the model "assume Claude-only", contradicting the
bullet `1555e05` rewrote to fix exactly that**

📍 Location: `plugins/council/skills/ask/SKILL.md:16` (vs. `:25-29`)

**What I see:**

```
!`sh "${CLAUDE_PLUGIN_ROOT}/scripts/detect.sh" 2>/dev/null || echo "detection unavailable — assume Claude-only"`
```

ten lines above the corrected bullet:

```
- If the block says `detection unavailable`, proceed without `codex` or `ollama` members
  and say so — those are the two that need a local binary or a reachable endpoint.
  **OpenRouter needs neither**, only the roster's `enabled` flag and the key chain, so seat
  it from the roster as usual;
```

The string is carried verbatim from cjus-dev's original (confirmed by diff), and
`1555e05` changed the bullet without changing the text the bullet interprets.

**The risk:** `detect.sh` is phase 3, so this fallback fires on **every** invocation for
the life of this branch. The model therefore reads an imperative — "assume Claude-only" —
injected into its context as the *first* thing in the skill, and then meets an instruction
ten lines later telling it to seat OpenRouter anyway. Which one wins is a coin flip, and
the injected context line has position on its side. That is a weaker rerun of the failure
`1555e05`'s own commit message describes: "every OpenRouter member would have been
invisible for the life of this branch and read as a bug in the file phase 2 just ported."
A user with a valid key and three consented models gets a Claude-only council and a
footer that says so.

Note that `skills/setup/SKILL.md:11` already has the right version of this string — plain
`detection unavailable`, no verdict attached. The two skills disagree.

**Suggested fix:** strip the verdict from the data block and let the bullet do the
interpreting.

```
!`sh "${CLAUDE_PLUGIN_ROOT}/scripts/detect.sh" 2>/dev/null || echo "detection unavailable"`
```

**Learning note:** a `!`-block is *data* the model reads, not a place to put instructions.
When a fallback string carries a conclusion, it competes with the prose that is supposed
to draw the conclusion — and prose ten lines down loses to context injected at the top.
Keep the injected block factual and keep every "therefore" in the instructions.

🟡 **`Bash(git diff:*)` does not match the `git` invocation this skill instructs**

📍 Location: `plugins/council/skills/ask/SKILL.md:5` (grant) vs. `:80` (instruction)

**What I see:** `1555e05` narrowed `Bash(git:*)` to `Bash(git diff:*), Bash(git config:*)`.
The command the skill instructs is:

```bash
git -c core.fsmonitor= -c core.hooksPath=/dev/null diff --no-ext-diff --no-textconv <ref>
```

That string starts `git -c core.fsmonitor=…`, not `git diff`. Permission patterns match
literal command prefixes, so the grant does not cover it.

**The risk:** every attachment-by-diff prompts for permission, on a path the frontmatter
claims to have granted. It fails closed, so nothing unsafe happens — but a grant that
looks right and matches nothing is worse than an absent one, because the next person to
touch this file will assume the path is covered. This branch's own `PLAN.md` relies on
exactly this matching rule for the deferred `M=`/`P=` item: "`Bash(node:*)` does not match"
a command that begins with an assignment. The same literal-prefix logic applies to `-c`.

**Suggested fix:** either restore the broad grant, which is what the `pr` plugin does for
the same tool (`plugins/pr/skills/cp/SKILL.md:4` is `Bash(git:*)`), or declare the exact
instructed form:

```yaml
# option A — matches repo precedent
allowed-tools: …, Bash(git:*)

# option B — narrow and exact; must be kept in sync with line 80 verbatim
allowed-tools: …, Bash(git -c core.fsmonitor= -c core.hooksPath=/dev/null diff:*), Bash(git config --get-regexp:*)
```

Option A is the honest one unless the skill's `git` surface is going to stay frozen.
Whichever you pick, the two `git` sites must be read together — that is the only way this
class of defect is visible at all.

**Learning note:** narrowing a permission grant is only a win if the narrow form still
matches. The test is mechanical: take the command the skill literally instructs, and check
that the grant is a prefix of that exact string, flags and all. Anything between the binary
and the subcommand — `-c`, `env VAR=…`, a leading assignment — breaks the match.

### Suggestions

🟢 **`status` asks the model to name which key level is missing, which the script does not
establish**

📍 Location: `plugins/council/skills/status/SKILL.md:45-47`

**What I see:** "Key absent while OpenRouter members are consented … State which of the
three levels is missing."

**The risk:** when the key is absent, `council-state.sh:231` prints only
`key: COUNCIL_OPENROUTER_API_KEY absent -- OpenRouter members cannot be seated`. There is
no per-level detail in the output, and "which of the three levels is missing" has no
answer other than *all three* — so a model following this instruction either states the
tautology awkwardly or invents specificity ("your `~/.config/council/.env` doesn't have
it") that it has not checked. In a skill whose closing section is *What this skill must
not claim*, that is the wrong shape of instruction. The `Read` grant makes it worse, not
better: the way to "check" would be to read a credential file into context.

**Suggested fix:**

```markdown
- **Key absent while OpenRouter members are consented** — the most common surprise. The
  roster says yes and the key chain says no, so those members silently never run. Name the
  chain in order — the environment, `./.env`, then `$XDG_CONFIG_HOME/council/.env` (else
  `~/.config/council/.env`) — and say that none of the three supplied it. Do not guess
  which one the user meant to use, and do not read those files to find out.
```

**Learning note:** the reliable way to keep a reporting skill honest is to bound every
instruction by what its source of truth actually emits. "State which level is missing" is
a question about the filesystem; the script answered a question about resolution.
