## PR review: Add an iac plugin for inter-agent messaging over GitHub comments

Reviewed 2026-10-10 against `main`, at `9d73db9` (12 commits), plus the uncommitted `PLAN.md`
change and the untracked `pr-summary-2026-10-10.md`. This is the first review on the branch, so
there are no earlier rulings to carry forward.

### Summary

The branch adds `plugins/iac/`: a stdlib-only `iac.py` that makes every GitHub call through
`gh api -i`, five skills, four reference documents, an offline suite that runs against a faked
`gh` and a fake model server, a CI workflow, and the marketplace and README rows. Agents exchange
append-only JSON messages as comments on issues in a private repo. A request's state is derived
from the messages that follow it, retries are matched by `from` and `key`, and a local outbox
covers a crash between doing the work and posting the reply. Six of the nine acceptance items were
verified live. At close the operator moved the three that run skills inside Claude Code to
post-deploy testing.

### What is working well

- **The channel is the single source of truth.** `match()` re-derives every request's state from
  the comments on each read, so no local cache can drift from what the other agents see. The
  local file holds only what the channel can't show: the handled pairs, the outbox and the seen
  marks.
- **`post()` treats an uncertain failure correctly.** A 5xx or no answer triggers `find_landed`
  before any repost, and a 4xx is final. Together with `send --key` refusing a reused key whose
  recipient or body differ, retries can't fork a request.
- **Save-then-post for replies,** in both `cmd_reply` and the runner. A crash after the model
  answers posts the saved answer instead of calling the model again, and a test covers it.
- **Trust-boundary checks enforced in code rather than prose:**
  - refusing a non-private repo on every command
  - checking the comment author against the operator's login
  - rejecting secret-looking roster fields and credentialed endpoints
  - never reading `OPENROUTER_API_KEY`
  - `detect` never printing a key
  - bodies going through `--body-file`, and JSON going to `gh` on stdin
- **The fake `gh` reproduces the real quirks the code depends on:** mixed `\n`/`\r\n` header
  endings, exit 1 on 304, 409 on a stale SHA and 422 on a missing one. The tests run `iac.py` as
  a subprocess, so they test the command line a skill uses rather than internals. The test names
  read as a specification: `test_an_agent_that_stops_after_its_ack_resumes_instead_of_skipping`.
- **CI pins the 3.9 floor honestly.** It runs the runner's own `/usr/bin/python3` and fails if
  that isn't 3.9, instead of quietly testing something else.

#### Critical

#### Important

**[Important] A restarted session that only runs `/iac:watch` never learns of its own interrupted request**

Location: `plugins/iac/scripts/iac.py:L1362-L1380` (`waiting`, the `r.state == "pending"` filter
at L1372), and `plugins/iac/skills/watch/SKILL.md:L12-L22` and `L49-L50`.

**What I see:** `waiting()` leaves out `received` requests on purpose, so slow work that has been
acknowledged doesn't wake the session on every poll. But `wait` can't tell this session's own work
in progress from a request that a *previous* session acknowledged and then lost. `/iac:watch`
starts `wait` directly, with no `/iac:check` first.
`test_wait_ignores_its_own_work_in_progress_and_times_out` shows the exact sequence: an `ack`
followed by a `wait` that times out.

**The risk:** a session acks a request and is then closed or crashes. The operator restarts it and
runs `/iac:watch`, as the post-deploy two-session run will. The request then sits in `received`
indefinitely, and nothing tells anyone. That is rule 5 ("an ack is not completion") failing quietly
on the tier A path, and only `/iac:check` or `/iac:status` would show it. The runner and the dot
were verified to resume, but a watching Claude Code session is not.

**Suggested fix:** the smallest fix is in the skill. Under "Start it", add: *"First, follow
`/iac:check` once, so a request an earlier session acknowledged and never answered is resumed
before the watch starts."* A more robust alternative is to have `wait`'s first check
(`check_first=True`) include `received` requests while later polls keep excluding them. A fresh
watch then reports inherited work exactly once.

**Learning note:** a filter meant to suppress noise ("my own work in progress") needs a notion of
*whose* work it is. When the state that tells them apart lives in a process that has gone away,
the safe default at startup is to surface the work, not hide it.

**[Important] A saved reply that can't post wakes `/iac:watch` at once, every time, and hides a re-sent request**

Location: `plugins/iac/scripts/iac.py:L1376-L1379` (outbox items in `waiting`), `L852-L858`
(`flush_outbox` keeping an entry for a closed issue), `L833-L837` (`handled_pairs` counting outbox
entries as handled), and `plugins/iac/skills/watch/SKILL.md:L33-L34`.

**What I see:** `waiting()` adds one item per outbox entry, unconditionally and for every channel.
`flush_outbox` keeps an entry indefinitely when its issue is closed, and keeps it on any 4xx. The
watch skill says to run `/iac:check` and then "start the watch again" after every exit-0 wake.

**The risk:** two consequences follow.

1. **An unbounded loop.** Suppose a reply fails to post (three 5xx responses, or the network) and
   the operator then closes that channel's issue, which the ticket presents as the way to retire a
   channel. A repeated 403 secondary rate limit on POSTs has the same effect. From then on, every
   `wait` returns immediately, and the skill re-arms it after every wake. Each cycle is a model
   turn plus several API calls, with no bound until someone edits the state file by hand.
2. **A self-defeating instruction.** `flush_outbox` tells the operator to "ask the sender to post
   the request again on the new issue". If the sender does that with the same key, as the rotation
   message instructs, `handled_pairs` treats the request as handled, because the outbox entry still
   holds its `(sender, key)`. This agent then never sees it.

**Suggested fix:** any one of the following breaks the loop. The first also fixes the hidden
re-send.

- In `flush_outbox`, when the issue is closed, move the entry out of `outbox` into a separate
  `stranded` list. `status` reports that list, and neither `waiting()` nor `handled_pairs` reads it.
- In `waiting()`, report outbox entries only when nothing else is waiting, and at most once per
  `wait` invocation.
- In the watch skill, under "Exit 0 with items", add: *"If every item was `outbox` and `inbox`
  still couldn't post them, report that and stop rather than restarting."*

**Learning note:** a "retry later" queue needs a terminal state. Without one, a permanently
failing item turns every consumer that reads the queue into a busy loop.

**[Important] The changelog names the live private channel repo by owner/name**

Location: the branch folder's `PLAN.md` at L254, L257, L300, L315, L324, L335 and L345, plus the
uncommitted `## Deferred` line, and its `CHANGELOG.md` at L19, L25 and L30.

**What I see:** the acceptance evidence and the resume notes give the channel repo's full
`owner/name`, 14 times in committed files. The plugin's own docs correctly use the generic
`<operator>/iac-channels`.

**The risk:** the repo's rule is that nothing in it references another repo, and that facts are
stated generically. The `changelog/**` artifacts are named as the place these leaks usually come
from. There is no `#N` backlink here, and the leak value is small, because the owner is already
public and the name is the plugin's documented default. Still, it's an introduced instance of a
rule the operator asked reviewers to hold. Once merged it's in public history, and removing it then
means a history rewrite rather than an edit.

**Suggested fix:** replace each occurrence with "the private channel repo" or
`<operator>/iac-channels`. Comment IDs and issue numbers are enough evidence by themselves. This is
a one-line `sed` over the two files before `/pr:close` commits.

**Learning note:** a repo's own data repo can feel like part of the project, but a hygiene rule
works only if it has no "this one's fine" exceptions that each reviewer has to re-adjudicate.

#### Suggestions

**[Suggestion] `/iac:check` doesn't carry `--channel` through to `ack` and `reply`**

Location: `plugins/iac/skills/check/SKILL.md:L19`, `L47-L49` and `L72-L74`.

Step 1 says to add `--channel` to `inbox` for a channel other than `IAC_CHANNEL`. The `ack` and
`reply` commands show no `--channel`, so after `/iac:watch --channel foo` wakes the session, the
`ack` is refused with "comment N is not a request on channel <IAC_CHANNEL>". Add one sentence:
*"Use the same `--channel` on every command in this run; `inbox --json` reports it as `channel`."*

**[Suggestion] One transient failure during `wait`'s re-read ends the watch**

Location: `plugins/iac/scripts/iac.py:L1434`, which sits outside the retrying `try` at
`L1410-L1426`.

Polls are retried up to ten times, but the full `read_channel` that follows new data isn't, so a
single 5xx or network blip there exits 1. The watch skill then says to stop and not restart. Wrap
the re-read in the same failure counter. The runner is unaffected, because `cmd_run` catches the
error.

**[Suggestion] `gh()` has no subprocess timeout**

Location: `plugins/iac/scripts/iac.py:L150`.

A stalled connection blocks `wait` or `run` indefinitely. Pass `timeout=120` to `subprocess.run`
and map `TimeoutExpired` to `GhError(None, ...)`. `post()` then treats it as uncertain and checks
whether the message landed, which is the right semantics.

**[Suggestion] A runner whose channel was closed underneath it never re-reads the roster**

Location: `plugins/iac/scripts/iac.py:L1643` and `L1701-L1711`.

If `run_pass` hits `require_open`'s refusal, which needs a rotation during a GitHub outage, the
loop backs off and retries the same closed issue indefinitely. Rotation is detected only inside
`poll()`, which is never reached. On that refusal, re-read the roster and `pick_channel` again.

**[Suggestion] A truncated HTTP response crashes the runner with a traceback**

Location: `plugins/iac/scripts/iac.py:L1494-L1501`.

`http.client.IncompleteRead` is an `HTTPException`, not an `OSError`, so it escapes `post_json`'s
handlers and the `CallFailed` path. Nothing is lost, since the ack is posted and a restart resumes,
but catching `http.client.HTTPException` there would turn it into a `failed` reply.

**[Suggestion] An endpoint's query string can carry a secret into the roster**

Location: `plugins/iac/scripts/iac.py:L382-L395`.

`endpoint_problem` rejects credentials in the URL's userinfo but allows `?api_key=...`, and every
tier B vendor reads the roster. Reject a query or fragment on an endpoint, since none of the three
kinds needs one.
