#### Important

🟡 **1. The stray remedy assumes every stray comes from body text, but `closingIssuesReferences` also carries issues linked by hand**

📍 Location: `plugins/pr/skills/close/SKILL.md:L305`

**What I see:**
> In a body this skill wrote, the summary broke `/pr:summary`'s closing-keyword rule: fix the summary and re-run the close, which replaces that body.

**The risk:**
`closingIssuesReferences` is GitHub's list of issues the merge "may close". By default it includes issues someone linked in the PR's Development sidebar: the field takes `userLinkedOnly` and `excludeUserLinked` arguments to split the two sources. The new verify correctly stops on a sidebar-linked stray. But the remedy then tells the model, flatly, that the summary broke the rule. The model will look for a keyword that is not there. It may reword a compliant summary, or it may re-run the whole close, including the review gate, and land on the same stop, because no body edit removes a sidebar link. This is logic the PR added, and the case is reachable through an ordinary GitHub workflow. It is not a regression, because on `main` that stray would have merged silently, so this does not block.

**Suggested fix:**
Add a sentence after the kept-description remedy:

> A stray can also be a manual link from the PR's Development sidebar, which `closingIssuesReferences` includes and no body edit removes. If neither the summary nor the body carries a closing keyword for it, report it as a manual link for the operator to remove in the sidebar, and do not re-run.

If you want the skill to tell the two apart instead of inferring, `gh api graphql` with `closingIssuesReferences(userLinkedOnly: true)` lists only the manual ones. The sentence above is probably enough.

**Learning note:**
When a check asserts on a platform's resolved state, which is the right call and is `evidence-discipline.md`'s rule, the remedy has to cover every input that feeds that state, not just the one you were thinking about when you wrote the check. The assertion was widened correctly. The remedy text was written for the narrower mental model.

#### Suggestions

🟢 **1. Name the colon form in the summary rule**

📍 Location: `plugins/pr/skills/summary/SKILL.md:L55`

GitHub's docs say that "the keywords can be followed by colons or in uppercase", for example `Closes: #N` with a real number. The rule covers case. "A closing keyword followed by an issue reference" can be read as excluding the colon form, and that form is common in commit-style prose. Suggested change: "…in any case and with or without a colon after it, and a reference is…". The verify catches it regardless, so this only saves a stop-and-re-run.

🟢 **2. Say what a stray naming this repository under another name means**

📍 Location: `plugins/pr/skills/close/SKILL.md:L307`

The keying compares against `$REPO`, which comes from `.claude/pr-config.json` or the origin remote. Either can go stale after a repository is renamed or transferred, while GitHub reports the current owner and name. If `gh` still resolves the old name, the ticket then shows as `newowner/newname#42`, the verify reports both "does not close" and a stray, and the close stops. That fails closed, but the cause is not obvious. One clause fixes it: "A stray that names this repository under a different owner or name means `$REPO` is stale: correct `repo` in `.claude/pr-config.json` or the remote." (An alternative is to key on the owner and name parsed from the PR's own `url`, which is always canonical. That is more machinery than this edge case needs.)
