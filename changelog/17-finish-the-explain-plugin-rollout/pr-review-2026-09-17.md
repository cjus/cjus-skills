#### Important

🟡 **Phase 1's checkbox carries no caveat, while the caveat lives 16 lines away**

📍 Location: `changelog/17-finish-the-explain-plugin-rollout/PLAN.md:36`, caveat at `:52`

**What I see:**

Line 36 reads, in full:

```
- [x] Phase 1 (verified 2026-09-17): Install the plugin as a user does ... and verify
  `/explain:qe` and `/explain:qve` both resolve and run from a repo other than `cjus-skills`.
```

The qualification that the *run* half did not happen from a repo other than `cjus-skills`
appears only under `## Open Questions` at line 52, after the Deferred section.

**The risk:**

This is narrow but it matters more here than it would in code, because the document's entire
job is to be the record. A reader scanning the Plan section — which is how a plan gets read
six months later, and how `/pr:close` and any downstream audit read it — sees a checked box
whose text asserts something that was not fully done, with no marker pointing to the
qualification. The branch is scrupulously honest about this gap everywhere else, which is
what makes the one unqualified restatement stand out: the checkbox is the most-read line and
the only one that drops the nuance.

To be clear about severity: the gap is *disclosed*, three times, so nothing is hidden and
the engineering judgment behind it is sound. This is a placement problem, not an honesty
problem, and it is not a regression against the objective.

**Suggested fix:**

Append one clause to line 36 so the checkbox is self-contained:

```
- [x] Phase 1 (verified 2026-09-17): ... (Recorded split: resolution observed in the source repo,
  execution in this worktree; the plugin is user-scoped so the path is identical. See Open
  Questions.)
```

**Learning note:**

In a document of record, a caveat is only as good as its distance from the claim it
qualifies. Readers scan headings and checkboxes and stop; anything load-bearing has to
survive that scan. The rule of thumb is that a qualification belongs in the same visual unit
as the assertion it weakens, not in a later section that a skimmer never reaches.

#### Suggestions

🟢 **`PLAN.md`'s Deferred section reads as "nothing outstanding" while the summary carries two live observations**

📍 Location: `PLAN.md:41-46` versus `pr-summary-2026-09-17.md:103-111`

**What I see:**

`PLAN.md`'s Deferred section opens "Both items triaged here were completed in-branch rather
than deferred out" and lists only the two struck-through items. The summary then records two
further observations "not this branch's to fix": the `page-template.html` footer and the source repo hook-token discrepancy. Neither appears in `PLAN.md`.

**The risk:**

`PLAN.md` is the durable artifact; a PR summary is read once at merge time. A reader who
opens the plan alone concludes nothing was left behind, and the footer defect — which is
live in *this* repo's shipped `explain@0.1.0` — loses its only durable home. The summary's
scope call is right; the problem is only that the note does not survive where it would be
found again.

**Suggested fix:**

Add both to `PLAN.md`'s Deferred section under a short lead-in, marked as observations rather
than work — for example "Not this branch's to fix, recorded so they are not re-derived" —
keeping the struck-through completed pair above them.

**Learning note:**

Deferred sections serve two distinct purposes: tracking work that was handed off, and
preserving observations so a later reader does not rediscover them from scratch. Collapsing
the second into "nothing deferred" is how known defects get found twice.

🟢 **The impact assessment's file count will be stale the moment the summary is committed**

third untracked file that will land in the same PR, and it does not count itself. Either

🟢 **Consider a forward pointer on the superseded Phase 4 entry**

📍 Location: `CHANGELOG.md:115` ("**Phase 4 is half done, and the half that remains is in another repo.**")

A changelog is append-only history and a later dated entry supersedes this one, so this is

hits the pessimistic entry first. A trailing "(superseded — see the 2026-09-17 entry below)"
costs one clause and removes the ambiguity.
