# PR review: port qe and qve into a standalone explain plugin

PR #16 · branch `feature/12-port-qe-and-qve-into-a-standalone-explain-plugin` · reviewed 2026-09-16
Scope reviewed: `origin/main...HEAD` (commit `2ca5105`) plus the uncommitted `PLAN.md`, `CHANGELOG.md` and `pr-summary-2026-09-16.md`.
Acceptance bar: `PLAN.md` § Overview, judged against decisions D-1 through D-6.

## Summary

Packages the two explain skills as a third marketplace plugin: `plugins/explain/` with
`.claude-plugin/plugin.json`, a plugin `README.md`, `skills/qe/SKILL.md`,
`skills/qve/SKILL.md` and `skills/qve/references/page-template.html`, registered in
`.claude-plugin/marketplace.json`. 656 insertions, 0 deletions; the only edit to an
existing file is a six-line insert into the marketplace manifest. Both originals are left
in place, so nothing existing changes behaviour.

This is a well-evidenced, strictly additive port. No in-scope Critical issue. Three
Important items, all of them portability or documentation gaps the port left behind rather
than regressions.

## What is working well

- **Verbatim-first porting, then edits.** Each `SKILL.md` was copied and diff-verified
  against its source before any change, so every edit reads as a diff instead of hiding
  inside a move. I re-ran both diffs against `~/.claude/skills/qe/SKILL.md` and
  `~/dev/the source repo/.claude/skills/qve/SKILL.md`: every hunk is deliberate and matches a
  documented decision. `page-template.html` is byte-identical (both sides sha1
  `747dcd542ba6ead2d18e7f27112e42d63d0d3947`), which is what D-2 promised.
- **The anchored replacement, rather than a global one.** A blind `/qve` → `/explain:qve`
  substitution would have corrupted `OUT_DIR="$HOME/.claude/qve"` (`skills/qve/SKILL.md:67`)
  and the example output path at `:133`. Both survive intact. That is the kind of thing
  that gets shipped broken and found a month later.
- **The dead-command catch.** `qe`'s closing offer of a bare `/qve` would have resolved to
  nothing for a marketplace installer. Broadening Phase 3 to cover both directions and both
  forms was the right call, and the reasoning is recorded rather than silently applied.
- **D-4's evidence holds up under check.** I verified `dataviz` independently: it appears in
  the Claude Code 2.1.274 binary and in no user-level, project-level or cached-plugin skill
  directory, so "resolves from the built-in set" is correct and leaving that reference
  untouched was right. `diagram-dot` becoming conditional with Graphviz named as the real
  requirement is a genuine improvement over the original.
- **The D-5 rationale was written into the skill, not just the plan** (`skills/qve/SKILL.md:120`).
  That is what stops the next person from "tidying" the venv under `${CLAUDE_PLUGIN_ROOT}`
  and paying for it on every release.
- **Validation is stronger than the plan claims.** `PLAN.md` Phase 7 records plain
  `claude plugin validate`. `--strict` also passes, on both `plugins/explain` and the
  marketplace manifest. Worth upgrading the claim.
- **Manifest hygiene.** `plugin.json` matches `bookcraft` and `pr` field for field; the
  marketplace description is reused verbatim from it, which is what both existing entries do;
  the entry is inserted alphabetically and the 6-insert/0-delete diff proves the JSON
  round-trip reformatted nothing.

### Important

🟡 **A fourth machine-scoped skill reference survived the Phase 4 audit: `/debrief`**

📍 Location: `plugins/explain/skills/qve/SKILL.md:35`

**What I see:**

```
Practical shape: 2-5 numbered sections, 1-4 visuals. Beyond that, ask whether the topic
actually wants `/debrief` instead.
```

**The risk:**

D-4 enumerates three cross-skill references (`dataviz`, `diagram-dot`, `make-pdf`) and
disposes of each. `/debrief` is a fourth, and it is in the same bucket as `diagram-dot`:
it lives at `~/.claude/skills/debrief/` on this machine only. I checked the other three
places it could resolve from and it is in none of them — not the source repo's project skills,
not any plugin under `~/.claude/plugins/cache/`, and not the Claude Code binary (`dataviz`
greps out of it, `debrief` does not).

So for anyone who installs `explain@cjus-skills`, `qve` points at a command that does not
exist. It is also the one surviving **bare** slash-command form in either file, which is
precisely what Phase 3 set out to eliminate: this is the same defect class as the `/qve`
offer in `qe` that the PR summary rightly celebrates catching. It fails quietly — the agent
suggests a command, the user types it, nothing happens — which is worse than failing loudly.

**Suggested fix:**

Make it conditional, the way `diagram-dot` now is, or drop the pointer and keep the
judgement:

```markdown
Practical shape: 2-5 numbered sections, 1-4 visuals. Beyond that, the topic probably wants
a full walkthrough rather than an explainer page — say so rather than stretching the page.
(If a `debrief` skill is installed, that is the one to hand off to.)
```

**Learning note:**

An audit that enumerates its targets up front only catches what the enumeration caught. When
the criterion is "any reference a plugin installer may lack", drive the sweep off a mechanical
pass over the file — every backticked `/word` and every `~/` path — and then triage the hits.
Name the list from the grep, not from memory.

🟡 **`qve` still delegates a rule to the host repo's `CLAUDE.md`**

📍 Location: `plugins/explain/skills/qve/SKILL.md:40`

**What I see:**

```
If a claim is load-bearing and you're unsure, verify or hedge — root `CLAUDE.md`
§ Evidence Discipline applies to a rendered page exactly as it does to a chat reply.
```

**The risk:**

That section existed in the source repo, which is why the line was safe where it was written. A
plugin installs into arbitrary repos, most of which have no `CLAUDE.md` and none of which
are obliged to have a section by that name. The rule then resolves to nothing, and the page's
honesty bar quietly drops to whatever the model defaults to — on the one path (`General
topics`) where there is no code to check the claims against.

This repo has already taken a position on exactly this: the root `README.md` describes the
`pr` plugin's reference documents as carrying their rules "so nothing depends on the host
repo having a `CLAUDE.md`". `explain` should meet that same bar.

Line 39 has a milder version of the same thing (`ASSERTIONS.md`, `continuity/`,
`changelog/<branch-slug>/` as grounding sources), but it is hedged as "fair game", so it
degrades to a no-op rather than to a dropped rule. I would leave 39 alone.

**Suggested fix:**

State the rule inline — it is one clause — so the skill carries it:

```markdown
- **General topics** (a pattern, protocol, algorithm): no repo reading needed. If a claim is
  load-bearing and you're unsure, verify it or hedge it — the evidence bar for a rendered page
  is the same as for a chat reply, and where the host repo declares its own, that applies too.
  Do not invent numbers for a chart; label illustrative figures as schematic.
```

**Learning note:**

A skill that ships in a plugin owns every rule it depends on. Any rule it cites from the host
repo is a rule that is optional in practice, and an optional honesty rule is not one.

🟡 **The root `README.md` does not know the third plugin exists**

📍 Location: `README.md:23-58` (§ Plugins) and `README.md:96-113` (§ Layout)

**What I see:**

`## Plugins` carries a `### bookcraft` section with a per-skill table and a `### pr` section
with its own table and lifecycle diagram. `## Layout` enumerates the tree for both. Neither
mentions `explain`, and `README.md:5` still reads "`bookcraft` is the first plugin in it".

**The risk:**

The marketplace manifest is what the CLI resolves; the root README is what a human resolves.
After this PR they disagree: `claude plugin install explain@cjus-skills` works, but nothing
on the repo's front page says the plugin exists or what its two skills do. The plugin-level
`plugins/explain/README.md` is good and does not substitute — `pr` ships no plugin-level
README at all and is still fully documented at the root, which tells you which of the two is
the convention here.

This is drift the PR creates: the README was accurate before the branch and is stale after it.

**Suggested fix:**

Add an `### explain` section after `### bookcraft`, in the same table shape:

```markdown
### explain

Explains a thing to a working engineer: one skill in prose, one as a page you can look at.
Same audience and the same honesty bar, different medium.

| Skill | What it does |
|---|---|
| `/explain:qe` | Explains a topic for a mid-level engineer in at most 250 words — core idea, then mechanism, then why it exists. No preamble, no recap, no follow-up prompts. Grounds itself in the repo's code when the topic touches it. |
| `/explain:qve` | Builds one self-contained HTML page with Mermaid diagrams and opens it, for topics whose *shape* is the point. Refuses rather than decorates: if there is nothing worth drawing it says so and sends you back to `/explain:qe`. |
```

and an `explain/` stanza in § Layout:

```
  explain/
    .claude-plugin/plugin.json    the plugin manifest, and the version of record
    skills/<name>/SKILL.md        one directory per skill
    skills/qve/references/page-template.html   the dark-mode page qve fills in
```

**Learning note:**

Registering something in a manifest and documenting it are two different deliverables. When a
repo keeps a human-facing index, adding an entry to the machine-facing one without it leaves
the project describing itself inaccurately — and the README is the first thing a new installer
reads.

## Questions

   Do you know whether it actually pins the model for a plugin skill? If it is a silent no-op,

   verbatim from the source, so this is a question rather than a finding.
2. **Phase 7's shadowing check.** The revised wording says the namespaced form "should be

   to run Phase 8 first and skip the question? The pre-edit version of Phase 7 had an explicit
   ordering instruction; the new one softens it, and post-merge is exactly where that detail
   gets lost.

## Verdict

VERDICT: APPROVE

Strictly additive, well evidenced against D-1 through D-6, and it regresses nothing — `main`
has no `explain` plugin, and both originals are untouched. The three Important items are
portability and documentation gaps the port left behind; `/debrief` and the root README entry
are each a few minutes of work and worth doing before merge, since both undercut the objective
(a plugin that works anywhere, and is discoverable) without breaking it.
